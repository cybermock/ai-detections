# AI-038 - Sanctioned AI DLP Violation

> **Detection ID:** AI-038
> **Package:** `hdsi_ai_sanctioned_dlp_violation` (v1.1.0, `deployment_type: global`, deployed only where a data path exists, see Data Requirements)
> **Search name:** `Audit - HDSI AI Sanctioned DLP Violation - Rule`
> **Status:** Active. Risk-only (`action.notable = 0`, `action.risk = 1`). The package ships with `enable_alerting: false`.
> **Risk Score:** Dynamic, 5-45 per user. Each row carries one risk object; a host row gets half the user score (minimum 5). Literal fallback: user 20, system 10.
> **MITRE ATT&CK:** T1567 - Exfiltration Over Web Service (Exfiltration)
> **Data Model / Source:** Microsoft Purview DLP for Microsoft 365 Copilot (`o365:management:activity`, `Operation=DLPRuleMatch`) and CIM `DLP.DLP_Incidents`
> **Schedule:** `23 * * * *` (hourly)
> **Lookback Window:** `-65m@m` to `-5m@m` (CIM path, event time); Purview path: events indexed in that slot whose event time is within 72 h
> **Suppression:** 24 hours per `user`,`src`
> **Kill Chain Phase:** `exfiltration` (RBA vector `data_exposure`; also an exfiltration step in the data-collection kill chain aggregator)
> **Last Updated:** 2026-10-09

---

## Overview

This detection raises risk when a **DLP control finds sensitive content going to an AI service the organisation has approved**. Examples: a user pastes a password, a cloud client secret or a card number into a Microsoft 365 Copilot prompt, or a CASB/endpoint DLP incident shows a PII file uploaded to an allow-listed ChatGPT Enterprise workspace.

Approved tools still should not receive credentials or regulated data. The content stays in prompt history, can resurface through Copilot memory or grounding, and a credential pasted anywhere must be rotated. Treat the finding as a **data-handling signal, not proof of theft**: for in-tenant Microsoft 365 Copilot the data stays inside the organisation's Microsoft 365 boundary. Scores are modest for that reason. A single match stays below the 60-point user threshold even for a privileged identity.

There are two data paths:

- **Purview DLP for Microsoft 365 Copilot.** Wherever Purview DLP policies cover the Copilot location, this path needs only the O365 audit index set in `..._purview_events`. Two of the four validation tenants had such policies.
- **CIM DLP incidents** whose destination resolves to an AI provider that `ai_sanctioned_entities` allow-lists for the user, host, identity group (`bunit`) or the whole organisation. This is the exact complement of `Audit - HDSI AI DLP Violation On Service Upload - Rule` (AI-020): each AI-bound incident is scored by one of the two rules, never both. AI-020 is incubating (not released; see [`saved_searches/incubating/hdsi_ai_dlp_violation_on_service_upload/`](../../saved_searches/incubating/hdsi_ai_dlp_violation_on_service_upload/RUNBOOK.md)), so in a release deployment this rule covers sanctioned providers only and CIM DLP incidents to unsanctioned AI providers are not scored by any released rule.

The rule creates no notable.

## Detection Logic

### Plain English

**CIM path**

1. `tstats summariesonly=false` over `DLP.DLP_Incidents` by `user`, `src_user`, `src`, `dest`, `app`, `signature` and `dlp_type`. Placeholder, `SYSTEM`, service and machine accounts become null. Rows with no user and no host, or no `dest` and no `app`, are dropped.
2. Keep only content hits (`..._content_evidence`): a CIM `dlp_type`, or a policy name that names a data class (PII, PCI, secrets, source code, confidential...). A file name or a severity alone is not enough, because CASB add-ons also tag access-control and threat alerts as DLP incidents.
3. Resolve `dest` and `app` to an AI provider with `ai_domains_filter`.
4. Keep only incidents that `ai_unsanctioned_filter(user,src,provider)` *would have dropped*: an active (enabled, not expired) user, host, `bunit` or organisation-wide (`*|<provider>`) allow-list entry.

**Purview path**

1. `DLPRuleMatch` events indexed in the dispatch hour whose event time is within 72 h (the O365 audit API delivers late).
2. Keep Microsoft first-party generative AI: `AppHostCategories` containing `FIRST_PARTY`, or a `Copilot*` location (`Copilot-Sydney` = prompts, `Copilot.M365` = items Copilot processes).
3. Pair each sensitive information type (SIT) with its confidence. A SIT counts at confidence ≥ 85 (`..._purview_min_confidence`), or ≥ 75 for high-impact types. IP-address types never count (`..._purview_ignored_types`).
4. Keep a match only if a SIT survived or the rule is rated medium/high (`..._purview_content_evidence`). Low-severity access rules ("do not let Copilot process external email") and label-only matches drop out.
5. Aggregate per user. Prompt text and SIT values are never copied; a prompt shows as `prompt in <app host>`.

**Both paths**

1. Aggregate per `user` + `src`. Outcome is `blocked` only when everything was blocked. For Purview, at least one rule must itself be enforced (`RuleMode=Enable`) with a block or `RestrictAccess` action. Simulation rules and `RestrictWebGrounding` count as not blocked.
2. Score, then split rows that name both a user and a host (`risk_target`) so the host gets half the user score.

### Key Fields

| Field | Description | Example Value |
|---|---|---|
| `risk_target` | `user` or `system` (rows naming both are split) | `user` |
| `user_display` / `src_display` | User and host, or "no attributed ..." | `jdoe@example.com` |
| `provider` / `ai_domains` | AI provider and host or Copilot app host | `Microsoft 365 Copilot` / `office` |
| `data_sources` | `Purview DLP for Copilot` and/or `CIM DLP` | `Purview DLP for Copilot` |
| `violations` | Distinct matched items (Purview) or incident count (CIM) | `2` |
| `dlp_policies` / `dlp_types` | Policies and data types (names only, never values) | `All Credential Types` |
| `dlp_actions` / `policy_modes` | Rule actions; `enforced` or `simulation` | `NotifyUser` / `simulation` |
| `dlp_severity_max` / `dlp_outcome` | `high`/`medium`/`low`/`unrated`; `blocked` or `not blocked` | `high` / `not blocked` |
| `objects` | Items or `prompt in <app host>` | `prompt in Outlook` |
| `risk_multiplier` | Identity multiplier (1.0-2.0) | `1.0` |

### Risk scoring

| Step | Value |
|---|---|
| Base | 30 when the DLP severity is high/critical or a data type matches `..._high_impact_types` (credentials, secrets, tokens, payment cards, bank accounts, US SSN); 20 for medium or unrated; 10 for low |
| × `severity_weight` | Provider weight on the CIM path (0.3-1.2); 1.0 for Copilot |
| × `risk_multiplier` | Identity `bunit` sensitivity × 1.25 for privileged identities, capped at 2.0 |
| × `..._blocked_factor` | 0.5 when everything was blocked (`0` drops blocked rows) |
| Clamp | `risk_score = min(45, max(5, round(...)))`; host row = half, minimum 5 |

### Thresholds

| Parameter | Default Value | Macro | Notes |
|---|---|---|---|
| Count threshold | none | n/a | One credential or regulated record in an AI prompt is actionable |
| Purview SIT confidence floor | 85 (75 for high-impact types) | `hdsi_ai_sanctioned_dlp_violation_purview_min_confidence` | 65 low, 75 medium, 85 high |
| Ignored SIT names | `^(ip address)` | `..._purview_ignored_types` | Add noisy types your organisation cannot hold |

## Triage Steps

> **Estimated triage time:** 10-15 minutes

Replace `<user>`, `<src>`, `<provider>` and `<risk_object>` with values from the risk event. Replace `index=*` with your O365 audit index if the macro has not been set.

### Step 1: Read the risk event

```spl
| from datamodel:"Risk.All_Risk"
| search source="Audit - HDSI AI Sanctioned DLP Violation - Rule" risk_object="<risk_object>"
| table _time risk_object risk_object_type risk_score risk_message
| sort - _time
```

- The message lists the data source, policies, data types, objects, highest severity and outcome.
- A credential, secret or token type means a rotation task, whatever the rest of the triage shows.

### Step 2a: Review the Purview Copilot matches (Purview path)

```spl
`hdsi_ai_sanctioned_dlp_violation_purview_events` UserId="<user>" earliest=-72h
| rename "SessionMetadata.AppHostCategories{}" as pv_hostcat
| where `hdsi_ai_sanctioned_dlp_violation_purview_ai_scope`
| rename "SessionMetadata.AppHost" as app_host, "PolicyDetails{}.PolicyName" as policy, "PolicyDetails{}.Rules{}.RuleName" as rule, "PolicyDetails{}.Rules{}.RuleMode" as rule_mode, "PolicyDetails{}.Rules{}.Severity" as rule_severity, "PolicyDetails{}.Rules{}.Actions{}" as rule_actions, "PolicyDetails{}.Rules{}.ConditionsMatched.SensitiveInformation{}.SensitiveInformationTypeName" as sensitive_info_types, "PolicyDetails{}.Rules{}.ConditionsMatched.SensitiveInformation{}.Confidence" as confidence, "ItemMetadata.Name" as item
| table _time UserId Location app_host item policy rule rule_mode rule_severity rule_actions sensitive_info_types confidence
| sort - _time
```

- `rule_mode` `Enable` means enforced; `TestWithNotifyUser`/`TestWithoutNotifyUser` means simulation, so the content reached Copilot.
- `Location=Copilot-Sydney` is a prompt the user typed or pasted. `Copilot.M365` is an item Copilot processed on the user's behalf.
- The SIT names say what kind of data matched, not the value. Open the Purview alert or Activity Explorer to see the matched content.

### Step 2b: Review the CIM DLP incidents (CIM path)

```spl
| tstats summariesonly=false allow_old_summaries=true fillnull_value="unknown" count min(_time) as firstTime max(_time) as lastTime values(DLP_Incidents.object) as objects values(DLP_Incidents.signature) as dlp_policies values(DLP_Incidents.dlp_type) as dlp_types values(DLP_Incidents.severity) as dlp_severity values(DLP_Incidents.action) as dlp_action values(DLP_Incidents.vendor_product) as vendor_product from datamodel=DLP.DLP_Incidents where (DLP_Incidents.user="<user>" OR DLP_Incidents.src_user="<user>" OR DLP_Incidents.src="<src>") by DLP_Incidents.user DLP_Incidents.src DLP_Incidents.dest DLP_Incidents.app
| rename DLP_Incidents.* as *
| convert ctime(firstTime) ctime(lastTime)
| table firstTime lastTime user src dest app dlp_policies dlp_types dlp_severity dlp_action objects vendor_product count
| sort - count
```

- Confirm the destination is the approved AI service (an enterprise workspace or tenant) and not a personal account on the same provider.
- Open the incident in the DLP console for the file and matched content.

### Step 3: Confirm the approval that put the event on the sanctioned side

```spl
| inputlookup ai_sanctioned_entities
| search allow_key="<user>|*" OR allow_key="<src>|*" OR allow_key="*|<provider>"
| table entity_type entity provider scope expires owner reason enabled allow_key
```

- CIM path only. The matching entry should be active (`enabled=1`, `expires` in the future). Group entries (`<bunit>|<provider>`) match through the user's ES identity `bunit`.
- If the entry should not exist, remove it: the next incident will then go to AI-020 at a higher score where that incubating rule is deployed. Otherwise no released rule scores it.

### Step 4: Identify the user

```spl
| inputlookup identity_lookup_expanded
| search identity="<user>"
| table identity first last email managedBy bunit category priority
```

- Does the user's role explain handling this data type (for example, payroll and bank accounts)? That makes the paste a policy issue, not an incident.

### Step 5: Check related AI risk

```spl
| from datamodel:"Risk.All_Risk"
| search risk_object="<risk_object>" source="* - HDSI AI * - Rule"
| stats sum(risk_score) as total_risk dc(source) as detections values(source) as sources min(_time) as first_seen max(_time) as last_seen by risk_object risk_object_type
| convert ctime(first_seen) ctime(last_seen)
```

- `Threat - HDSI RBA AI Data Collection Kill Chain - Rule` treats this rule as an exfiltration step after a data-collection detection (clipboard, file-access spike, capture extension).
- Unsanctioned-AI or personal-account detections for the same user suggest the same data may also have gone elsewhere.

### Step 6: Make a determination

- **True Positive:** real credentials, secrets or regulated records were put into an AI prompt or upload.
- **Benign True Positive:** documentation examples, test credentials, or data the user is entitled to handle in an approved workflow.
- **False Positive:** a SIT the organisation cannot hold, reported at high confidence (for example foreign tax IDs), or a policy rule that is not content inspection.

---

## True Positive Indicators

- Credential, password, client secret, token, payment card, bank account or US SSN types, at confidence 85 or from an enforced rule.
- `Location=Copilot-Sydney` (the user typed or pasted the content) rather than an item Copilot read.
- `dlp_outcome=not blocked`: the content reached the AI service.
- Repeated matches for the same user on different days, or several data types in one prompt.
- The user's role does not involve the data type.

---

## False Positive Scenarios

| Scenario | Likelihood | Mitigation |
|---|---|---|
| Microsoft default Copilot DLP policy ("Protect sensitive M365 Copilot interactions", simulation) matching foreign national-ID and tax-number types | High on tenants with that policy | Run the threshold search and add the type names to `..._purview_ignored_types`. Tenant A's 30-day residue (2 users, a foreign tax ID and a DEA number at confidence 85, score 20) is this case |
| "All Credential Types" / "General Password" on documentation examples or test credentials | Medium | Check the matched value in Purview. One such match scores 30 (45 at most for a privileged identity), not enough to cross a threshold alone |
| Low-severity access rules on the Copilot location (about 6,000 matches a day on Tenant C) | Gated out | Already dropped by the content gate. If your tenant rates them medium/high, exclude them in `..._purview_events` |
| CASB access-control or threat alerts tagged `dlp`+`incident` | Gated out | Already dropped by `..._content_evidence` |
| Data-at-rest scanners in the DLP model | No effect | They never name an AI destination; exclude them in `..._filter` to save run time |

---

## Response Actions

### If confirmed True Positive

1. **Rotate:** Rotate any credential, secret, token or key that was exposed, regardless of whether Copilot is approved.
2. **Contain:** For payment or regulated identifiers, follow the data-classification incident procedure. Ask the AI platform admin whether the prompt or item can be purged from history or memory.
3. **Notify:** Inform the user and their manager; involve privacy or compliance for regulated data.
4. **Remediate:** Move the Purview rule from simulation to enforcement for the data types that matter, or add a block action for the Copilot location.
5. **Document:** Record the data types, location, policy mode and the rotation ticket.

### If Benign True Positive

1. Add noisy SIT names to `..._purview_ignored_types`, or exclude the policy in `..._purview_events`.
2. For the CIM path, keep the allow-list entry and document the approved workflow in its `reason` field.
3. Close the finding as Benign True Positive.

## Tuning Guidance

### Reducing false positives

- Set the O365 audit index in `..._purview_events` (the only required tuning step) and append `NOT` terms for policies to ignore.
- Keep `..._content_evidence` identical to `hdsi_ai_dlp_violation_on_service_upload_content_evidence`, so the two DLP rules stay complementary.
- Add the national IDs your organisation actually holds to `..._high_impact_types`.
- Run AI-020 and this rule against the same `hdsi_ai_rba_common` version. With an older common package, a group or organisation-wide entry can drop an incident from neither or both rules.

### Adjusting thresholds

The tenant-specific number is the Purview confidence floor. Review 30 days of Copilot DLP matches by type and confidence:

```spl
index=* sourcetype="o365:management:activity" Operation="DLPRuleMatch" earliest=-30d latest=now
| rename "PolicyDetails{}.Rules{}.ConditionsMatched.SensitiveInformation{}.SensitiveInformationTypeName" as sit, "PolicyDetails{}.Rules{}.ConditionsMatched.SensitiveInformation{}.Confidence" as conf, "SessionMetadata.AppHostCategories{}" as hostcat
| where match(lower(mvjoin(hostcat,",")),"first_party") OR match(lower(coalesce(Location,"")),"^copilot")
| where isnotnull(sit)
| eval pair=mvzip(sit,conf,"#")
| mvexpand pair
| eval sit=mvindex(split(pair,"#"),0), conf=tonumber(mvindex(split(pair,"#"),1))
| stats count dc(UserId) as users by sit conf
| sort - count
```

Keep 85 if foreign ID or tax types appear at 65-75 for users who do not handle such data. Lower it to 75 if your relevant types are mostly reported at 75.

### Adding allowlist entries (CIM path)

An entry here moves an AI-bound DLP incident from AI-020 to this rule:

```
entity_type,entity,provider,scope,expires,owner,reason,enabled,allow_key
group,finance,OpenAI,group,2027-06-30,security,ChatGPT Enterprise workspace,1,finance|openai
group,*,Anthropic,global,2027-06-30,security,enterprise licence,1,*|anthropic
```

### Tuning macros

| Macro | Ships as | Purpose |
|---|---|---|
| `hdsi_ai_sanctioned_dlp_violation_filter` | `()` | CIM path exclusions inside the `tstats` where clause |
| `..._content_evidence` | CIM `dlp_type` or a data-class policy name | CIM content gate |
| `..._purview_events` | `index=* sourcetype="o365:management:activity" Operation="DLPRuleMatch"` | Purview base search |
| `..._purview_window` | 72 h event time, last hour by index time | Late-arrival handling |
| `..._purview_ai_scope` | first-party AI host category or `Copilot*` location | Which Purview locations count |
| `..._purview_content_evidence` | SIT present or rule severity medium/high | Purview content gate |
| `..._purview_min_confidence` / `..._purview_ignored_types` | `85` / `"^(ip address)"` | SIT floor and ignore list |
| `..._high_impact_types` | credentials, secrets, tokens, cards, bank accounts, US SSN | Raises the base to 30 |
| `..._blocked_factor` | `0.5` | Score factor when everything was blocked |
| `..._customizations` / `..._risk_score` | `search *` | Post-aggregation hook / last-pipe score override |
