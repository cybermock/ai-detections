# AI-015 - HDSI AI After Hours Service Usage

> **AD HOC DETECTION. The rule emits nothing until it is configured per tenant.** The package ships with `deployment_type: adhoc` and `hdsi_ai_after_hours_service_usage_utc_offset = null()`. While the offset is unset the business-hours clock is empty and every row is dropped. Splunk Cloud runs scheduled searches in UTC, so an unconfigured clock would label a US afternoon as "after hours". Set the offset (and `..._dst_rule`) before enabling, and see [Data Requirements](#data-requirements).

> **Detection ID:** AI-015 (runbook ID; results carry `detection_id=hdsi_ai_after_hours_service_usage`)
> **Search name:** `Network - HDSI AI After Hours Service Usage - Rule`
> **Package:** `hdsi_ai_after_hours_service_usage` v1.1.0 (`deployment_type: adhoc`, `enable_alerting: false`)
> **Status:** Active, ad hoc deployment only (requires the business-hours clock)
> **Output:** Risk only (`action.notable = 0`). Aggregators raise the notable.
> **Risk Score:** `user` only. Dynamic `risk_score = min(40, max(1, round(base × severity_weight × risk_multiplier)))`, base 10 (`requests`) or 20 (`upload`, 5 MB or more). Literal `_risk` fallback 10. Measured 7 to 10 on a PAN-OS tenant once configured.
> **MITRE ATT&CK:** T1567 - Exfiltration Over Web Service (Exfiltration)
> **Data Model:** `Web` (egress proxy, SWG or SSE/CASB with `user` and `action`)
> **Schedule:** `12 * * * *` (hourly at :12)
> **Lookback Window:** `-65m@m` to `-5m@m`
> **Suppression:** 24 h (`86400s`) per `user` and `signal_type` (at most one `requests` and one `upload` event per user per day)
> **Kill Chain Phase:** `exfiltration` (multi-vector aggregator vector: `usage_anomaly`)
> **Last Updated:** 2026-10-09

---

## Overview

This detection finds **identified users who use AI web services repeatedly, or send them a lot of data, outside business hours**. The default after-hours window is before 06:00, from 20:00, and all of Saturday and Sunday, on a business-hours clock that the tenant sets. Only requests the proxy **allowed** count. Blocked attempts never reached the provider, so they appear in the risk message as `blocked_requests` but never qualify a user.

After-hours use is not malicious on its own. It is a context signal: data sent to an AI service at 02:00 or on a Sunday is less likely to be seen and less likely to be for an approved purpose. Typical actors are an employee working late, a departing employee moving material out, or a compromised account used at night. The rule adds a small amount of risk to the user so that the aggregators can weigh it with other AI-RBA signals.

The risk object is the bare account name: a proxy value of `DOMAIN\jdoe` becomes `jdoe` (UPNs stay UPNs), so the risk adds to the same object as other detections.

## Detection Logic

### Plain English

1. Query `Web` with `tstats` (`fillnull_value="unknown"`, `Web.user!="unknown"`), split by user, `src`, `url_domain`, `site`, `action` and 10-minute periods. Rows with placeholder users are dropped; `DOMAIN\` is stripped from `user` (the raw value is kept as `user_raw`).
2. Compute the business-hours clock for each period (`..._local_clock`, from `..._utc_offset` + `..._dst_rule`, or the owner's time zone when the offset is `"owner"`), and keep only after-hours periods (`..._after_hours`). During business hours every row is dropped here, before any lookup.
3. Mark requests whose `action` is in `..._blocked_actions` as blocked. Blocked requests and bytes never count.
4. Resolve the host (`url_domain`, or the SSE application name in `site` when `url_domain` is empty) with the common `ai_domains_filter`. Keep only `usage_type="web"` (`..._usage_types`), so IDE assistants, API endpoints and model registries are excluded.
5. Treat background hosts (`ai_traffic_class="background"` in the registry, or matching `..._background_hosts`) as not counting toward the thresholds.
6. Remove approvals with `ai_unsanctioned_filter(user,src,provider)` (user, host, identity `bunit` group, or organisation-wide `*|<provider>`).
7. Keep the user when `request_count >= 50` **and** `active_buckets >= 2` (repeated use, not one page load), **or** `mb_out >= 5` (upload).
8. Score: base 10, or 20 for `upload`, × highest provider `severity_weight` (0.3 to 1.2) × `risk_multiplier` (identity `bunit` sensitivity, × 1.25 privileged, max 2.0); minimum 1, maximum 40.

### Key Fields

| Field | Description | Example Value |
|---|---|---|
| `user` | Normalised account name (risk object) | `jdoe` |
| `user_raw`, `drilldown_user` | Raw proxy value(s); drilldown-safe copy with `\` and `"` replaced by `*` | `CORP\jdoe`, `CORP*jdoe` |
| `signal_type` | `requests` or `upload` | `requests` |
| `request_count`, `active_buckets` | Allowed foreground AI requests; 10-minute periods with such requests | `64`, `4` |
| `total_requests`, `blocked_requests` | Allowed including background; blocked (not counted) | `91`, `0` |
| `mb_out` | MB sent by allowed requests | `0.0` |
| `provider_list`, `ai_domains` | Providers and hosts with allowed traffic | `Google Gemini` |
| `local_start`, `local_end`, `local_tz`, `after_hours_reason` | When it happened on the business-hours clock | `Sat 21:10`, `Sat 22:10`, `UTC-4`, `weekend` |
| `src` | Up to 3 source addresses | `10.8.4.22` |
| `severity_weight`, `risk_multiplier`, `base_score`, `risk_score` | Scoring | `0.8`, `1.0`, `10`, `8` |

### Thresholds

| Parameter | Default | Macro | Notes |
|---|---|---|---|
| Business-hours time zone | `null()` (silent) | `hdsi_ai_after_hours_service_usage_utc_offset` | **Required.** Standard-time offset in hours (`-5`, `0`, `1`, `5.5`) or `"owner"` |
| Daylight saving rule | `"none"` | `hdsi_ai_after_hours_service_usage_dst_rule` | `"us"`, `"eu"` or `"none"` |
| After-hours definition | before 06:00, from 20:00, weekends | `hdsi_ai_after_hours_service_usage_after_hours` | `local_dow` 0 = Sunday, 6 = Saturday |
| Allowed foreground requests per hour | 50 | `hdsi_ai_after_hours_service_usage_min_requests` | About p90 (weekday night) to p95 (Saturday) on the PAN-OS validation tenant |
| 10-minute periods with requests | 2 | `hdsi_ai_after_hours_service_usage_min_buckets` | Stops a single page-load burst |
| Upload MB per hour | 5 | `hdsi_ai_after_hours_service_usage_upload_mb` | Needs `bytes_out` from the proxy |
| Usage types counted | `"web"` | `hdsi_ai_after_hours_service_usage_usage_types` | Add `"cli"`/`"api"` only if background jobs are not expected at night |

## Triage Steps

> **Estimated triage time:** 10 to 15 minutes. Replace `<user>` (normalised name from the risk event) and `<drilldown_user>` (from the result, e.g. `CORP*jdoe`). Run each search over the time of the risk event (time picker), unless stated otherwise.

### Step 1: Validate the risk event

```spl
| from datamodel:"Risk.All_Risk"
| search source="Network - HDSI AI After Hours Service Usage - Rule" risk_object="<user>"
| table _time, source, risk_object, risk_score, signal_type, local_start, local_end, local_tz, after_hours_reason, provider_list, risk_message
| sort - _time
```

- Check `local_start`, `local_end` and `local_tz` against the user's real working hours. A wrong `local_tz` means the clock is mis-set (Step 6).
- `upload` events (score 20 base) matter more than `requests` events.

### Step 2: Identify the user

```spl
| inputlookup identity_lookup_expanded
| search identity="<user>"
| table identity, first, last, email, bunit, category, priority, managedBy, endDate
```

- Shift workers, staff in other time zones and on-call teams explain most rows.
- A user with an `endDate` soon (leaver) or in a sensitive `bunit` deserves more attention. The ES identity has no `department`; `bunit` is used.

### Step 3: Review the AI web activity

This is the rule's second drilldown. It uses `drilldown_user` so `DOMAIN\user` values match, and it handles both `url_domain` (proxies) and `site` (SSE app names):

```spl
| tstats summariesonly=t allow_old_summaries=t fillnull_value="unknown" count sum(Web.bytes_out) as bytes_out values(Web.url) as url values(Web.action) as action values(Web.http_user_agent) as http_user_agent min(_time) as firstTime max(_time) as lastTime from datamodel=Web where (Web.url_domain=* OR Web.site=*) Web.user="<drilldown_user>" by Web.user Web.src Web.url_domain Web.site
| rename Web.* as *
| eval ai_domain=lower(coalesce(nullif(url_domain,"unknown"),nullif(site,"unknown"))), ai_input_type=if(isnull(nullif(url_domain,"unknown")),"app","host"), url_domain=coalesce(nullif(url_domain,"unknown"),site)
| `ai_domains_filter`
| eval mb_out=round(bytes_out/1024/1024,2), url=mvindex(url,0,9)
| convert ctime(firstTime) ctime(lastTime)
| table firstTime, lastTime, user, src, provider, url_domain, usage_type, count, mb_out, action, http_user_agent, url
| sort - count
```

What to look for:

- **Sustained, interactive use** (requests spread over many periods, several providers, upload URLs) versus an **idle tab or extension** (one host polling evenly all night).
- **Uploads:** `mb_out` and upload/file URLs. Upload rows on a sensitive user are the main reason to escalate.
- **Blocked attempts:** listed with their `action`. A user retrying blocked services at night is policy context, not after-hours use.
- **Source:** VPN pool, office or unexpected address.

### Step 4: Check for related detections

```spl
| from datamodel:"Risk.All_Risk"
| search risk_object="<user>" source="*HDSI*"
| stats sum(risk_score) as total_risk dc(source) as detections values(source) as sources by risk_object
| sort - total_risk
```

- This rule is a context signal (10 to 40). It maps to the `usage_anomaly` vector of `Threat - HDSI RBA AI Multi-Vector Risk - Rule`.
- User risk counts toward `Threat - HDSI RBA AI User Risk Threshold Exceeded - Rule` (60, at least two distinct detections) and `Threat - HDSI RBA AI User Critical Risk Threshold Exceeded - Rule` (90). After-hours risk alone never reaches either.
- Escalate when the same user also has upload, DLP, data-access-spike or personal-account risk in the same 24 h.

### Step 5: Determine sanctioned status

```spl
| inputlookup ai_sanctioned_entities
| where enabled=1 AND (lower(entity)=lower("<user>") OR match(allow_key, "^\*\|"))
| table entity_type, entity, provider, scope, expires, owner, reason, allow_key
```

- The second condition lists organisation-wide approvals (`*|<provider>`). Also check group approvals: the common macro keys groups on the identity `bunit` from Step 2 (`<bunit>|<provider>`).

### Step 6: Check the business-hours clock (if the time looks wrong)

```spl
| makeresults
| `hdsi_ai_after_hours_service_usage_local_clock`
| eval is_after_hours=if(`hdsi_ai_after_hours_service_usage_after_hours`, "yes", "no")
| table _time, local_slot, local_tz, local_hour, local_dow, is_after_hours
```

- `local_tz` empty means the offset is unset (the rule is silent). A wrong offset or DST rule shifts every result; fix `..._utc_offset` / `..._dst_rule`.

### Step 7: Make a determination

- **True Positive:** unexplained after-hours AI use, especially uploads, by a user without a night-time role, or together with other data-exposure risk.
- **Benign True Positive:** night shift, other time zone, on-call or an approved assistant. Approve by `bunit` or user.
- **False Positive:** mis-set clock, idle tab or extension polling a foreground host, blocked-action values not recognised as blocked.

---

## True Positive Indicators

- `signal_type=upload` with several MB sent to a general-purpose AI service.
- The user's role has no after-hours duties, and the activity started at an unusual time for them.
- The user is a leaver, or is in a sensitive `bunit`.
- Other HDSI AI risk on the same user in the same day (uploads, DLP, personal account, data-access spike).
- The source address is unusual (unexpected VPN or location).

---

## False Positive Scenarios

Evidence from the 2026-10-09/10 validation on 4 production ES tenants (package README):

| Scenario | Likelihood | Mitigation |
|---|---|---|
| Shift workers, other time zones, on-call staff | High | Approve by `bunit` or user in `ai_sanctioned_entities`, or exclude in `..._filter`. Split the rule per region if offices span time zones |
| Idle tab or writing extension polling the foreground host all night | Medium | Background hosts are already excluded. On Tenant A one Gemini user qualified in two consecutive Friday-night windows (54 to 60 requests); 24 h suppression turns this into one score-10 event |
| Unconfigured or wrong clock | High if mis-set | Ships silent (`null()`). Check `local_tz` in the risk message and Step 6 |
| Licensed enterprise assistant (e.g. Microsoft 365 Copilot) uploads | Medium where enabled in the registry | Approve organisation-wide (`*|microsoft 365 copilot`) or raise `..._upload_mb`. On Tenant C the Copilot Studio app is opt-in in the registry, so it no longer fires |
| Vendor-specific blocked action not in `..._blocked_actions` | Low | Add the value; CIM uses `blocked` |
| IDE and agent traffic left running overnight | n/a | Excluded by `..._usage_types` (GitHub Copilot appeared after hours for 122 users in 7 days on the SSE tenant) |

## Response Actions

### If confirmed True Positive

1. **Contain:** if data exposure is suspected, restrict the user's AI access at the proxy and review active sessions.
2. **Notify:** the user's manager, and data governance if uploads were involved.
3. **Investigate:** list what was uploaded (Step 3 URLs, `mb_out`), what the user accessed before (file servers, SaaS downloads) and the user's other risk.
4. **Remediate:** reinforce the AI acceptable-use policy; provide an approved service if there is a business need.
5. **Document:** record findings in the case.

### If Benign True Positive

1. Add the user or `bunit` to `ai_sanctioned_entities` with an `expires` date, or exclude night-shift service accounts in `..._filter`.
2. Put the justification in `reason`.
3. Close the related aggregator notable (if any) as benign.

## Tuning Guidance

### Reducing false positives

- Set the clock correctly (`..._utc_offset`, `..._dst_rule`) and adjust `..._after_hours` to the organisation's working week.
- Add extra background hostnames to `..._background_hosts` when a polling host keeps qualifying.
- Approve night-shift groups by `bunit` and licensed assistants organisation-wide.
- Use `hdsi_ai_after_hours_service_usage_customizations` for post-aggregation exclusions and `hdsi_ai_after_hours_service_usage_risk_score` (last pipe) to rescale `risk_score`.
- On large proxy tenants, paste the performance pre-filter from the package README into `..._filter` (Tenant A: 15 to 24 s per hourly run instead of 107 to 150 s, same rows).

### Adjusting thresholds

Set the clock first. Then derive `..._min_requests` from each user's busiest after-hours window over 1 to 7 days. The full search is in the package README, section *Threshold*. Its core:

```spl
| tstats summariesonly=t allow_old_summaries=t fillnull_value="unknown" count from datamodel=Web where (Web.url_domain=* OR Web.site=*) Web.user!="unknown" `hdsi_ai_after_hours_service_usage_filter` by Web.user Web.url_domain Web.site Web.action _time span=10m
| rename Web.* as *
| where NOT in(lower(action), `hdsi_ai_after_hours_service_usage_blocked_actions`) AND NOT in(lower(user),"-","n/a","none","null")
| eval user=replace(user,"^.*[\\\\]","")
| `hdsi_ai_after_hours_service_usage_local_clock`
| where `hdsi_ai_after_hours_service_usage_after_hours`
| eval ai_domain=lower(coalesce(nullif(url_domain,"unknown"),nullif(site,"unknown"))), ai_input_type=if(isnull(nullif(url_domain,"unknown")),"app","host"), win=floor((_time-420)/3600)
| stats sum(count) as count values(_time) as bk by user ai_domain ai_input_type win
| `ai_domains_filter`
| search usage_type IN (`hdsi_ai_after_hours_service_usage_usage_types`)
| where NOT (ai_traffic_class="background" OR match(ai_domain, `hdsi_ai_after_hours_service_usage_background_hosts`))
| stats sum(count) as req values(bk) as bk by user win
| where mvcount(bk)>=`hdsi_ai_after_hours_service_usage_min_buckets`
| stats max(req) as busiest_window by user
| stats count as users perc50(busiest_window) as p50 perc90(busiest_window) as p90 perc95(busiest_window) as p95 perc98(busiest_window) as p98 count(eval(busiest_window>=50)) as users_ge_50
```

On an SSE tenant that logs about one event per session, the request path rarely fires and the upload path does the work. That is intended.

### Adding allowlist entries

`ai_sanctioned_entities.csv` in `hdsi_ai_rba_common` (lower-case keys; `<user>` is the normalised name):

```
entity_type,entity,provider,scope,expires,owner,reason,enabled,allow_key
group,network operations,*,group,<YYYY-MM-DD>,<your_name>,<justification>,1,network operations|*
user,jdoe,OpenAI,provider,<YYYY-MM-DD>,<your_name>,<justification>,1,jdoe|openai
```

## Data Requirements

| Requirement | Details |

| Data Model | `Web`, accelerated, from an **egress** web proxy, SWG or SSE/CASB. Inbound server logs (load balancer, WAF, IIS) never match |

Validation summary (read-only, 2026-10-09/10, 4 production ES tenants): the rule and both drilldowns parse on Tenants A to D, with no FATAL/ERROR messages. With shipped defaults (offset unset) every tenant returns 0 rows, as designed. Configured as US Eastern: Tenant A (PAN-OS URL logs, about 10% of AI events carry a user, no `bytes_out`) flagged 3 to 7 users per replayed night or weekend day at scores 7 to 10, so about 5 to 8 risk events a day. Tenant B (inbound logs, no user on AI rows) and Tenant D (inbound IIS only) have no data path. Tenant C (SSE, `site` = app name) returned 0 with the shipped registry.
