# AI-031 - HDSI AI Generated Phishing Indicators

> **Detection ID:** AI-031 (`detection_id=hdsi_ai_generated_phishing_indicators`)
> **Search name:** `Threat - HDSI AI Generated Phishing Indicators - Rule`
> **Package:** `saved_searches/packages/hdsi_ai_generated_phishing_indicators` (version 1.1.0, `deployment_type: global`, ships `enable_alerting: false`)
> **Status:** Active, risk only (`action.notable = 0`, `action.risk = 1`). Notables come from the `HDSI RBA AI` aggregators.
> **Risk Score:** user (the internal recipient address) only, 20 to 60 (computed `risk_score`; the literal `_risk` fallback is 25)
> **MITRE ATT&CK:** T1566.002 - Phishing: Spearphishing Link (Initial Access); T1608.005 - Stage Capabilities: Link Target (Resource Development); T1588.007 - Obtain Capabilities: Artificial Intelligence (Resource Development)
> **Data Model:** `Email.All_Email` (accelerated, with `url` populated); optional `Web` for the click signal
> **Schedule:** `12 * * * *` (hourly at :12)
> **Lookback Window:** `-65m@m` to `-5m@m` (internal-domain inference looks back 24 h on its own)
> **Suppression:** `user` for 86400 s (24 h)
> **Kill Chain Phase:** Initial Access (`ai_kill_chain_phase=initial_access`)
> **Last Updated:** 2026-10-09

---

## Overview

This detection finds **delivered inbound email that links to a site published with an AI site or app builder**: Lovable (`*.lovable.app`), Vercel v0 previews (`*.vusercontent.net`), Gamma documents (`gamma.app/docs/...`, `*.gamma.site`), Base44, Bolt, Create, Replit, Framer and Figma Sites. It also catches Vercel and Netlify hosts (`*.vercel.app`, `*.netlify.app`) when the link has lure wording, points to a payload file, or the gateway hard-blocked the same site for other recipients from a non-bulk sender.

Attackers use these builders to produce convincing credential-harvesting pages in minutes, on trusted domains that most URL reputation engines do not block. Public reporting from 2025 covers Lovable, v0 and Gamma phishing campaigns. The rule flags the **hosting channel** that AI builders create. It cannot tell that a page or message was written by AI.

Each run writes risk on the **internal recipient** (`user` = recipient address). The score rises with lure wording, a payload link, a free-mail sender, copies of the same site that the gateway blocked, and a visit by the recipient to the host. No notable is created; the user threshold aggregators and the multi-vector aggregator (`adversarial` vector) decide.

Version 1.1.0 replaced a correlation of "the user made 5 or more AI web requests" with "the user sent 10 or more emails". That join never matched (`DOMAIN\user` against email addresses), and with the join fixed it measured ordinary office work.

## Detection Logic

### Plain English

1. `tstats` over `Email.All_Email` keeps rows whose `url` matches a cheap builder/hosting pre-filter, grouped by `recipient`, `src_user`, `url` and `action`.
2. The URL host and path are parsed (lowercased, scheme/userinfo/port stripped, leading `www.` removed). `..._platform` classifies the host as `ai_builder` (only serves builder-published content) or `generic` (`vercel.app`, `netlify.app`). Builder home pages (`lovable.dev`, `v0.app`, `bolt.new`, the `gamma.app` root) are not matched.
3. Static assets (images, CSS, fonts, Lovable `/__l5e/` and Next.js/Astro static paths) and hosts in `..._allowed_hosts` are dropped.
4. For each link: `lure` (credential, document/e-signature, finance/HR, update and brand words, but never unsubscribe/preference links), `payload` (archive, script, disk image, executable), `other_stopped` (other recipients whose copy of a link to the same site was hard-blocked), `link_bulk` (any sender of the link is a bulk/ESP sender) and `freemail_sender`.
5. A delivered link is kept when it is on an `ai_builder` host, or on a `generic` host with lure wording, a payload, or blocked copies for others from a non-bulk sender.
6. Only delivered mail from **external senders** to **internal recipients** is kept. A recipient is internal when the address resolves in `identity_lookup_expanded`, its domain is in `cim_corporate_email_domains.csv`, or its domain is one of the mail domains inferred from 24 h of Email data (`..._internal_domains`). Senders in a corporate or inferred domain are excluded.
7. **Click branch:** `tstats` over `Web` for the same hosts in `url_domain` or `site` (`fillnull_value="unknown"`, host = `url_domain`, or `site` when `url_domain` is empty). The web user (with `DOMAIN\` stripped) and the recipient are joined on the identity record and the host; `clicked=1` when the recipient reached the emailed host in the same window.
8. Each link is scored; the top-scoring link per recipient sets the score, `url_host`, `top_link` and the evidence string.

### Scoring

- Base: 25 for `ai_builder`, 20 for `generic`.
- +15 lure wording, +20 payload file, +10 free-mail sender, +15 stopped for other recipients, +20 clicked; -15 bulk/ESP link.
- Links below `..._min_score` (20) are dropped.
- `risk_score = min(60, round(base_score x risk_multiplier))`, where `risk_multiplier` comes from `ai_risk_multiplier` (identity `bunit` sensitivity, x1.25 for privileged identities, capped at 2.0).

### Key Fields

| Field | Description | Example Value |
|---|---|---|
| `user` / `recipient` | Internal recipient address (risk object) | `jsmith@example.com` |
| `url_host` / `top_link` | Host and host+path of the top-scoring link | `docs-portal.base44.app` / `docs-portal.base44.app/sign` |
| `url_host_list` / `links` / `link_count` | Qualifying hosts, links and their count | `docs-portal.base44.app` |
| `provider` / `ai_platforms` | Builder or hosting platform(s) | `Base44` |
| `senders` / `sender_list` / `sender_count` | External sender address(es) | `someone@gmail.com` |
| `subject` | Up to 5 subjects | `Contract ready for signature` |
| `email_events` | Delivered email events | `1` |
| `lure` / `payload` / `freemail_sender` / `link_bulk` / `other_stopped` / `clicked` | Indicator flags (`other_stopped` is a count) | `1` / `0` / `1` / `0` / `0` / `0` |
| `evidence` | Human-readable indicator list | `lure wording in link; free-mail sender` |
| `base_score` / `risk_multiplier` / `risk_score` | Score before and after the identity multiplier | `50` / `1.0` / `50` |

### Thresholds

| Parameter | Default | Macro | Notes |
|---|---|---|---|
| Minimum per-link score | 20 | `hdsi_ai_generated_phishing_indicators_min_score` | Drops a plain builder link from a bulk/ESP sender (25 - 15 = 10); 35 keeps only links with a second indicator |
| Delivered actions | `"delivered","allowed"` | `..._delivered_actions` | Only these rows create risk |
| Hard-block actions | `"blocked","quarantined","quarantine","dropped","rejected"` | `..._blocked_actions` | Feed the "stopped for other recipients" signal |
| Discard actions | `"__none__"` (off) | `..._discard_actions` | Opt-in; Proofpoint `deleted` is routine graymail on at least one tenant |

## Triage Steps

> **Estimated triage time:** 10 to 20 minutes. Treat a score of 45 or more, or any `clicked=1`, as urgent.

### Step 1: Validate the risk event

Set the time picker to the last 7 days.

```spl
| from datamodel:"Risk.All_Risk"
| search source="Threat - HDSI AI Generated Phishing Indicators - Rule" risk_object="$user$"
| table _time, risk_object, risk_score, base_score, provider, url_host, top_link, url_host_list, sender_list, subject, evidence, clicked, risk_message
| sort - _time
```

- Read `evidence` first. A free-mail sender with lure wording, a payload link, blocked copies for others, or a visit by the recipient is the high-confidence case.
- `evidence="delivered link only"` (score 25) is usually a partner's Gamma document or a small vendor's Lovable page.

### Step 2: Identify the recipient

```spl
| inputlookup identity_lookup_expanded where identity="$user$"
| table identity, first, last, email, managedBy, bunit, category, priority, watchlist
```

- Finance, HR, executive assistants and privileged users are the usual targets of e-signature, invoice and payroll lures.

### Step 3: Review every builder link the recipient received

This is the rule's second drilldown. Widen the time range to 7 days to see earlier messages from the same sender.

```spl
| tstats summariesonly=t allow_old_summaries=t count values(All_Email.action) as action values(All_Email.subject) as subject min(_time) as firstTime max(_time) as lastTime from datamodel=Email.All_Email where All_Email.recipient="$recipient$" `hdsi_ai_generated_phishing_indicators_url_prefilter` by All_Email.src_user All_Email.recipient All_Email.url
| rename All_Email.* as *
| convert ctime(firstTime) ctime(lastTime)
| table firstTime, lastTime, src_user, recipient, action, url, subject, count
| sort - lastTime
```

- Does the sender have a history with the recipient? A first-time free-mail sender with a document or sign-in lure is the classic pattern.
- Look at the full path: `/sign`, `/login`, `/verify`, `/invoice`, `/download/*.zip` are lure or payload paths; `/unsubscribe` and tracking paths are not.

### Step 4: Scope the campaign

Everyone who received a link to the same host, and what the gateway did with each copy:

```spl
| tstats summariesonly=t allow_old_summaries=t count values(All_Email.subject) as subject min(_time) as firstTime max(_time) as lastTime from datamodel=Email.All_Email where All_Email.url="*$url_host$*" by All_Email.src_user All_Email.recipient All_Email.action
| rename All_Email.* as *
| convert ctime(firstTime) ctime(lastTime)
| stats sum(count) as events values(action) as actions values(src_user) as senders values(subject) as subjects min(firstTime) as firstTime max(lastTime) as lastTime by recipient
| sort - events
```

- Copies blocked or quarantined for other recipients while this one was delivered mean the gateway caught the campaign only partly. Every delivered recipient is in scope for the response.

### Step 5: Did anyone visit the host?

This is the rule's third drilldown. Run it from the delivery time to now: the rule only counts a visit in the same hour.

```spl
| tstats summariesonly=t allow_old_summaries=t fillnull_value="unknown" count values(Web.action) as action values(Web.url) as url min(_time) as firstTime max(_time) as lastTime from datamodel=Web where (Web.url_domain="$url_host$" OR Web.site="$url_host$") by Web.user Web.src Web.url_domain Web.site
| rename Web.* as *
| eval url_domain=if(url_domain!="unknown", url_domain, site)
| convert ctime(firstTime) ctime(lastTime)
| table firstTime, lastTime, user, src, url_domain, action, count, url
| sort - lastTime
```

- POST requests or paths after the landing page (`/auth`, `/submit`, `/api/...`) suggest the user entered data.
- A Web model whose `site` holds SSE app names rather than hostnames cannot show visits; use the SSE console instead.

### Step 6: If the recipient visited, check for account compromise

Set the time range from the first visit to now.

```spl
| tstats summariesonly=t allow_old_summaries=t count values(Authentication.src) as src values(Authentication.app) as app values(Authentication.signature) as signature from datamodel=Authentication where Authentication.user="$user$" by Authentication.action _time span=1h
| rename Authentication.* as *
| sort - _time
```

- New source countries or ASNs, MFA prompts the user did not start, new device registrations, or a burst of failures after the visit indicate credential theft. Check mailbox rules and OAuth consents in the mail platform.

### Step 7: Inspect the link safely

- Open the URL only in an isolated browser or a URL sandbox, never from an analyst workstation.
- A login form for Microsoft 365, Google, DocuSign or a bank on a builder subdomain is phishing. A product page, booking form or newsletter archive is not.

### Step 8: Check related HDSI AI risk on the recipient

```spl
| from datamodel:"Risk.All_Risk"
| search source="* - HDSI AI * - Rule" risk_object="$user$"
| stats sum(risk_score) as total_risk dc(source) as detections values(source) as sources by risk_object
| sort - total_risk
```

### Step 9: Make a determination

- **True Positive:** a phishing page or payload on a builder or hosting site delivered to the recipient.
- **Benign True Positive:** a legitimate external organisation sharing content built with these tools (Gamma decks, vendor apps); allow-list the host.
- **False Positive:** the link was not what the score suggested (newsletter housekeeping, internal sender spoofing that DMARC handles, a vendor page whose path contains a lure word).

---

## True Positive Indicators

- Free-mail sender (+10) and lure wording (+15) together, e.g. a Base44 page with e-signature wording (scored 50 in validation, likely phishing).
- A payload path on `vercel.app` or `netlify.app` (`.zip`, `.js`, `.vbs`, `.iso`, `.lnk`); the validation tenants saw such campaigns blocked by the gateway.
- The gateway blocked the same site for other recipients while this copy was delivered.
- The recipient visited the host shortly after delivery, especially with POST requests.
- The page asks for corporate credentials or MFA codes.
- Authentication anomalies for the recipient after the visit.

---

## False Positive Scenarios

Evidence from read-only tests on 4 production ES tenants (2026-10-09). Tenant A (Email `url` from the gateway message log) produced 8 recipients in a 7-day test; Tenants B and C emit nothing (no Email data, or `url` not mapped); Tenant D emitted nothing because its delivered builder links did not qualify.

| Scenario | Likelihood | Mitigation |
|---|---|---|
| Gamma documents, newsletters and reports from partners or agencies (3 of 8 Tenant A recipients, score 25) | High | Add recurring hosts to `..._allowed_hosts`, or raise `..._min_score` to 35 |
| A small vendor's Lovable-built CRM sends a `/contract/<id>` page through Amazon SES and the recipient opens it (scored 45 on Tenant A) | Medium | `..._allowed_hosts` for the vendor's host |
| Tracking, unsubscribe and booking endpoints on vendors' `*.lovable.app` apps sent through ESPs | Medium | The -15 bulk/ESP adjustment and `..._benign_link_regex` handle most; allow-list recurring hosts |
| Gateway discards used for routine graymail (Proofpoint `deleted`: about 190,000 URL-bearing events a day on Tenant A) | High if `..._discard_actions` is enabled | Ships off. Enable only if the gateway discards nothing but malicious mail |
| Phish sent through an ESP with no other indicator scores 10 and is not emitted | Low (missed TP) | Lower `..._min_score` to 10 or trim `..._bulk_sender_regex` if ESP-borne phish is a concern |

### Known blind spots

- Gateways that log only rewritten links (`urldefense.com`, Safe Links) hide the builder host.
- Links inside attachments (PDF, HTML, QR codes) are not in `Email.url`.
- Spoofed internal senders are excluded (DMARC and gateway spoofing controls cover them).
- A click in a later hour adds nothing; use Step 5 over a longer range.
- If internal-domain inference times out (subsearch limit) on a tenant that relies on it alone, the rule emits nothing without a warning. Pin the domains in `..._internal_domains`.

## Response Actions

### If confirmed True Positive

1. **Contain:** purge the message from every recipient mailbox found in Step 4 (gateway retraction or mail-platform search and purge). Block the host (and the sender address or domain) at the email gateway, web proxy and DNS-security layer.
2. **Credential reset:** for every recipient who visited the host (Step 5), reset the password, revoke sessions and refresh tokens, review MFA methods, OAuth consents and mailbox rules.
3. **Notify:** the affected users and their managers; warn the wider organisation if the lure is generic.
4. **Investigate:** check endpoints of users who downloaded a payload for execution (process and file detections). Report the page to the platform's abuse team (Lovable, Vercel, Netlify, Gamma and similar have abuse channels).
5. **Document:** record the campaign host, senders, recipients, clicks and actions taken.

### If Benign True Positive

1. Add the known-good host to `hdsi_ai_generated_phishing_indicators_allowed_hosts` (quoted, wildcards allowed), e.g. `"status-page.vercel.app","*.example-brand.framer.website"`.
2. For a partner that legitimately sends builder links, exclude the sender in `hdsi_ai_generated_phishing_indicators_filter`, e.g. `NOT All_Email.src_user IN ("newsletter@vendor.example")`.
3. Record the reason in the case.

## Tuning Guidance

### Reducing false positives

- `..._allowed_hosts` and `..._filter` for recurring legitimate vendors.
- Raise `..._min_score` to 35 to keep only links with a second indicator. On Tenant A that would have kept 4 of the 8 recipients in the 7-day test.
- Tune `..._lure_regex` if a frequent legitimate sender trips it.
- Override `risk_score` (at most 100) in `hdsi_ai_generated_phishing_indicators_risk_score`.

### Adjusting thresholds

Run the rule over 7 days with the time picker and review the tier mix (an upper bound, because a 7-day window correlates more loosely than the hourly schedule):

```spl
| savedsearch "Threat - HDSI AI Generated Phishing Indicators - Rule"
| stats count as recipients values(provider) as platforms by base_score, evidence
| sort - base_score
```

Raw builder-link volume by platform and action before enabling:

```spl
| tstats summariesonly=t allow_old_summaries=t count dc(All_Email.recipient) as recipients from datamodel=Email.All_Email where `hdsi_ai_generated_phishing_indicators_url_prefilter` by All_Email.action All_Email.url
| rex field=All_Email.url "^(?:[A-Za-z][A-Za-z0-9+.-]*://)?(?:[^@/?#]*@)?(?<url_host>[^/:?#\s]+)(?::\d+)?(?<url_path>/[^?#\s]*)?"
| eval url_host=replace(lower(url_host), "^www\\d*\\.", ""), url_path=lower(coalesce(url_path, "/"))
| `hdsi_ai_generated_phishing_indicators_platform`
| stats sum(count) as events sum(recipients) as recipients by ai_platform, All_Email.action
```

Check which mail domains the rule treats as internal (expect the primary mail domain, not a free-mail domain):

```spl
| makeresults
| `hdsi_ai_generated_phishing_indicators_internal_domains`
| table internal_domains
```

### Adding a builder

Add the URL pattern to `..._url_prefilter` and `..._web_prefilter`, and a `case()` branch in `..._platform`.
