# AI-033 - HDSI AI API Key Exposure In Code/DLP

> **Detection ID:** AI-033
> **Package:** `hdsi_ai_api_key_exposure_in_code_dlp` (v1.1.0, `deployment_type: global`, requires `hdsi_ai_rba_common`)
> **Search name:** `Audit - HDSI AI API Key Exposure In Code/DLP - Rule`
> **Status:** Active. Risk-only (`action.notable = 0`, `action.risk = 1`); the HDSI RBA AI aggregators decide when accumulated risk becomes a notable.
> **Risk Objects / Score:** `user` (user) and `dest` (system: the exposing host, or the repository for secret-scanner findings). Dynamic `risk_score = min(80, round(50 x risk_multiplier))` when a key from a critical provider (OpenAI, Anthropic, Gemini) is involved, otherwise `40 x risk_multiplier`. Applies to both objects. Literal fallback user 50, system 30.
> **MITRE ATT&CK:** T1552 (Unsecured Credentials), T1552.001 (Credentials In Files)
> **Data Model:** `Endpoint.Processes` (command lines), plus optional raw code-repository, DLP and secret-scanner logs
> **Schedule:** `1-59/15 * * * *` (every 15 minutes)
> **Lookback Window:** `-20m@m` to `-5m@m`
> **Suppression:** 24 h (`86400s`) on `user,dest`
> **Kill Chain Phase:** `staging` (`ai_kill_chain_phase`)
> **Last Updated:** 2026-10-09

---

## Overview

This detection finds AI provider API keys written in clear text to places Splunk can read. The main source is endpoint process command lines, for example `curl -H "Authorization: Bearer sk-proj-..."`, `setx OPENAI_API_KEY ...` or `docker run -e HF_TOKEN=hf_...`. It also scans code-repository, DLP and secret-scanner logs (for example TruffleHog output) when a tenant ingests them.

A key in a command line can be read by local administrators, the EDR console, every Splunk user who can see endpoint data, and shell history. **Treat any confirmed hit as a compromised credential that must be rotated.** A leaked key also lets anyone run AI workloads billed to the organisation, or read data the key's project can access (stored files, assistants, fine-tuning data).

The rule never copies the key into the risk event. The event carries the provider, the last 4 characters (`key_hints`, for example `OpenAI ****9f02`) and a count of distinct SHA-256 key hashes.

## Detection Logic

### Plain English

1. `tstats` over `Endpoint.Processes` keeps command lines that pass a cheap case-insensitive wildcard pre-filter (`..._process_prefilter`: `*sk-proj-*`, `*sk-ant-*`, `*hf_*`, `*api_key*`, `*deepseek*`, ...).
2. An `append` adds raw events from `..._log_sources` (GitHub, GitLab, Bitbucket, DLP, code review and secret-scanner sourcetypes) that pass `..._log_prefilter`. `..._log_identity` attributes them to a user (CIM user fields, then the commit author email) and a host or repository.
3. Placeholder identities (`unknown`, `-`, `SYSTEM`, `LOCAL SERVICE`, `NETWORK SERVICE`, machine accounts `HOST$`) are dropped as user objects; the host keeps the risk. Rows with neither a user nor a host are discarded.
4. Every candidate is tested against every enabled pattern in the shared `ai_api_key_patterns` lookup plus package patterns AKX-002 to AKX-006 (DeepSeek, Together, Cohere `CO_API_KEY`, short Fireworks, 84-character Azure OpenAI keys).
   - Prefix patterns may not start right after a letter, digit, `_` or `-`, so a prefix inside a longer random token does not fire.
   - Label-led (contextual) patterns match an exact length and count only when the same text names an AI provider.
   - `..._pattern_policy` drops AWS (AK-019) and GitHub (AK-020) patterns, needs Gemini context for Google `AIzaSy` keys, `deepseek` for AKX-002 and `fireworks` for AKX-005.
   - Placeholder keys (`xxxxxx`, `your`, `example`, `changeme`, ...) are dropped.
5. Results roll up per user and host: `exposure_count`, `distinct_keys`, `provider`, `matched_patterns`, `key_hints`, `evidence_sources`.
6. Score: 50 for a critical-provider key, 40 otherwise, x `risk_multiplier` (identity `bunit` sensitivity, x1.25 for privileged identities), capped at 80.

### Key Fields

| Field | Description | Example Value |
|---|---|---|
| `user` / `user_display` | Account that ran the command or committed the code | `jdoe@example.com` |
| `dest` / `dest_display` | Host where the key was exposed, or the repository URL for scanner findings | `WS-0142` |
| `provider` | Provider(s) of the matched key format | `OpenAI` |
| `matched_patterns` | Pattern IDs that matched | `AK-002` |
| `key_hints` | Provider plus last 4 characters per key (max 5) | `OpenAI ****9f02` |
| `distinct_keys` | Distinct SHA-256 key hashes | `1` |
| `exposure_count` | Command-line executions or log events | `3` |
| `evidence_sources` | `endpoint_command_line` or `log:<sourcetype>` | `endpoint_command_line` |
| `process_names` / `log_sourcetypes` | Processes or sourcetypes involved | `curl.exe` |
| `user_dd` / `dest_dd` | Drilldown-safe copies (backslash and quote replaced by `*`) | `EXAMPLE*jdoe` |

### Thresholds

The rule has no count threshold: one exposed key is enough.

| Parameter | Default Value | Macro | Notes |
|---|---|---|---|
| Critical-provider base | 50 | in SPL; override in `hdsi_ai_api_key_exposure_in_code_dlp_risk_score` | OpenAI, Anthropic, Gemini (pattern severity `critical`) |
| Other-provider base | 40 | same | |
| Score cap | 80 | same | Applies to both `user` and `dest` |

## Triage Steps

> **Estimated triage time:** 10-20 minutes. There is no notable for this rule. You reach it from an HDSI RBA AI aggregator notable or a risk event. The drilldowns show raw command lines, which may contain the live key: handle the output as a credential incident and do not paste it into tickets or chat.

### Step 1: Validate the risk event

```spl
| from datamodel:"Risk.All_Risk"
| search source="Audit - HDSI AI API Key Exposure In Code/DLP - Rule" risk_object IN ("$user$","$dest$")
| table _time, risk_object, risk_object_type, risk_score, risk_message
| sort - _time
```

- The risk message gives the provider, pattern IDs, distinct key count, exposure count, evidence source and key suffixes.
- Note each `key_hints` value (`<provider> ****<last4>`). It is how you match the finding to a key in the provider console without handling the key itself.

### Step 2: Review the command lines on the host

Replace `$dest_dd$` with the host from the risk event. If it contains a backslash or a quote, replace that character with `*`.

```spl
| tstats summariesonly=true allow_old_summaries=true count min(_time) as firstTime max(_time) as lastTime
    from datamodel=Endpoint.Processes
    where Processes.dest="$dest_dd$" `hdsi_ai_api_key_exposure_in_code_dlp_process_prefilter`
    by Processes.user Processes.parent_process_name Processes.process_name Processes.process
| rename Processes.* as *
| convert ctime(firstTime) ctime(lastTime)
| sort - count
```

- Find the line whose key ends in the `key_hints` suffix. Note the parent process: an interactive shell, a scheduled task, a CI agent or an installer.
- Repeated identical lines mean a script or service that leaks the key on every run.

### Step 3: Review code, DLP and secret-scanner events (log path only)

```spl
search `hdsi_ai_api_key_exposure_in_code_dlp_log_sources`
| `hdsi_ai_api_key_exposure_in_code_dlp_log_prefilter`
| `hdsi_ai_api_key_exposure_in_code_dlp_log_identity`
| search user="$user_dd$" OR dest="$dest_dd$"
| table _time, index, sourcetype, source, user, dest, _raw
| sort - _time
| head 200
```

- For secret-scanner findings, `dest` is the repository. Identify the commit, branch and whether the repository is public or shared outside the team.

### Step 4: Identify the key owner

```spl
| inputlookup identity_lookup_expanded where identity="$user$"
| table identity, first, last, email, managedBy, bunit, category, priority
```

- Is the user a developer, a data scientist, or someone outside technical roles? A privileged identity raises the score through `risk_multiplier`.
- If no user is attributed (service account or scanner finding without an author), find the host or repository owner:

```spl
| inputlookup asset_lookup_by_str where asset="$dest$"
| table asset, ip, dns, nt_host, owner, bunit, category, priority
```

### Step 5: Check for related AI risk on the same objects

```spl
| from datamodel:"Risk.All_Risk"
| search risk_object IN ("$user$","$dest$") source="*HDSI AI*"
| stats sum(risk_score) as total_risk dc(source) as detections values(source) as rules count as events by risk_object, risk_object_type
| sort - total_risk
```

- This rule belongs to the high-impact `data_exposure` vector of `Threat - HDSI RBA AI Multi-Vector Risk - Rule`. At 40 to 80 points it can reach the medium user threshold (60, two detections) with one other detection.
- API access from a non-developer host, scripted CLI use or agent activity on the same host shows where the key is being used.

### Step 6: Make a determination

- **True Positive:** a real, live AI provider key in clear text. Rotate it, whatever the intent.
- **Benign True Positive:** a key that is already revoked, or a test or CI key with no access to data. Rotate or confirm revocation, then exclude the host or process.
- **False Positive:** the matched text is not a key (a placeholder variant the rule did not know, or a vendor's public key). Tune the pattern policy or the filter.

---

## True Positive Indicators

- The key suffix matches an active key in the provider's console or the organisation's secrets inventory.
- The key belongs to a personal account (not in the corporate provider organisation).
- The command line sends the key to a provider API (`curl ... api.openai.com`) or stores it persistently (`setx`, `docker run -e`, a service definition).
- The secret-scanner finding is in a repository that is public or shared with third parties.
- `distinct_keys` greater than 1, or the same key on several hosts, shows the key is being spread.

---

## False Positive Scenarios

Evidence is from read-only live tests on 4 production ES tenants (Tenant A-D) on 2026-10-09.

| Scenario | Likelihood | Mitigation |
|---|---|---|
| Public Google API key in a desktop application's crash-reporter command line (Tenant A, several hosts) | Low (removed by the shipped AK-004 context rule) | No action unless Gemini context is present. If a vendor key still fires, exclude the process in `..._filter` |
| Key-like substrings inside longer random tokens in endpoint DLP events (Tenant A: `hf_...`, `fw_...`) | Low (removed by the leading-boundary rule) | Exclude the source in `..._log_sources` if a new token format appears |
| Revoked keys, test fixtures and CI pipelines | Medium | Rotate or confirm revocation, then exclude the host or process in `..._filter`, for example `NOT Processes.dest IN ("build-agent-*")` |
| Pre-filter candidates (Tenant A about 6.0k and Tenant C about 5.8k executions a day of unrelated `HF_`/`api_keys` lines) | None for risk; costs search time only | Exclude the noisiest benign command lines in `..._filter` if runtime matters |

In validation, all four tenants returned 0 rows over 4 hours and over 7 days after the false-positive fixes. A synthetic test fed 43 fake command lines and 2 fake log events through the production pipeline: all 30 expected detections and all 15 expected suppressions held on every tenant.

## Response Actions

### If confirmed True Positive

1. **Contain:** revoke or rotate the key in the provider console immediately. Do not wait for the investigation.
2. **Notify:** inform the key owner, their manager and the team that owns the provider account. If the key was in a public repository, follow the secret-leak process.
3. **Investigate:** review the provider's usage and audit logs for the key since the first exposure (`firstTime`). Look for unexpected models, regions, volumes or files accessed. Check who could read the command line or repository.
4. **Remediate:** purge the key from shell history, scripts, service definitions and repository history. Move the key into a secrets manager or environment-specific secret store. Restrict access to the `Endpoint` data model and this rule's drilldowns to roles that handle credential incidents.
5. **Document:** record the key suffix (never the key), the rotation time and the findings in the case management system.

### If Benign True Positive

1. Confirm the key is revoked or rotated.
2. Exclude the build host, CI runner or test process in `hdsi_ai_api_key_exposure_in_code_dlp_filter` (datamodel field names), with a comment on why.
3. If an aggregator notable was raised, close it as Benign True Positive and reference the rotation.

## Tuning Guidance

### Reducing false positives

- Prefer excluding a specific host or process in `..._filter` over disabling a pattern.
- Pin `..._log_sources` to the real indexes on large tenants (`index=*` searches every non-internal index for the listed sourcetypes). If no code or DLP logs exist, set it to `(index=main sourcetype="hdsi_ai_log_path_disabled")`. Never add sourcetype `stash`: it is the summary, risk and notable sourcetype, not Bitbucket.
- If a new key format is enabled in the shared lookup, add its literal prefix to `..._process_prefilter`, or it can never match a command line. Add label-led patterns to `..._contextual_patterns`.

### Adjusting thresholds

There is no count threshold. To see which command lines pass the pre-filter on a tenant (search-time cost, no risk), run over 24 hours:

```spl
| tstats summariesonly=true allow_old_summaries=true count dc(Processes.dest) as hosts
    from datamodel=Endpoint.Processes
    where `hdsi_ai_api_key_exposure_in_code_dlp_process_prefilter`
    by Processes.process_name
| sort - count
```

### Key tuning macros

| Macro | Ships as | Use |
|---|---|---|
| `hdsi_ai_api_key_exposure_in_code_dlp_filter` | `()` | Inline exclusions in the `Endpoint.Processes` `tstats` |
| `..._process_prefilter` | key prefix and AI keyword wildcards | Candidate filter; add new prefixes here |
| `..._log_sources` / `..._log_prefilter` / `..._log_identity` | portable defaults | Raw log path: indexes, candidate regex, user and host attribution |
| `..._extra_patterns` / `..._contextual_patterns` / `..._pattern_policy` | AKX-002..006; label-led list; context rules | Which key formats count |
| `..._customizations` / `..._risk_score` | `search *` | Post-normalisation hook; last-pipe score override (keep `risk_score` at or below 100) |

### Adding allowlist entries

This rule does not call `ai_unsanctioned_filter`: an exposed key is never "approved". Use `..._filter` for hosts or processes that are known to carry only revoked or test keys.

## Data Requirements

| Requirement | Details |
|---|---|
| Data Model | `Endpoint.Processes` (required). Raw code, DLP and secret-scanner logs (optional). The CIM `DLP` data model is not used |
| Required Fields | `Processes.process` (full command line), `Processes.dest`, `Processes.user`, `Processes.process_name`. Log path: `_raw` plus CIM user/host fields or TruffleHog `SourceMetadata.Data.*` fields |
| Sourcetype Examples | Sysmon EID 1, Windows 4688 with command-line auditing, EDR process telemetry; GitHub/GitLab/Bitbucket, DLP, TruffleHog and other secret-scanner sourcetypes |
| CIM Compliance | Full command lines in `Processes.process`. Linux and macOS coverage is limited: `export VAR=...` is a shell builtin and creates no process |
| Acceleration | `Endpoint.Processes` acceleration required (`summariesonly=true`) |
| Lookups | `ai_api_key_patterns` (common package; if missing, Splunk reports the lookup table is invalid and the rule cannot run), `identity_lookup_expanded` and `ai_department_sensitivity` (via `ai_risk_multiplier`) |

Known blind spots: keys in environment variables, `.env` files and IDE settings never appear in `Processes.process`; SaaS repository audit logs contain no code; GitHub secret-scanning and GitGuardian alerts name the secret type, not the key; the raw path uses `append` (60 s, 50,000 events per run).
