# AI-010 - Repeated Unsanctioned AI Access Burst

> **Detection ID:** AI-010
> **Package:** `hdsi_ai_repeated_unsanctioned_access_burst` (v1.1.0, `deployment_type: global`)
> **Search name:** `Network - HDSI AI Repeated Unsanctioned Access Burst - Rule`
> **Status:** Active. Risk-only (`action.notable = 0`, `action.risk = 1`). The package ships with `enable_alerting: false`.
> **Risk Score:** Dynamic, 1-50 per event, applied to both risk objects (`user`, `src`). Literal fallback: user 20, system 10.
> **MITRE ATT&CK:** T1588.007 - Obtain Capabilities: Artificial Intelligence (Resource Development)
> **Data Model:** Web (refused requests only)
> **Schedule:** `3-59/15 * * * *` (every 15 minutes)
> **Lookback Window:** `-20m@m` to `-5m@m`
> **Suppression:** 24 hours per `entity`,`provider`
> **Kill Chain Phase:** `recon` (RBA vector `shadow_usage` in the multi-vector aggregator)
> **Last Updated:** 2026-10-09

---

## Overview

This detection finds a user, or an internal host with no user, that **keeps trying to reach an AI provider after the organisation's web control has blocked it**. The web control can be a proxy, NGFW URL filtering, an SSE/CASB or an enterprise browser. A single blocked page load is policy working as intended. Ten or more refused requests spread over at least three separate minutes in a 15-minute window mean that a person or an installed tool keeps trying against the policy.

That is shadow-AI intent the policy has not yet stopped. The same person may next move to a personal device, a different provider or an evasion technique. "Unsanctioned" here means "refused by your own web control", minus any approval in `ai_sanctioned_entities`.

The score is deliberately low (5-24 observed). The rule adds context to the user's RBA profile and rarely matters on its own. It creates no notable.

## Detection Logic

### Plain English

1. `tstats` over `Web` reads **only refused requests**: `Web.action` in `..._blocked_actions` (`blocked`, `block`, `denied`, `deny`, `dropped`, `drop`, `rejected`, `reset`), plus the tenant exclusions in `..._filter`. Rows are split by user, src, `url_domain`, `site`, action, sourcetype and 1-minute `_time`. Both domain fields are read with `fillnull_value="unknown"`, so a proxy that fills only one of them works.
2. Resolve the provider: `ai_domain` is `url_domain`, or `site` when there is no `url_domain` (then treated as an SSE or App-ID application name). `ai_domains_filter` keeps enabled AI providers only.
3. Attribute. Placeholder users become null. A row with no user takes the user seen from the same `src` in the window, when exactly one user was seen. Each row is keyed by `entity`: the user, or the `src` when there is no user.
4. Aggregate per entity and provider: `blocked_attempts` (refused requests) and `blocked_minutes` (distinct minutes with a refusal). Keep the row when `blocked_attempts >= 10` and `blocked_minutes >= 3`.
5. Set risk objects. `user` when attributed. `src` when the entity used exactly one address. A host-only row whose `src` matches `..._unreliable_src` (ships as public IPv4) is dropped. This removes inbound WAF and load-balancer logs whose `src` is an internet client.
6. Remove approved users, hosts and groups with `ai_unsanctioned_filter(user,src,provider)`. The user's ES identity `bunit` is the group key.
7. Score and write risk.

### Key Fields

| Field | Description | Example Value |
|---|---|---|
| `entity` | User, or `src` when there is no user | `corp\jdoe` |
| `entity_dd` | `entity` with backslashes and double quotes replaced by `*`, used by the drilldowns | `corp*jdoe` |
| `user` / `user_display` | Attributed user, or "an unattributed user" | `corp\jdoe` |
| `src` / `src_display` | Single source address, "N hosts", or "an unknown host" | `10.1.2.50` |
| `provider` | AI provider | `OpenAI` |
| `ai_domain_sample` / `ai_domain_count` | Up to 5 refused AI hosts / their count | `chatgpt.com, ab.chatgpt.com` |
| `blocked_attempts` | Refused requests in 15 minutes | `42` |
| `blocked_minutes` | Distinct minutes with a refusal | `9` |
| `action` / `orig_sourcetype` | Refusal verbs and the sourcetypes that logged them | `blocked` / `pan:threat` |
| `bunit`, `sensitivity_level`, `risk_multiplier` | Identity context | `engineering`, `high`, `1.5` |
| `base_score`, `severity_weight`, `risk_score` | Scoring inputs and result | `20`, `1.0`, `20` |

### Risk scoring

`risk_score = max(1, min(50, round(base_score × severity_weight × risk_multiplier)))`

| Input | Value |
|---|---|
| `base_score` | 20 when a user is attributed, 10 for host-only rows |
| `severity_weight` | 0.3-1.2, from the common provider lookups |
| `risk_multiplier` | Identity `bunit` sensitivity × 1.25 for privileged identities, capped at 2.0 |

ES applies the computed `risk_score` to every risk object in the row. Observed on Tenant A: 5 to 24, mean 13.

### Thresholds

| Parameter | Default Value | Macro | Notes |
|---|---|---|---|
| Refused requests per entity and provider in 15 minutes | 10 | `hdsi_ai_repeated_unsanctioned_access_burst_min_attempts` | Raising it mostly removes short bursts |
| Distinct minutes with a refusal | 3 | `hdsi_ai_repeated_unsanctioned_access_burst_min_minutes` | One blocked page load produces many refusals in one minute; this is what makes it "repeated" |

## Triage Steps

> **Estimated triage time:** 5-10 minutes

Replace `<entity_dd>`, `<src>`, `<provider>` and `<risk_object>` with values from the risk event. Use `entity_dd` (backslashes replaced by `*`) for any user in `DOMAIN\user` form: a raw backslash inside a quoted SPL term acts as an escape and the term matches nothing.

### Step 1: Read the risk event

```spl
| from datamodel:"Risk.All_Risk"
| search source="Network - HDSI AI Repeated Unsanctioned Access Burst - Rule" risk_object="<entity_dd>"
| table _time risk_object risk_object_type risk_score risk_message
| sort - _time
```

- Note the provider, `blocked_attempts`, `blocked_minutes` and the sample hosts from the risk message.
- A repeat on several days for the same entity and provider usually means an installed app or an open tab, not a person (see Step 3).

### Step 2: Review allowed and blocked AI traffic for the entity

```spl
| tstats summariesonly=t allow_old_summaries=t fillnull_value="unknown" count from datamodel=Web where (Web.user="<entity_dd>" OR Web.src="<entity_dd>") by Web.user Web.src Web.url_domain Web.site Web.action sourcetype _time span=1m
| rename Web.* as *
| eval ai_domain=lower(coalesce(nullif(url_domain,"unknown"),nullif(site,"unknown"))), ai_input_type=if(isnull(nullif(url_domain,"unknown")),"app","host")
| `ai_domains_filter`
| stats sum(count) as requests dc(_time) as active_minutes min(_time) as firstTime max(_time) as lastTime by user src provider ai_domain action sourcetype
| convert ctime(firstTime) ctime(lastTime)
| sort provider - requests
```

- **Displacement:** allowed traffic to a *different* AI provider right after the blocks means the user found a way around the policy. That is the main true-positive pattern.
- Refusals on `ws.`, `ab.` or backend subdomains (`ws.chatgpt.com`, `ab.chatgpt.com`, `codex-cloud-backend.chatgpt.com`, `*.individual.githubcopilot.com`) in nearly every minute mean a background client, not a person.
- `sourcetype` should be your proxy, firewall, SSE or enterprise-browser feed. An inbound web-server or WAF sourcetype here is a false positive (see False Positive Scenarios).

### Step 3: Look for an installed AI client on the host

```spl
| tstats summariesonly=t allow_old_summaries=t count min(_time) as firstTime max(_time) as lastTime from datamodel=Endpoint.Processes where Processes.dest="<src>" by Processes.user Processes.dest Processes.process_name
| rename Processes.* as *
| eval process_name_lc=lower(process_name)
| `ai_process_enrich`
| where enabled=1
| convert ctime(firstTime) ctime(lastTime)
| table firstTime lastTime user dest process_name tool provider usage_type count
```

- A desktop app (ChatGPT, Claude), an IDE with a personal GitHub Copilot sign-in or a meeting-transcription agent retries constantly when blocked. Remove the tool or its sign-in.
- `Processes.dest` is usually a hostname. If `src` is an IP address, resolve it to the host first (DHCP, asset list or EDR).

### Step 4: Check DNS from the source for other AI providers

```spl
| tstats summariesonly=t allow_old_summaries=t count from datamodel=Network_Resolution where DNS.src="<src>" by DNS.query
| rename DNS.query as query
| eval ai_domain=lower(query), ai_input_type="dns"
| `ai_domains_filter`
| stats sum(count) as queries dc(query) as distinct_names values(query) as names by provider
| sort - queries
```

- DNS is the most portable AI-usage signal across tenants. Resolutions for providers that the proxy did not block suggest the user moved to them.

### Step 5: Identify the user and check approvals

```spl
| inputlookup identity_lookup_expanded
| search identity="<user>"
| table identity first last email managedBy bunit category priority
```

```spl
| inputlookup ai_sanctioned_entities
| search allow_key="<user>|*" OR allow_key="<src>|*" OR allow_key="*|<provider>"
| table entity_type entity provider scope expires owner reason enabled allow_key
```

- Use the bare account name for `<user>` if the `DOMAIN\user` form finds no identity. On the NGFW validation tenant most `DOMAIN\user` values did not match an ES identity.
- An expired or disabled allow-list entry explains why an approved user suddenly appears.

### Step 6: Check related AI risk

```spl
| from datamodel:"Risk.All_Risk"
| search risk_object="<entity_dd>" source="* - HDSI AI * - Rule"
| stats sum(risk_score) as total_risk dc(source) as detections values(source) as sources min(_time) as first_seen max(_time) as last_seen by risk_object risk_object_type
| convert ctime(first_seen) ctime(last_seen)
```

- `Network - HDSI AI Access Via VPN/Proxy Evasion - Rule` or `Network - HDSI AI Access From Unmanaged Device - Rule` (incubating, not released) after a burst is the escalation pattern this rule exists to catch.
- Upload or DLP detections for the same user turn shadow use into data exposure.

### Step 7: Make a determination

- **True Positive:** a person persisted against the block and then reached AI another way, or sent data to an AI service.
- **Benign True Positive:** a blocked desktop app, extension or open tab retrying; or an approved user whose allow-list entry is missing or expired.
- **False Positive:** inbound server logs, or a refusal verb that does not mean "blocked by policy".

---

## True Positive Indicators

- Refusals come from page loads (`chatgpt.com`, `claude.ai`, `gemini.google.com`) across several separate minutes, not from one background endpoint every minute.
- After the blocks, allowed traffic or DNS resolutions appear for another AI provider, a VPN or proxy service, or an unmanaged device of the same user.
- The user is in a sensitive `bunit` or is a privileged identity.
- Upload, DLP or copy-paste AI detections fire for the same user on the same day.

---

## False Positive Scenarios

| Scenario | Likelihood | Mitigation |
|---|---|---|
| Blocked desktop or mobile app, IDE with a personal Copilot sign-in, or an open browser tab retrying constantly (most Tenant A windows had refusals in 11-15 of 15 minutes) | High | Remove the client or sign-in; or exclude the host in `..._filter` or add an `ai_sanctioned_entities` entry. The 24 h suppression already limits it to one event a day |
| Host-only rows from networks without user mapping (about 135 of 190 daily events on Tenant A) | High where User-ID is missing | Put guest, BYOD, NAT and VPN pools in `..._unreliable_src` |
| Inbound web servers behind a load balancer or reverse proxy (`src` is the balancer's private address) | Low, latent | Exclude those sourcetypes or balancer addresses in `..._filter`, e.g. `NOT sourcetype IN ("iis","access_combined","aws:elb:accesslogs")` |
| Approved user without an allow-list entry, or with an expired one | Medium | Add or renew the `ai_sanctioned_entities` row |
| An explicit proxy reporting itself as `src`, collapsing many users into one host-only entity | Low | Exclude the proxy address in `..._filter` or fix user logging on the proxy |

## Response Actions

### If confirmed True Positive

1. **Contain:** Confirm the block also covers the provider the user moved to. Block VPN or proxy services the user reached after the burst.
2. **Notify:** Inform the user's manager and remind the user of the AI acceptable-use policy. Point them to the approved AI service, if there is one.
3. **Investigate:** Check upload, DLP and copy-paste detections for the same user over the last 7 days to see whether data left.
4. **Remediate:** Remove unapproved AI clients from the endpoint. Review whether the business need justifies an approved tool.
5. **Document:** Record the provider, the evasion path (if any) and the outcome.

### If Benign True Positive

1. Remove or reconfigure the retrying client, or add an `ai_sanctioned_entities` row with an expiry date:
   ```
   entity_type,entity,provider,scope,expires,owner,reason,enabled,allow_key
   user,corp\jdoe,OpenAI,provider,2027-03-31,security,approved research use,1,corp\jdoe|openai
   ```
   `allow_key` is lowercase. Group entries use the user's ES identity `bunit` (`<bunit>|<provider>`).
2. Close the finding as Benign True Positive.

## Tuning Guidance

### Reducing false positives

- Extend `..._unreliable_src` with guest, BYOD, NAT and VPN pools (`OR cidrmatch("10.200.0.0/16",src)`).
- Add the vendor's refusal verb to `..._blocked_actions` if your TA does not map to CIM `blocked`. Do not add `isolate`, `warn` or `reported`.
- Check `orig_sourcetype` on the first results: it should list only proxy, firewall, SSE or enterprise-browser sourcetypes.
- Normalise users in the TA, or add the `DOMAIN\user` form as an identity key, so one person has one risk object across detections.

### Adjusting thresholds

Volume after the 24 h suppression depends on the number of distinct entities, not on the threshold. On Tenant A, 10/3 and 20/3 gave 1,158 and 1,045 qualifying windows a day, both from about 185 entities. Run over `-24h@h` to `@h`:

```spl
| tstats summariesonly=t allow_old_summaries=t fillnull_value="unknown" count from datamodel=Web where `hdsi_ai_repeated_unsanctioned_access_burst_blocked_actions` by Web.user Web.src Web.url_domain Web.site _time span=1m
| rename Web.* as *
| eval ai_domain=lower(coalesce(nullif(url_domain,"unknown"),nullif(site,"unknown"))), ai_input_type=if(isnull(nullif(url_domain,"unknown")),"app","host")
| `ai_domains_filter`
| eval entity=coalesce(nullif(user,"unknown"), src)
| bin _time span=15m as window
| stats sum(count) as attempts dc(_time) as minutes by entity provider window
| stats count as windows dc(entity) as entities count(eval(attempts>=10 AND minutes>=3)) as at_10_3 count(eval(attempts>=20 AND minutes>=3)) as at_20_3 count(eval(attempts>=10 AND minutes>=5)) as at_10_5 p90(attempts) as p90_attempts p99(attempts) as p99_attempts
```

Expect roughly one risk event per qualifying entity and provider per day.

### Tuning macros

| Macro | Ships as | Purpose |
|---|---|---|
| `hdsi_ai_repeated_unsanctioned_access_burst_filter` | `()` | Exclusions inside the `tstats` where clause |
| `..._blocked_actions` | `Web.action IN ("blocked","block","denied","deny","dropped","drop","rejected","reset")` | Values that mean the control refused the request |
| `..._min_attempts` / `..._min_minutes` | `10` / `3` | Thresholds |
| `..._unreliable_src` | public IPv4 | Host-only rows from these addresses are dropped. `false()` keeps everything |
| `..._customizations` / `..._risk_score` | `search *` | Post-scoring hook / last-pipe score override (1-100) |
