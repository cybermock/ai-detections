# AI-027 - Personal Email To AI Service Upload Correlation

> **Detection ID:** AI-027 (package `hdsi_ai_personal_email_to_ai_service_upload_correlation`, `detection_id=hdsi_ai_personal_email_to_ai_service_upload_correlation`)
> **Search name:** `Network - HDSI AI Personal Email To AI Service Upload Correlation - Rule`
> **Status:** Active, version 1.1.0, `deployment_type: global`, ships with `enable_alerting: false`
> **Data dependency:** needs user-egress `Web` data (forward proxy, SWG or SSE) with `user` **and** `bytes_out`. It returned 0 rows on all 4 validation tenants because none had such data with AI uploads. Confirm the data before enabling.
> **Output:** Risk only (`action.notable = 0`). Notables come from the HDSI RBA AI aggregators.
> **Risk Score:** static, user 35 + system 15 (`src` only when known). No computed `risk_score` unless the risk-score macro sets one
> **MITRE ATT&CK:** T1567 - Exfiltration Over Web Service (Exfiltration)
> **Data Model:** `Web`
> **Schedule:** `5 * * * *` (hourly at minute 5)
> **Lookback Window:** `-65m@m` to `-5m@m`
> **Suppression:** `user,src` for 86400s (one risk event per user and host per day)
> **Kill Chain Phase:** `exfiltration`
> **Last Updated:** 2026-10-09

---

## Overview

This detection finds a user who uploads attachment-sized data to personal (consumer) webmail and then, in the same hourly window, uploads file-sized data to an AI web service. Mailing work files to a personal Gmail, Yahoo or Outlook.com account and then pushing them into ChatGPT, Claude or Gemini moves corporate data through two uncontrolled hops, and the second hop usually escapes DLP.

The correlation is a staging pattern, not proof of a leak, so it carries a modest static score (35 on the user, 15 on the host). It is one of the upload signals that `Threat - HDSI RBA AI Data Collection Kill Chain - Rule` pairs with an earlier collection signal. The rule never creates a notable on its own.

## Detection Logic

### Plain English

1. **One `tstats`** over `Web` in 5-minute buckets by `user`, `src`, `url_domain` and `site`, restricted inline to rows with a user, `bytes_out>0` and a method other than `GET`/`HEAD`/`OPTIONS`, minus `hdsi_ai_personal_email_to_ai_service_upload_correlation_filter`. Placeholder users (`unknown`, `-`, empty, `anonymous`) are dropped.
2. **Personal-email half.** `dest_name` is `url_domain` without a leading `www.`, or the SSE app name in `site`. It is matched exactly against `..._personal_email_names` (consumer webmail hosts such as `mail.google.com`, `outlook.live.com`, `mail.yahoo.com`, and SSE app names such as `google gmail`, `yahoo mail`, `microsoft live outlook`).
3. **Corporate-platform guard.** A personal-email destination reached by 25 or more users in the window is the company's own mail platform (for example Gmail at a Google Workspace tenant) and is ignored.
4. **AI half.** Only for users with personal-email traffic. Other destinations go through `ai_domains_filter` (hostnames as `host`, SSE app names as `app`). Only `usage_type` `web` counts. `ai_unsanctioned_filter(user,src,provider)` removes approved pairs per provider before aggregation.
5. **Thresholds per 5-minute bucket.** Personal email at least 5 MB, AI at least 1 MB.
6. **Order.** Only AI buckets at or after the first qualifying email bucket count.
7. **Output** one row per `user` and `src`. A `src` of `unknown` is nulled, so no system risk is created for it.
8. `..._customizations`, then `..._risk_score` as the last pipe.

| Field | Description | Example Value |

## Triage Steps

> **Estimated triage time:** 15-20 minutes. Replace `$user$` and `$src$` with the values from the risk event. For a `DOMAIN\user` value, replace the backslash with `*` inside quoted search terms. Set the time picker to the risk event hour, widened by an hour on each side.

### Step 1: Validate the risk event

```spl
| from datamodel:"Risk.All_Risk"
| search source="Network - HDSI AI Personal Email To AI Service Upload Correlation - Rule" (risk_object="$user$" OR risk_object="$src$")
| table _time, risk_object, risk_object_type, risk_score, risk_message, personal_email_list, personal_mb, provider_list, ai_mb, gap_minutes
| sort - _time
```

- How much went to personal webmail and how much to AI, and how close together?
- A small `gap_minutes` with similar volumes on both halves is the strongest form of the pattern.

### Step 2: Identify the user

```spl
| inputlookup identity_lookup_expanded
| search identity="$user$"
| table identity, first, last, email, managedBy, category, priority, bunit
```

- Does the user handle sensitive data? Is the user leaving the organisation, on notice, or under HR review?

### Step 3: Rebuild the upload timeline

```spl
| tstats summariesonly=t allow_old_summaries=t fillnull_value="unknown" sum(Web.bytes_out) as bytes_out from datamodel=Web where Web.user="$user$" Web.bytes_out>0 NOT Web.http_method IN ("GET","HEAD","OPTIONS") by _time span=5m Web.src Web.url_domain Web.site
| rename Web.* as *
| eval dest_name=replace(lower(trim(coalesce(nullif(url_domain,"unknown"),nullif(site,"unknown"),""))),"^www\d*\.",""), channel=if(in(dest_name,`hdsi_ai_personal_email_to_ai_service_upload_correlation_personal_email_names`),"personal_email","other")
| appendpipe [| where channel="other" | eval ai_domain=dest_name, ai_input_type=if(url_domain="unknown","app","host") | `ai_domains_filter` | eval channel="ai"]
| where channel IN ("personal_email","ai")
| eval mb_out=round(bytes_out/1048576,2)
| table _time, src, channel, dest_name, provider, usage_type, mb_out
| sort _time
```

- Personal-email buckets should come first, followed by AI buckets.
- Repeated pairs across the hour suggest several files moved one after another.

The rule's "View web uploads" drilldown adds methods, URLs and user agents per destination:

```spl
| tstats summariesonly=t allow_old_summaries=t fillnull_value="unknown" count sum(Web.bytes_out) as bytes_out sum(Web.bytes_in) as bytes_in values(Web.http_method) as http_method values(Web.url) as url values(Web.http_user_agent) as http_user_agent min(_time) as firstTime max(_time) as lastTime from datamodel=Web where Web.user="$user$" (Web.url_domain=* OR Web.site=*) by Web.user Web.src Web.url_domain Web.site
| rename Web.* as *
| eval url_domain=coalesce(nullif(url_domain,"unknown"),site), mb_out=round(bytes_out/1048576,2), mb_in=round(bytes_in/1048576,2)
| convert ctime(firstTime) ctime(lastTime)
| table firstTime, lastTime, user, src, url_domain, count, mb_out, mb_in, http_method, http_user_agent, url
| sort - mb_out
```

- On SSE connection logs (`netskope:connection` and similar), `bytes_out` is per connection and reported when it closes. A long webmail session can cross 5 MB without an attachment. Check the SSE's own upload or activity events for an attachment name if available.

### Step 4: Check what was accessed before the upload

```spl
| from datamodel:"Risk.All_Risk"
| search (risk_object="$user$" OR risk_object="$src$") source="* - HDSI AI * - Rule"
| stats sum(risk_score) as total_risk dc(source) as detections values(source) as sources values(ai_kill_chain_phase) as phases by risk_object, risk_object_type
| sort - total_risk
```

```spl
`notable`
| search search_name="Threat - HDSI RBA AI *" ("$user$" OR "$src$")
| table _time, search_name, rule_title, urgency, status_label, owner
```

- A collection signal earlier the same day (file-access spike, clipboard copy into AI, page-reader extension) plus this upload raises `Threat - HDSI RBA AI Data Collection Kill Chain - Rule` (high).
- Check DLP, file-share and email-gateway logs for the files the user touched or forwarded before the webmail upload.

### Step 5: Determine sanctioned status

```spl
| inputlookup ai_sanctioned_entities
| where enabled=1
| table entity_type, entity, provider, scope, expires, owner, reason, allow_key
| sort entity_type, entity
```

- An approved AI provider for this user removes only that provider from the AI half. Personal webmail cannot be sanctioned through this lookup.

### Step 6: Make a determination

- **True Positive:** work data mailed to a personal account and then uploaded to an unapproved AI service, confirmed by file names, DLP or the user's own account.
- **Benign True Positive:** the "personal" destination is the corporate platform below the 25-user guard (small Google Workspace tenant), or the AI upload is an approved enterprise service. Tune the macro or approve the provider.
- **False Positive:** a long-lived SSE webmail connection crossing 5 MB without an attachment, with a small, unrelated AI upload in the same hour. Raise `..._min_email_bytes` (see Tuning).

---

## True Positive Indicators

- Similar volume on both halves within a few minutes (the same file moved twice).
- Upload to a personal account of a user who is leaving or under review.
- A collection signal (file-access spike, clipboard, page reader) before the webmail upload.
- The AI destination is a consumer service and not on the approved list.
- Repeated pairs across several hours or days.

---

## False Positive Scenarios

| Scenario | Likelihood | Mitigation |
|---|---|---|
| Gmail is the corporate platform (Google Workspace) but the tenant is small enough to stay under 25 users an hour | Medium at small Workspace tenants | Remove `mail.google.com`, `google gmail` and `gmail` from `..._personal_email_names` |
| SSE connection-level `bytes_out` makes long webmail sessions cross 5 MB without an attachment | Medium on connection-level SSE data | Raise `..._min_email_bytes` to the p90 of the busiest webmail destination (Tuning) |
| Sanctioned enterprise AI with heavy upload volume. On Tenant C the SSE app `microsoft copilot studio` carried about 55-67 MB a day per user of background connection traffic; the common package now ships that app name disabled (opt-in, provider `Microsoft 365 Copilot`) | Low | Keep it disabled, or approve the provider in `ai_sanctioned_entities` if you enable it |
| Personal mail read with large inline content, followed by an ordinary AI chat upload | Low | The 1 MB AI threshold already removes typed prompts; raise it if needed |

---

## Response Actions

### If confirmed True Positive

1. **Contain:** block personal webmail uploads and the unapproved AI service for the user in the proxy or SSE policy. If departure-related, involve HR and legal before contacting the user.
2. **Notify:** the user's manager, the data owner, and privacy or legal if regulated data is involved.
3. **Investigate:** identify the files (DLP, SSE activity events, endpoint file access, email gateway). Ask the AI provider admin console (if enterprise) for retention and deletion options.
4. **Remediate:** request deletion from the personal mailbox and the AI service, and review DLP coverage for personal webmail and AI uploads.
5. **Document:** record the data involved, both destinations and the actions taken in the case.

### If Benign True Positive

1. Approve the AI provider for the user or group in `ai_sanctioned_entities`, or remove the corporate mail platform from `..._personal_email_names`.
2. Record the business justification.
3. Close any related aggregator notable as benign.

## Tuning Guidance

### Reducing false positives

| Macro | Ships as | Use |
|---|---|---|
| `hdsi_ai_personal_email_to_ai_service_upload_correlation_filter` | `()` | Inline `Web.*` exclusions, e.g. `NOT Web.src IN ("10.1.2.0/24")` for VDI or explicit-proxy egress |
| `..._personal_email_names` | Consumer webmail hosts and SSE app names | Remove Gmail where Workspace is corporate. Add ISP or regional webmail seen in your data |
| `..._corporate_mail_users` | `25` | Users per window above which a destination is the corporate platform |
| `..._ai_usage_types` | `"web"` | Add `"api"` for direct API uploads from endpoints |
| `..._customizations` / `..._risk_score` | `search *` | Post-correlation hook / last pipe (a numeric `risk_score` here overrides both static scores) |

### Adjusting thresholds

Measure upload sizes per 5-minute bucket for personal webmail over 7 days:

```spl
| tstats summariesonly=t allow_old_summaries=t fillnull_value="unknown" sum(Web.bytes_out) as bytes_out from datamodel=Web where Web.user=* Web.bytes_out>0 NOT Web.http_method IN ("GET","HEAD","OPTIONS") by _time span=5m Web.user Web.url_domain Web.site
| rename Web.* as *
| eval dest_name=replace(lower(coalesce(nullif(url_domain,"unknown"),site)),"^www\d*\.","")
| where in(dest_name, `hdsi_ai_personal_email_to_ai_service_upload_correlation_personal_email_names`)
| eval mb=bytes_out/1048576
| stats count as buckets dc(user) as users p50(mb) as p50_mb p90(mb) as p90_mb p99(mb) as p99_mb by dest_name
```

Keep `..._min_email_bytes` at or above the p90 of the busiest consumer webmail destination. On Tenant C (connection-level SSE), p90 was about 2-10 MB depending on the destination, so the shipped 5 MB is below the p90 for the busiest ones: raise it there. Replace the `where in(...)` with `ai_domains_filter` to size `..._min_ai_bytes`.

### Adding allowlist entries

```
entity_type,entity,provider,scope,expires,owner,reason,enabled,allow_key
user,jdoe@example.com,OpenAI,provider,2027-03-31,security,approved_chatgpt_enterprise,1,jdoe@example.com|openai
group,*,Microsoft 365 Copilot,global,2099-12-31,security,m365_copilot_licensed,1,*|microsoft 365 copilot
```

Use the provider name exactly as `ai_domains_filter` resolves it (see the `provider_list` field of the risk event).

## Validation (2026-10-09)

Read-only live tests on 4 production ES tenants. The search and both drilldowns parse on all four; no FATAL or ERROR.

| Tenant | Web data | Rows 4h / 24h / 7d | Notes |
|---|---|---|---|
| A | PAN-OS URL logs: `bytes_out` 0% | 0 / 0 / 0 | No data path. `mail.google.com` is the corporate platform there (about 43,000 users a day) |
| B | Mostly inbound load-balancer and WAF logs plus a small proxy feed | 0 / 0 / 0 (7d stopped at the test limit) | No AI web uploads in the proxy feed |
| C | SSE connection logs: app names in `site`, user and `bytes_out` populated | 0 / 0 / 0 | Users crossing 5 MB a bucket to personal webmail are common (57 users in 7 days at the rule's grain), but none had AI web uploads in the same window |
| D | Inbound IIS only | 0 / 0 / 0 | No data path |

A synthetic test fed through the full pipeline on Tenant C fired for a 6 MB Gmail upload followed 10 minutes later by 2 MB to ChatGPT, and did not fire when the AI upload came first or stayed under 1 MB. Expected volume: 0 a day on the validation tenants; a few users a day at most on a tenant with a byte-accurate user proxy and active consumer AI use.
