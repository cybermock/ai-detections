# AI-007 - High Volume Upload To AI Service

> **Detection ID:** AI-007
> **Package:** `hdsi_ai_high_volume_upload_to_ai_service` (v1.1.0, deployment type `global`, ships `enable_alerting: false`)
> **Search name:** `Network - HDSI AI High Volume Upload To AI Service - Rule`
> **Status:** Active (risk-only: `action.risk = 1`, `action.notable = 0`)
> **Risk Score:** dynamic, applied to `src` (system) and, when attributed, `user`: tier base 20 / 30 / 45 / 60 x `risk_multiplier` (1.0 to 2.0) x provider `severity_weight` (0.3 to 1.2), capped at 80. Literal `_risk` fallback 20 per object
> **MITRE ATT&CK:** T1567 - Exfiltration Over Web Service (Exfiltration)
> **Data Model:** `Network_Traffic` (firewall App-ID with byte counts) OR `Web` (proxy/SSE with byte counts)
> **Schedule:** `7 * * * *` (hourly at minute 7)
> **Lookback Window:** `-65m@m` to `-5m@m`
> **Suppression:** 4 hours (`14400s`) on `src`
> **Kill Chain Phase:** `exfiltration` (multi-vector aggregator vector: `data_exposure`, high impact)
> **Last Updated:** 2026-10-09

---

## Overview

This detection finds a host, and the user where the log source knows it, that uploads a large volume of data to an AI service in one hour. Examples are ChatGPT, Gemini, Claude, Perplexity, DeepSeek, AI APIs and Hugging Face. A large upload to a chat or API service usually means files, documents or bulk text are being pasted or attached, which is a direct data-exposure path outside the organisation.

Volume is measured from `bytes_out` in two places: firewall sessions that carry an AI application ID (PAN-OS App-ID or equivalent, `Network_Traffic.app`), and proxy or SSE logs that carry request bytes (`Web`). Four volume tiers (50 / 100 / 500 / 2,000 MB per hour by default) set the base score. The rule writes risk on `src` and on the top uploading `user` when that user alone crossed the low tier. It creates no notable. The AI risk aggregators (`Threat - HDSI RBA AI ... - Rule`) turn accumulated risk into notables; this rule is listed as an upload/exfiltration step in the data collection kill-chain aggregator.

Typical actors: an employee pasting or attaching internal documents, source code or exports into a consumer AI service; an integration server or build host calling an AI API in bulk (often legitimate and allow-listed); occasionally a compromised host using an AI API as an exfiltration channel.

## Detection Logic

### Plain English

1. **Firewall branch:** `tstats` over `Network_Traffic` sums `bytes_out`, `bytes_in` and sessions by `src`, `user` and `app`. It keeps only candidate AI App-IDs (`hdsi_ai_high_volume_upload_to_ai_service_app_ids`), `bytes_out>0`, not `blocked`, and the tenant `_filter`. `ai_domains_filter` resolves the App-ID through `ai_provider_apps`.
2. **Web branch (`append maxtime=240`):** `tstats` over `Web` sums bytes by `src`, `user`, `url_domain` and `site` (`fillnull_value="unknown"`, so proxies that fill only one of the two are kept), not `blocked`, plus the tenant `_web_filter`. `ai_domain` is `url_domain`, or `site` when the SSE product logs only an app name such as "ChatGPT". Providers are resolved inside the subsearch.
3. Keep only `usage_type` web, api, cli and model registry. IDE coding assistants (`ide`) and the provider `Microsoft 365 Copilot` are excluded by default.
4. Null placeholder users (`unknown`, `-`, empty), drop rows without a usable `src`, and remove approved entities with `ai_unsanctioned_filter(user,src,provider)`.
5. Aggregate to **one row per `src`**: bytes are summed per evidence type (firewall or proxy) across all users, and the larger evidence total is used, so a flow seen by both the firewall and the proxy is counted once.
6. Keep `src` rows at or above `_low_mb` (50 MB) in the hour and assign the tier.
7. **User attribution:** the attributed user with the most upload on that `src` becomes `user` only if that user alone uploaded at least `_low_mb`. If that user has more than `_max_user_sessions` (1,000) sessions in the hour, the login is named in `user_display` but gets no risk (shared terminal, VDI or proxy server mapped to one User-ID).
8. Score: `risk_score = min(80, round(base x risk_multiplier x severity_weight))`, applied to both risk objects.

### Key Fields

| Field | Description | Example Value |

### Thresholds

| Parameter | Default | Macro | Notes |
|---|---|---|---|
| Tier low | 50 MB/hour | `hdsi_ai_high_volume_upload_to_ai_service_low_mb` | Base 20. Also the minimum a single user must upload to be scored |
| Tier medium | 100 MB/hour | `hdsi_ai_high_volume_upload_to_ai_service_medium_mb` | Base 30 |
| Tier high | 500 MB/hour | `hdsi_ai_high_volume_upload_to_ai_service_high_mb` | Base 45 |
| Tier critical | 2,000 MB/hour | `hdsi_ai_high_volume_upload_to_ai_service_critical_mb` | Base 60 |

## Triage Steps

> **Estimated triage time:** 15-25 minutes. Replace `$src$` and `$user$` with the values from the risk event. Run the risk queries with the time picker set to the last 24 hours (or 7 days for history).

### Step 1: Read the risk event

```spl
| from datamodel:"Risk.All_Risk"
| search source="Network - HDSI AI High Volume Upload To AI Service - Rule" (risk_object="$src$" OR risk_object="$user$")
| table _time risk_object risk_object_type risk_score risk_message
| sort - _time
```

- The `risk_message` gives the MB, provider(s), tier, evidence and `user_display`.
- If `user_display` says "not scored: N sessions under one login", treat the `src` as a shared server, not as that person.
- Several events for the same `src` (one per 4 hours at most) mean sustained upload, not a single burst.

### Step 2: Identify the host and the user

```spl
| inputlookup asset_lookup_by_str
| search ip="$src$" OR dns="$src$" OR nt_host="$src$"
| table ip dns nt_host owner bunit category priority
```

```spl
| inputlookup identity_lookup_expanded
| search identity="$user$"
| table identity first last email managedBy bunit category priority
```

- Is the `src` a workstation, a VDI or terminal server, a NAT pool or an integration/build server? Shared infrastructure is the most common benign cause.
- `bunit` drives the `risk_multiplier`. A privileged or critical identity raises it by 1.25.

### Step 3: Break down the firewall upload volume (App-ID evidence)

```spl
| tstats summariesonly=t allow_old_summaries=t count sum(All_Traffic.bytes_out) as bytes_out sum(All_Traffic.bytes_in) as bytes_in values(All_Traffic.dest) as dest
    from datamodel=Network_Traffic
    where All_Traffic.src="$src$" All_Traffic.bytes_out>0 earliest=-24h
    by _time span=1h All_Traffic.user All_Traffic.app
| rename All_Traffic.* as *
| eval mb_out=round(bytes_out/1048576,1), mb_in=round(bytes_in/1048576,1)
| where mb_out>=1
| sort - mb_out
| table _time user app count mb_out mb_in dest
```

- Which AI App-IDs carry the volume, in which hours, and under which users?
- Upload far larger than download (`mb_out` >> `mb_in`) fits file or document upload. Roughly symmetric streams fit voice or screen-sharing modes.
- Many unrelated applications on the same `src` in the same hours point to a shared host or NAT address.

### Step 4: Break down the proxy/SSE upload volume (Web evidence)

```spl
| tstats summariesonly=t allow_old_summaries=t fillnull_value="unknown" count sum(Web.bytes_out) as bytes_out sum(Web.bytes_in) as bytes_in values(Web.http_method) as http_method values(Web.url) as url
    from datamodel=Web
    where Web.src="$src$" (Web.url_domain=* OR Web.site=*) Web.bytes_out>0 earliest=-24h
    by Web.user Web.url_domain Web.site
| rename Web.* as *
| eval url_domain=coalesce(nullif(url_domain,"unknown"),site), mb_out=round(bytes_out/1048576,1), mb_in=round(bytes_in/1048576,1)
| where mb_out>=1
| sort - mb_out
| table user url_domain count mb_out mb_in http_method url
```

- `url_domain` is the hostname, or the SSE app name (for example "ChatGPT") when the product logs no domain.
- Look for `POST`/`PUT` to file-upload or attachment endpoints, and for API hosts (`api.openai.com`, `generativelanguage.googleapis.com`) from a workstation.
- Some SSE products log a long connection once, with all its bytes, when it closes. A single row with tens of MB and almost no `mb_in` can be a background client connection rather than a user upload (see False Positive Scenarios).

### Step 5: Check whether the host is shared

```spl
| tstats summariesonly=t allow_old_summaries=t count dc(All_Traffic.app) as apps sum(All_Traffic.bytes_out) as bytes_out
    from datamodel=Network_Traffic
    where All_Traffic.src="$src$" earliest=-4h
    by All_Traffic.user
| rename All_Traffic.* as *
| eval mb_out=round(bytes_out/1048576,1)
| sort - count
```

- A normal user has at most a few dozen AI sessions an hour (24-hour p99.9 on the largest validation tenant: 36). Thousands of sessions under one login, or many users on one `src`, indicate a terminal, VDI or proxy server.

### Step 6: Correlate with other HDSI AI risk on the same entities

```spl
| from datamodel:"Risk.All_Risk"
| search (risk_object="$user$" OR risk_object="$src$") source="* - HDSI AI * - Rule"
| stats sum(risk_score) as total_risk dc(source) as detections values(source) as sources values(ai_kill_chain_phase) as phases by risk_object risk_object_type
| sort - total_risk
```

- An upload preceded by a collection detection (copy/paste correlation, data access spike, browser extension activity) within 4 hours is what `Threat - HDSI RBA AI Data Collection Kill Chain - Rule` raises.
- The user aggregators raise a medium notable at 60 to below 90 in 24 hours (with 2+ detections) and a high notable at 90 or more (`medium_risk_threshold`/`high_risk_threshold` in `ai_detection_config`).

### Step 7: Check sanctioned status

```spl
| inputlookup ai_sanctioned_entities
| where enabled=1 AND (lower(entity)=lower("$user$") OR entity="$src$" OR entity="*" OR entity_type="group")
| table entity_type entity provider scope expires owner reason allow_key
```

- A sanctioned `user|provider`, `src|provider`, `bunit|provider` or `*|provider` row suppresses the rule. If the entity should be covered, check the row is enabled, unexpired and that `allow_key` is lowercase `<entity>|<provider>`.

### Step 8: Make a determination

- **True Positive:** a person uploaded a large volume of internal data to an unsanctioned AI service.
- **Benign True Positive:** the volume is real but approved (integration server, sanctioned research group, approved provider). Allow-list it.
- **False Positive:** the volume is not a user upload (shared egress, streaming/voice overhead, background SSE connection). Tune it.

## True Positive Indicators

- One attributed user, on their own workstation, with `user_out_mb` well above the low tier and few sessions (tens, not thousands).
- `mb_out` far exceeds `mb_in`, concentrated in one or two hours, to a chat or file-capable endpoint of a consumer AI service.
- The provider is not sanctioned for the user's `bunit`, or the user is in a sensitive `bunit` (`risk_multiplier` above 1.0).
- Other HDSI AI risk on the same user: collection detections shortly before, DLP or personal-email correlations, first-seen provider.
- Repeat events on the same `src` across days, or a sudden first-time upload just before the user's departure date.

## False Positive Scenarios

| Scenario | Likelihood | Mitigation |
|---|---|---|
| Shared egress: NAT pool, VDI or terminal server seen as `src` with no user (most sources above 50 MB/hour on Tenant A had no firewall user) | High where User-ID is sparse | Exclude proven shared addresses in `_filter` (`NOT All_Traffic.src IN (...)`) or `_web_filter` (`NOT Web.src IN (...)`) |
| One User-ID login on a shared server (about 17,700 sessions in 4 hours under one login on Tenant A) | Medium | Handled by `_max_user_sessions`: the user is named but not scored. Lower the macro for lighter fleets, or exclude the server |
| Voice or screen-sharing modes of chat assistants stream continuously | Medium | Treat tier low as "look at it"; check `mb_in` symmetry. Raise `_low_mb` if this dominates |
| Long-lived SSE connection logged once at close (Tenant C: "Microsoft Copilot Studio", 55-67 MB a day per user, under 0.3 MB returned) | Medium (SSE tenants) | Ships excluded via `_excluded_providers` = `"Microsoft 365 Copilot"`. Add other providers with the same pattern |
| Integration servers and build hosts calling AI APIs (`anthropic-api-base`, `deepseek-api` dominated 72 of 111 source-hours once those App-IDs were counted) | High once those App-IDs are enabled in the common lookup | Add the servers to `ai_sanctioned_entities` (`<src>|<provider>`) or `_filter` before enabling the App-IDs |
| IDE coding assistants (Copilot, Cursor, Windsurf) upload code context all day (about 1 GB/day for GitHub Copilot via SSE on Tenant C) | High if `ide` is added | Ships excluded (`_usage_types` has no `"ide"`). Add it only with a much higher `_low_mb` |
| Inbound web logs (load balancer, WAF, IIS) in `Web` | No false positives, but slow | Exclude by sourcetype in `_web_filter`: `NOT sourcetype IN ("aws:elb:accesslogs","aws:waf","ms:iis:auto")`. Never `Web.sourcetype`: it matches nothing in `tstats` |

## Response Actions

### If confirmed True Positive

1. **Contain:** block or restrict upload to the AI service for the user or host through the proxy/SSE or firewall policy (for example, block file upload or the App-ID's posting function). If the host is suspected compromised, isolate it with EDR.
2. **Notify:** inform the user's manager and the data governance or privacy owner. Involve HR or legal if policy or regulatory data is involved.
3. **Investigate:** determine what was uploaded: proxy/SSE content or DLP logs, endpoint file access in the hour before the upload (`Endpoint.Filesystem`), clipboard or browser telemetry. Check whether the provider retains or trains on submitted data under the account type used.
4. **Remediate:** request deletion from the provider where an enterprise agreement allows it, rotate any credentials or keys that were in the data, and offer an approved AI alternative.
5. **Document:** record the provider, volume, data classification and disposition in the case.

### If Benign True Positive

1. Add the approved entity to `ai_sanctioned_entities` (common package) with an `expires` date, for example:
   ```
   entity_type,entity,provider,scope,expires,owner,reason,enabled,allow_key
   system,10.20.30.40,OpenAI,provider,2027-03-31,<owner>,<approved integration server>,1,10.20.30.40|openai
   ```
2. For a whole group, use `entity_type=group` with the ES identity `bunit` as `entity` (`allow_key` `<bunit>|<provider>`).
3. Document the business justification in `reason`. The lookup staleness health check (HEALTH-002) warns 14 days before the entry expires.

## Tuning Guidance

### Reducing false positives

- Exclude shared egress and approved integration servers by address in `_filter` / `_web_filter`; put approved people and groups in `ai_sanctioned_entities` instead, so the exemption expires and is reviewed.
- Exclude inbound server sourcetypes from the Web branch (see the table above). On Tenant B this cut the hourly Web branch from about 14 s to 3 s with the same result.
- Keep `"ide"` out of `_usage_types` and keep `Microsoft 365 Copilot` in `_excluded_providers` unless those uploads matter to you.
- Override the score at the last pipe (`hdsi_ai_high_volume_upload_to_ai_service_risk_score`), keeping it between 1 and 100.

### Adjusting thresholds

Measure your own tenant over at least a full day. This reproduces the rule's per-`src` hourly total (firewall branch) and prints the high percentiles and the number of source-hours at each candidate threshold:

```spl
| tstats summariesonly=t allow_old_summaries=t sum(All_Traffic.bytes_out) as bytes_out
    from datamodel=Network_Traffic
    where All_Traffic.bytes_out>0 NOT All_Traffic.action="blocked" `hdsi_ai_high_volume_upload_to_ai_service_app_ids` `hdsi_ai_high_volume_upload_to_ai_service_filter` earliest=-24h@h latest=@h
    by _time span=1h All_Traffic.src All_Traffic.user All_Traffic.app
| rename All_Traffic.* as *
| eval ai_domain=app, ai_input_type="app"
| `ai_domains_filter`
| search usage_type IN (`hdsi_ai_high_volume_upload_to_ai_service_usage_types`) NOT provider IN (`hdsi_ai_high_volume_upload_to_ai_service_excluded_providers`)
| stats sum(bytes_out) as bytes_out by _time src
| eval mb=bytes_out/1048576
| stats count as src_hours exactperc99.9(mb) as p99_9 exactperc99.99(mb) as p99_99 max(mb) as max_mb
    count(eval(mb>=25)) as ge25 count(eval(mb>=50)) as ge50 count(eval(mb>=100)) as ge100
    count(eval(mb>=500)) as ge500 count(eval(mb>=2000)) as ge2000
```

Pick `_low_mb` so the `ge*` count per day is a volume analysts will review. It usually lands at or above `p99_99`. Never go below about 25 MB: on Tenant A the 99th percentile was about 1 MB per hour and a 1 MB threshold would have fired about 7,100 times a day. Keep tiers strictly increasing.

### Expected volume growth

Several PAN-OS App-IDs (`openai-base`, `anthropic-api-base`, `claude-base`, `claude-post`, `deepseek-api`, `google-gemini-posting`, `google-gemini-downloading`) carried real upload volume on Tenant A but were not yet enabled in `ai_provider_apps`. Re-measuring with them counted raised Tenant A from about 24 to about 66 risk events a day. Allow-list API servers first, then re-run the threshold SPL after the common lookup change. Any App-ID you add to `ai_provider_apps` must also be covered by a pattern in `_app_ids`.
