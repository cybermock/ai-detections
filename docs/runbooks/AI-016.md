# AI-016 - Privileged Account AI Service Usage

> **Detection ID:** AI-016 (package `hdsi_ai_privileged_account_service_usage`, `detection_id=hdsi_ai_privileged_account_service_usage`)
> **Search name:** `Identity - HDSI AI Privileged Account Service Usage - Rule`
> **Status:** Active, version 1.1.0, `deployment_type: global`, ships with `enable_alerting: false`
> **Output:** Risk only (`action.notable = 0`), user risk object only (no system risk). Notables come from the HDSI RBA AI aggregators.
> **Risk Score:** computed `risk_score = min(60, highest row_score + 5 per additional provider)`, where `row_score = min(60, max(15, round(30 x basis_weight x severity_weight x bunit_multiplier)))`. Typical 30, or 45 for a built-in administrator. Static `_risk` fallback: user 30
> **MITRE ATT&CK:** T1078 - Valid Accounts (Initial Access / Persistence / Privilege Escalation / Defense Evasion); T1588.007 - Obtain Capabilities: Artificial Intelligence (Resource Development)
> **Data Model:** any of `Web`, `Network_Traffic` (App-ID with User-ID), `Authentication` (IdP sign-ins), plus ES identities
> **Schedule:** `23 * * * *` (hourly at minute 23)
> **Lookback Window:** `-65m@m` to `-5m@m`
> **Suppression:** `user` for 86400s (at most one risk event, at most 60 points, per account per day)
> **Kill Chain Phase:** `collection`
> **Last Updated:** 2026-10-09

---

## Overview

This detection adds user risk when a privileged account uses an AI service. A privileged account is a built-in or break-glass administrator (`Administrator`, `root`, `admin`, `globaladmin`), a separate admin account (`adm-jdoe`, `jdoe_admin`), an ES identity with an admin category (`privileged`, `domain_admin`, `tier0`, ...), or an ES service account. Such accounts exist to administer systems. Chatting with ChatGPT, Claude or Gemini from one is poor credential hygiene, and it is also a common sign that someone else is using the account. Admin context such as scripts, configs, secrets and network details can also end up in an external model.

Evidence comes from any of three sources keyed on the account name: proxy or SSE web logs, firewall App-ID traffic with User-ID, and SSO sign-ins to non-suite AI applications. DNS is deliberately not used because it identifies a host, not an account. The rule emits one risk event per account per day, listing every provider seen in the run that fired. It never creates a notable on its own.

## Detection Logic

### Plain English

1. **Three branches, all keyed on the account, each pre-filtered inside its `tstats` to AI names:**
   - Web (`hdsi_ai_privileged_account_service_usage_web_scope`), with `fillnull_value="unknown"` so domain-less SSE app names in `site` still work. `ai_domain` is `url_domain`, or `site` when there is no `url_domain`.
   - Network_Traffic App-IDs (`..._traffic_scope`, including `-base`, `-post`, `-upload` variants). An App-ID is looked up in `ai_provider_apps` as logged first; only if there is no row is a trailing `-base` removed.
   - Successful Authentication to AI applications (`..._sso_scope`). IdP labels are reduced to lookup keys by `..._sso_app_name` (for example "ChatGPT Enterprise" becomes `chatgpt`, `<org>-chatgpt-sso` resolves through the provider word).
2. **Privileged accounts only (`..._privileged_users`).** The account is looked up in `identity_lookup_expanded` as logged and as the bare name. In order:
   1. Computer accounts (`*$`) are dropped.
   2. Built-in administrator names (`..._builtin_admin`) always count (basis `builtin_admin`).
   3. Other identities that exist only in the ES built-in default account list (guest, oracle, cisco, adm, ...) are dropped.
   4. ES admin category, whole-value match (`..._privileged_identity`, basis `es_identity`).
   5. ES service-account category (`..._service_identity`, basis `service_account`).
   6. Admin naming convention (`..._privileged_name`, basis `account_naming`).
3. **Provider resolution.** `ai_domains_filter`. Disabled rows (including opt-in Microsoft 365 Copilot and Gemini for Workspace) never alert. `traffic_class=background` rows (telemetry, feature flags) are dropped.
4. **Evidence thresholds** per account and provider in the window: Web plus App-ID events at least 3, or at least 25 for suite-embedded providers (`..._ambient_providers`: Google Gemini, Microsoft Copilot, Microsoft 365 Copilot, Gemini for Workspace). An SSO sign-in counts on its own only for non-ambient providers.
5. **Sanctioned use per provider** via `ai_unsanctioned_filter(user,src,provider)`. The rule sets the group to `privileged`, `privileged_service` or `privileged_naming`, so `privileged|github copilot` approves GitHub Copilot for every admin account.
6. **Score.** `basis_weight` 1.5 for a built-in administrator, otherwise 1.0. `severity_weight` from the provider row (0.3-1.2). `bunit_multiplier` from `ai_department_sensitivity` on the identity `bunit`, capped at 2.0. The common `ai_risk_multiplier` is not used, so privilege is not counted twice.
7. **Roll-up** to one row per account: `risk_score = min(60, highest row_score + 5 x (provider_count - 1))`.
8. `..._customizations`, then `..._risk_score` as the last pipe.

## Triage Steps

> **Estimated triage time:** 10-20 minutes. Replace `$user$` with the risk object. For a `DOMAIN\user` value, replace the backslash with `*` inside quoted search terms. Set the time picker to the last 24 hours (7 days for sign-ins).

### Step 1: Validate the risk event

```spl
| from datamodel:"Risk.All_Risk"
| search source="Identity - HDSI AI Privileged Account Service Usage - Rule" risk_object="$user$"
| table _time, risk_object, risk_score, risk_message, privilege_basis, privilege_reason, provider_list, evidence_list, request_count, mb_out
| sort - _time
```

- Why is the account privileged (`privilege_basis`)? A built-in administrator or a domain/tier-0 admin is more serious than a naming-convention match.
- Which providers, through which evidence (web, App-ID, SSO), and how much data was sent (`mb_out`)?

### Step 2: Confirm the privilege classification

```spl
| makeresults
| eval user="$user$"
| `hdsi_ai_privileged_account_service_usage_privileged_users`
| table user, user_bare, privilege_basis, user_category, user_priority, user_bunit
```

```spl
| inputlookup identity_lookup_expanded
| search identity="$user$"
| table identity, first, last, email, managedBy, category, priority, bunit
```

- Is the account really an admin account? ES `category` sometimes holds job titles; the rule matches whole values only.
- Who owns the account (`managedBy`, `email`)? A built-in or shared admin account has no single owner: find out who used it at that time.

### Step 3: Review the AI evidence

App-ID traffic (the rule's "View AI App-ID traffic" drilldown):

```spl
| tstats summariesonly=t allow_old_summaries=t count sum(All_Traffic.bytes_out) as bytes_out sum(All_Traffic.bytes_in) as bytes_in values(All_Traffic.dest) as dest values(All_Traffic.action) as action min(_time) as firstTime max(_time) as lastTime from datamodel=Network_Traffic where All_Traffic.user="$user$" by All_Traffic.user All_Traffic.src All_Traffic.app
| rename All_Traffic.* as *
| eval app_lc=lower(trim(app))
| lookup ai_provider_apps app_name as app_lc OUTPUT app_name as app_exact
| eval ai_domain=if(isnotnull(app_exact),app_lc,replace(app_lc,"-base$","")), ai_input_type="app"
| `ai_domains_filter`
| eval mb_out=round(bytes_out/1024/1024,2), mb_in=round(bytes_in/1024/1024,2)
| convert ctime(firstTime) ctime(lastTime)
| table firstTime, lastTime, user, src, app, provider, usage_type, action, count, mb_out, mb_in, dest
| sort - count
```

Web activity (the rule's "View AI web activity" drilldown):

```spl
| tstats summariesonly=t allow_old_summaries=t fillnull_value="unknown" count sum(Web.bytes_out) as bytes_out sum(Web.bytes_in) as bytes_in values(Web.src) as src values(Web.dest) as dest values(Web.http_user_agent) as http_user_agent min(_time) as firstTime max(_time) as lastTime from datamodel=Web where (Web.url_domain=* OR Web.site=*) Web.user="$user$" by Web.user Web.url_domain Web.site
| rename Web.* as *
| eval ai_domain=lower(coalesce(nullif(url_domain,"unknown"),nullif(site,"unknown"))), ai_input_type=if(isnull(nullif(url_domain,"unknown")),"app","host")
| `ai_domains_filter`
| eval url_domain=coalesce(nullif(url_domain,"unknown"),site), mb_out=round(bytes_out/1024/1024,2), mb_in=round(bytes_in/1024/1024,2)
| convert ctime(firstTime) ctime(lastTime)
| table firstTime, lastTime, user, src, provider, usage_type, url_domain, count, mb_out, mb_in, dest, http_user_agent
| sort - count
```

SSO sign-ins (the rule's "View sign-ins to AI applications" drilldown; use 7 days):

```spl
| tstats summariesonly=t allow_old_summaries=t count values(Authentication.src) as src values(Authentication.dest) as dest values(sourcetype) as sourcetype min(_time) as firstTime max(_time) as lastTime from datamodel=Authentication where Authentication.user="$user$" by Authentication.user Authentication.app Authentication.action
| rename Authentication.* as *
| eval ai_domain=`hdsi_ai_privileged_account_service_usage_sso_app_name`, ai_input_type="app"
| `ai_domains_filter`
| convert ctime(firstTime) ctime(lastTime)
| table firstTime, lastTime, user, app, provider, action, count, src, dest, sourcetype
| sort - lastTime
```

- Browser chat (`usage_type=web`) from an admin account suggests a person pasting admin context. API App-IDs (`openai-api`, `anthropic-api-base`) from a server suggest automation running as the account.
- Which host (`src`) did it come from? An admin workstation, a jump host, a server, or an unexpected location?

### Step 4: Check how the account was used around that time

```spl
| tstats summariesonly=t allow_old_summaries=t count min(_time) as firstTime max(_time) as lastTime from datamodel=Authentication where Authentication.user="$user$" by Authentication.src Authentication.dest Authentication.app Authentication.action
| rename Authentication.* as *
| convert ctime(firstTime) ctime(lastTime)
| sort - count
```

- Logons from unusual sources, failures followed by success, or interactive logons of a service account point at misuse or compromise.

### Step 5: Check related risk and notables

```spl
| from datamodel:"Risk.All_Risk"
| search risk_object="$user$"
| stats sum(risk_score) as total_risk dc(source) as detections values(source) as sources values(ai_kill_chain_phase) as phases by risk_object, risk_object_type
| sort - total_risk
```

```spl
`notable`
| search search_name="Threat - HDSI RBA AI *" "$user$"
| table _time, search_name, rule_title, urgency, status_label, owner
```

- Look for non-AI risk on the same account too (privilege changes, suspicious logons). The query above covers all sources on purpose.
- `Threat - HDSI RBA AI Privilege Escalation Correlation - Rule` deliberately ignores this rule as its AI half, so a privilege change plus this rule alone does not raise that notable. Other AI activity by the account after a privilege change does.
- This rule counts as the high-impact `risky_access` vector in `Threat - HDSI RBA AI Multi-Vector Risk - Rule`.

### Step 6: Determine sanctioned status

```spl
| inputlookup ai_sanctioned_entities
| where enabled=1 AND (in(lower(entity),"privileged","privileged_service","privileged_naming","*") OR entity_type="user")
| table entity_type, entity, provider, scope, expires, owner, reason, allow_key
```

- Is the provider approved for all admin accounts (`privileged|<provider>`), for service accounts (`privileged_service|<provider>`), for the organisation (`*|<provider>`), or for this account?

### Step 7: Make a determination

- **True Positive:** a person used an admin, service or built-in administrator account for AI chat or uploads, or the account was used from an unexpected host or after suspicious logons.
- **Benign True Positive:** approved automation running as a service account (for example an integration host calling `openai-api`), or an approved AI tool (GitHub Copilot) licensed for admins. Sanction it.
- **False Positive:** the account is not really privileged (wrong ES category, a normal account whose name ends in `adm`). Fix the identity data or set `..._privileged_name` to `false()`.

---

## True Positive Indicators

- A built-in administrator (`Administrator`, `root`, `admin`) or tier-0 / domain admin account using a consumer AI chat service.
- `mb_out` greater than zero to a chat service: admin context was sent, not just read.
- The account logged on from an unusual source, or had failed logons before the AI use.
- A service account used interactively (browser user agent, chat web UI) rather than from its integration host.
- Other risk on the account the same day (privilege change, suspicious logon, upload or DLP risk).

---

## False Positive Scenarios

| Scenario | Likelihood | Mitigation |
|---|---|---|
| Suite-embedded AI (Gemini in Workspace, Copilot in M365) on admin accounts. Tenant A: about 200 privileged account-hours a day of Gemini App-ID traffic, almost all at 1-5 events an hour | High without the ambient threshold | Already removed by the ambient threshold (25 an hour); add other suite providers to `..._ambient_providers` |
| Licensed GitHub Copilot via IdP SSO for admin accounts | Medium | `privileged\|github copilot` or `*\|github copilot` in `ai_sanctioned_entities` |
| Sanctioned automation calling an AI API as a service account | Medium where integrations exist | `<account>\|<provider>` or `privileged_service\|<provider>`, halve the score in `..._risk_score`, or set `..._service_identity` to `false()` |
| `admin` or `root` used by a Linux or appliance automation account | Low (not seen on A-D) | Remove the name from `..._builtin_admin`, or sanction the `user\|provider` pair |
| Normal accounts that end in `adm` or ES `category` holding job titles | Low | `..._privileged_name` = `false()`; whole-value category matching already ignores "administrative assistant" |

## Response Actions

### If confirmed True Positive

1. **Contain:** if misuse or compromise is suspected, reset the account's credentials, revoke sessions and tokens, and confirm MFA. Block consumer AI services for admin accounts in the proxy, SSE or firewall policy.
2. **Notify:** the account owner's manager, the privileged-access (PAM) team and the owners of systems the account administers.
3. **Investigate:** determine what admin context could have been sent (scripts, configs, secrets, network details). Review PAM and vault checkouts and the account's recent logons. For a service account, identify the integration and its owner.
4. **Remediate:** enforce separate accounts for admin work and AI use, rotate any secret that may have been pasted, and add an approved AI tool for admins if there is a real need.
5. **Document:** record the account, the providers, the data at risk and the actions taken in the case.

### If Benign True Positive

1. Sanction the combination in `ai_sanctioned_entities` (see Tuning) with an expiry.
2. Record the business justification in `reason`.
3. Close any related aggregator notable as benign.

## Tuning Guidance

### Reducing false positives

| Macro | Ships as | Use |
|---|---|---|
| `hdsi_ai_privileged_account_service_usage_filter` / `..._traffic_filter` / `..._sso_filter` | `()` | Inline exclusions for the Web, Network_Traffic and Authentication `tstats` |
| `..._builtin_admin` | administrator, admin, root, globaladmin, superadmin, ... | Add break-glass names, remove automation names, or `false()` |
| `..._privileged_identity` | whole-value ES admin categories | Append `OR user_priority="critical"` only if critical priority means admin in your ES |
| `..._service_identity` | service, service_account, service_accounts | `false()` to leave service accounts out |
| `..._privileged_name` | admin naming regex | `false()` to use ES categories only |
| `..._ambient_providers` / `..._ambient_min_events` | Gemini, Copilot, M365 Copilot, Gemini for Workspace / 25 | Suite-embedded providers and their higher bar |
| `..._web_scope`, `..._traffic_scope`, `..._sso_scope`, `..._sso_app_name` | generated scopes | Regenerate when the common lookups grow (SPL in the package README) |
| `..._customizations` / `..._risk_score` | `search *` | Final-row filter (e.g. `search NOT privilege_basis="account_naming"`) / last pipe |

### Adjusting thresholds

First check that the tenant marks privileged accounts at all:

```spl
| inputlookup identity_lookup_expanded
| eval user=mvindex(identity,0)
| `hdsi_ai_privileged_account_service_usage_privileged_users`
| stats count by privilege_basis
```

Then size the hourly thresholds from the App-ID branch over 24 hours to 7 days:

```spl
| tstats summariesonly=t allow_old_summaries=t count from datamodel=Network_Traffic where NOT All_Traffic.user IN ("unknown","-") `hdsi_ai_privileged_account_service_usage_traffic_scope` by _time span=1h All_Traffic.user All_Traffic.app
| rename All_Traffic.* as *
| eval app_lc=lower(trim(app))
| `hdsi_ai_privileged_account_service_usage_privileged_users`
| lookup ai_provider_apps app_name as app_lc OUTPUT app_name as app_exact
| eval ai_domain=if(isnotnull(app_exact),app_lc,replace(app_lc,"-base$","")), ai_input_type="app"
| `ai_domains_filter`
| where coalesce(ai_traffic_class,"interactive")!="background"
| stats sum(count) as hourly_events by _time user provider
| eval ambient=if(in(provider,`hdsi_ai_privileged_account_service_usage_ambient_providers`),1,0)
| stats count as account_hours dc(user) as accounts p50(hourly_events) as p50 p90(hourly_events) as p90 max(hourly_events) as max by ambient provider
```

Keep `..._ambient_min_events` above the p90 of ambient providers and `..._min_events` below the typical p50 of deliberate use. On Tenant A, privileged Gemini hours had p90 5 and max 22; OpenAI hours had p50 23.5.
