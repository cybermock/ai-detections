# AI-017 - Usage Volume Anomaly

> **Detection ID:** AI-017
> **Package:** `hdsi_ai_usage_volume_anomaly` v1.1.0 (`deployment_type: global`, ships `enable_alerting: false`)
> **Search name:** `Network - HDSI AI Usage Volume Anomaly - Rule`
> **Status:** Active. Risk-only (`action.notable = 0`). Notables come from the HDSI RBA AI aggregators
> **Risk object:** `user` only (lowercased). No system risk
> **Risk score:** dynamic, `min(70, round(base x risk_multiplier))`, base 20-50 by anomaly type (see Thresholds). Literal fallback 30
> **MITRE ATT&CK:** T1567 Exfiltration Over Web Service (Exfiltration)
> **Data Model:** `Network_Traffic` (firewall App-ID) and/or `Web` (proxy, SSE, URL-filtering or enterprise-browser logs)
> **Schedule:** `30 3 * * *` (daily at 03:30)
> **Lookback Window:** `-15d@d` to `@d` (the last complete day is evaluated against the 14 days before it)
> **Suppression:** 23 hours per `user` (`82800s`)
> **Kill Chain Phase:** `exfiltration` (upload anomaly) or `execution` (request/session-only anomaly)
> **Last Updated:** 2026-10-09

---

## Overview

Once a day this detection compares each user's AI usage on the last complete day with **that user's own baseline** over the previous 14 days. It measures two things: AI sessions or requests, and MB uploaded. Firewall App-ID sessions (`Network_Traffic`) and web/SSE requests (`Web`) are scored separately, each against its own baseline, because their counts are not comparable.

A day far above the user's normal pattern can be a bulk paste or upload of data into an AI service, a script or agent running under the user's identity, or a compromised account. Because the comparison is per user, heavy but steady users do not fire; only a sharp change does. The rule writes risk on the user and never raises a notable on its own.

## Detection Logic

### Plain English

1. **Network_Traffic branch:** `tstats` reads AI App-ID sessions (`..._app_prefilter`) per user per day, excluding blocked sessions. `ai_domains_filter` resolves the App-ID.
2. **Web branch** (appended, `maxtime=1800`): `tstats` reads candidate AI hosts and SSE app names (`..._web_prefilter`) per user per day, excluding blocked requests. `ai_domain` is `url_domain`, or `site` when `url_domain` is empty.
3. **Daily baseline** (`..._daily_baseline`, both branches): keeps the usage types in `..._usage_types` (IDE assistants excluded by default), drops background and vendor-site hosts (`ai_traffic_class` background/site) and rows without a usable user, removes approved entries (`ai_unsanctioned_filter`), sums activity per user per day, then computes the mean and standard deviation over the history days only (the evaluated day is left out).
4. **Coverage scaling:** `history_days` counts the days that really hold summaries (a day counts when its AI user population is at least 2% of the busiest day). A user needs `required_days = min(7, max(4, ceiling(7 x history_days / 14)))` active baseline days: 7 at full coverage, 4 when summaries cover about a week.
5. **z-scores:** `z = (day - mean) / max(stdev, 0.5 x mean, 1)`. With z >= 4 a day must be at least 3x the mean.
6. **Fleet-shift guard:** with 20+ scored users in a source, the population's median z (if positive) is subtracted, so an organisation-wide change does not fire for everyone.
7. **Anomaly:** z >= 4 and count >= the branch floor (100 web/SSE requests, or 500 firewall sessions), or z >= 4 on upload and MB >= 20. If a user is anomalous in both branches, only the stronger row is kept.
8. **Scoring:** base by anomaly type x `risk_multiplier` (identity `bunit` sensitivity, x1.25 privileged, cap 2.0), capped at 70.

## Triage Steps

> **Estimated triage time:** 10-20 minutes

Replace `$user_dd$` with the `user_dd` field from the finding (or the user with any backslash replaced by `*`). Set the time picker to the 15-day window ending at the end of the evaluated day.

### Step 1: Validate the risk event

```spl
| from datamodel:"Risk.All_Risk"
| search source="Network - HDSI AI Usage Volume Anomaly - Rule" risk_object="$user_dd$"
| table _time, risk_object, risk_object_type, risk_score, risk_message
| sort - _time
```

- Read the anomaly type, the count against the baseline mean, the z-scores, MB uploaded and the providers.
- `baseline_days` of `history_days`: a short `history_days` (below 14) means the data model acceleration range is shorter than 15 days and the baseline is thin.

### Step 2: Review the user's daily AI activity

Firewall App-ID (drilldown 2):

```spl
| tstats summariesonly=t allow_old_summaries=t count as sessions sum(All_Traffic.bytes_out) as bytes_out
    from datamodel=Network_Traffic
    where All_Traffic.user="$user_dd$" NOT All_Traffic.action="blocked" `hdsi_ai_usage_volume_anomaly_app_prefilter`
    by _time span=1d All_Traffic.app
| rename All_Traffic.* as *
| eval ai_domain=app, ai_input_type="app"
| `ai_domains_filter`
| search usage_type IN (`hdsi_ai_usage_volume_anomaly_usage_types`) NOT ai_traffic_class IN ("background","site")
| eval day=strftime(_time,"%F")
| stats sum(sessions) as sessions sum(bytes_out) as bytes_out values(app) as app by day provider
| eval mb_out=round(bytes_out/1048576,2)
| fields - bytes_out
| sort - day
```

Web/SSE (drilldown 3). `url_domain` falls back to `site` for SSE app names:

```spl
| tstats summariesonly=t allow_old_summaries=t fillnull_value="unknown" count as requests sum(Web.bytes_out) as bytes_out
    from datamodel=Web
    where Web.user="$user_dd$" NOT Web.action="blocked" (Web.url_domain=* OR Web.site=*)
    by _time span=1d Web.url_domain Web.site
| rename Web.* as *
| eval ai_input_type=if(url_domain="unknown","app","host"), url_domain=coalesce(nullif(url_domain,"unknown"),site), ai_domain=lower(url_domain)
| `ai_domains_filter`
| search usage_type IN (`hdsi_ai_usage_volume_anomaly_usage_types`) NOT ai_traffic_class IN ("background","site")
| eval day=strftime(_time,"%F")
| stats sum(requests) as requests sum(bytes_out) as bytes_out values(ai_domain) as url_domain by day provider
| eval mb_out=round(bytes_out/1048576,2)
| fields - bytes_out
| sort - day
```

- Is the spike one provider or several? A new provider on the spike day is worth noting.
- Did upload MB rise with the request count (bulk paste or file upload), or only requests (interactive use, a script or an agent)?
- The drilldowns are not restricted by the web prefilter or the allow-list, so they can show slightly more than the risk message.

### Step 3: Look at the hours of the spike day

```spl
| tstats summariesonly=t allow_old_summaries=t count as sessions sum(All_Traffic.bytes_out) as bytes_out values(All_Traffic.src) as src
    from datamodel=Network_Traffic
    where All_Traffic.user="$user_dd$" NOT All_Traffic.action="blocked" `hdsi_ai_usage_volume_anomaly_app_prefilter`
    by _time span=1h All_Traffic.app
| rename All_Traffic.* as *
| eval mb_out=round(bytes_out/1048576,2)
| table _time, app, sessions, mb_out, src
| sort _time
```

Set the time picker to the evaluated day only. Use the `Web` equivalent (drilldown 3 with `span=1h`) for web/SSE findings.

- A steady, machine-like rate across many hours or overnight suggests a script or agent; a dense burst during working hours suggests a person pasting or uploading.
- Several source addresses may mean shared credentials or a compromised account.

### Step 4: Identify the user and check related AI risk

```spl
| inputlookup identity_lookup_expanded
| search identity="$account$" OR email="$account$@*"
| table identity, first, last, email, bunit, category, priority, managedBy
```

Here `$account$` is the bare account name (the user without `DOMAIN\` and without `@suffix`), because ES identities are rarely stored in the `DOMAIN\user` form.

```spl
| from datamodel:"Risk.All_Risk"
| search risk_object="$user_dd$" source="*HDSI AI*"
| stats count as events, sum(risk_score) as total_risk, dc(source) as detections, values(source) as sources by risk_object
```

- Upload, DLP, after-hours or first-seen-provider detections on the same day strengthen the finding.
- The user aggregators raise notables at 60 (AI-RISK-001) and 90 (AI-RISK-002) rolling 24-hour AI risk from at least two distinct detections.

### Step 5: Determine sanctioned status

```spl
| inputlookup ai_sanctioned_entities
| search enabled=1 (entity="$user_dd$" OR entity="*")
| table entity_type, entity, provider, scope, expires, owner, reason, allow_key
```

- Supported keys here: `user|provider`, `user|*`, `<bunit>|provider`, `<bunit>|*` and `*|provider` (organisation-wide). The system key is not used, because both branches group by user only. Provider names are matched lowercased.

### Step 6: Make a determination

- **True Positive:** a sharp, unexplained rise in AI use with a large upload to an unsanctioned service, or machine-like activity under a person's identity.
- **Benign True Positive:** a known heavy day (deadline, training, a new AI-enabled IDE or agent, an approved bulk task). Approve with an expiry if it will repeat.
- **False Positive:** a log-source change (new proxy, verbosity change), a thin baseline on a short acceleration range, or ambient assistant traffic that slipped past the background filter.

---

## True Positive Indicators

- `anomaly_type` = `requests and upload` or `upload` with a large MB (tens of MB of text is a lot of pasted data).
- The provider is unsanctioned, or new for the user on the spike day.
- Activity outside the user's normal hours, or from an unusual source address.
- Co-occurring upload, DLP, data-access or after-hours detections.
- The user is leaving, under investigation, or in a sensitive `bunit`.

---

## False Positive Scenarios

Evidence from read-only validation on 4 production ES tenants (Tenant A-D), 2026-10-09.

| Scenario | Likelihood | Mitigation |
|---|---|---|
| Legitimate heavy day (deadline, training, new agent or IDE) | Medium | Allow-list with an expiry (`jdoe|openai`, `jdoe|*`, `<bunit>|openai`) |
| Request-only spikes on sources without `bytes_out` (all Tenant A Web rows were 104-498 requests at 4.6-9.5x the mean) | Medium | They score 20-30 and are labelled `execution`; raise `..._min_requests` if they are too many |
| Ambient assistant traffic (`google-gemini` App-ID seen for more than 120,000 users in 30 days on Tenant A; `gemini.gstatic.com` loaded for more users than `gemini.google.com`) | Low after v1.1 | Generic `google-gemini` App-ID and background hosts are excluded; specific Gemini action App-IDs still count |
| IDE coding assistants following coding workload (produced almost every anomaly on the SSE tenant at low thresholds) | Low (excluded by default) | Keep `"ide"` out of `..._usage_types`; AI-019 covers coding assistants |
| Short acceleration range (Tenant A accelerates `Web` and `Network_Traffic` for `-1w`) makes the baseline thin; a busy Monday after a quiet week can look anomalous | Medium on short ranges | Widen the acceleration range to at least 15 days (a separately approved data model change) |
| Log-source change (new proxy or SSE, changed verbosity) shifts every user's counts | Low | The fleet-shift guard absorbs organisation-wide shifts; re-baseline after onboarding |

---

## Response Actions

### If confirmed True Positive

1. **Contain:** restrict the user's access to the provider (proxy/SSE or firewall policy) while investigating. If an agent or script is running under the user's identity, revoke its API keys or tokens.
2. **Notify:** the user's manager and the data protection team according to policy.
3. **Investigate:** determine what was uploaded (SSE/DLP content logs, endpoint telemetry), and whether the activity came from the user's own device (Step 3 source addresses).
4. **Remediate:** move the use case to an approved service; reset credentials if compromise is suspected.
5. **Document:** record the spike, baseline, evidence and disposition.

### If Benign True Positive

1. Add the approval to `ai_sanctioned_entities` with an expiry and a reason.
2. Close the aggregator notable (if any) as benign.

## Tuning Guidance

### Reducing false positives

- Exclude service accounts or approved AI integration hosts in `hdsi_ai_usage_volume_anomaly_filter` (`All_Traffic.*`).
- Restrict `hdsi_ai_usage_volume_anomaly_web_filter` to the proxy/SSE indexes (`index IN ("proxy","netskope")`). On a tenant with no user-attributed egress Web data, turn the branch off with `index="hdsi_web_branch_off"`: on Tenant B the Web branch cost about 10 minutes a run and found nothing, and the off switch cut the 15-day Web read to 1.5 s.
- Add enabled App-IDs to `..._app_prefilter`; add `*.base` host patterns to `..._web_prefilter` only where needed (leading wildcards are expensive).
- Override the score in `hdsi_ai_usage_volume_anomaly_risk_score` (last pipe, keep 1-100).

### Adjusting thresholds

Check the acceleration range first (the rule reads summaries only):

```spl
| rest /servicesNS/-/-/datamodel/model splunk_server=local count=0
| search title IN ("Web","Network_Traffic")
| spath input=acceleration path=enabled output=accel_enabled
| spath input=acceleration path=earliest_time output=accel_earliest_time
| table title, accel_enabled, accel_earliest_time
```

Then run the rule's search up to (not including) the `| eval count_unit=` line over `-15d@d` to `@d` and append the statistics from the package README (Threshold section) to see, per evidence source, the request/session percentiles, upload percentiles and how many users z >= 4 flags with and without each floor. The floors are noise floors: place them between the median and the p99 of a scored user-day for that branch. On Tenant A the shipped values sit between p90 and p99 (web requests), between median and p75 (firewall sessions) and below p90 (MB).

### Adding allowlist entries

```
entity_type,entity,provider,scope,expires,owner,reason,enabled,allow_key
user,jdoe,OpenAI,provider,2027-03-31,<your_name>,<justification>,1,jdoe|openai
```

## Data Requirements

| Requirement | Details |
|---|---|
| Data Model | `Network_Traffic` and/or `Web` (at least one, with user attribution) |
| Required Fields | Network_Traffic: `user`, `app`, `bytes_out`, `action`. Web: `user`, `url_domain` or `site`, `bytes_out` (optional), `action` |
| Sourcetype Examples | PAN-OS traffic with User-ID; forward proxy, SSE/CASB (app name in `site`), firewall URL-filtering, enterprise-browser audit logs |
| CIM Compliance | Rows without a usable user are dropped; inbound server logs (load balancer, WAF, IIS) never score. Without `bytes_out` only request anomalies are possible |
| Acceleration | Required, with `earliest_time` reaching back at least 15 days for a full baseline |
| Lookups | Common package `hdsi_ai_rba_common`: `ai_provider_domains` (incl. `traffic_class`), `ai_provider_apps`, `ai_sanctioned_entities`, `ai_department_sensitivity`; ES `identity_lookup_expanded` (`bunit`, `category`, `priority`) |

Validation (2026-10-09, 4 production ES tenants): the rule and its 3 drilldowns parse on all tenants. Tenant A (firewall App-ID and URL/enterprise-browser Web logs, `-1w` acceleration) returned 6 rows in 562 s: 2 firewall OpenAI days (16x and 5.5x the mean sessions with 24x and 5x the mean upload, score 50) and 4 request-only Web days. Tenants B, C and D returned 0 rows (B and D have no user-attributed AI data; C scored only 7 non-IDE users). No row had an empty or `unknown` user.
