# AI-036 - Compromised AI Plugin/Extension Installation

> **Detection ID:** AI-036 (package `hdsi_ai_compromised_plugin_extension_installation`, `detection_id="hdsi_ai_compromised_plugin_extension_installation"`)
> **Search name:** `Endpoint - HDSI AI Compromised Plugin/Extension Installation - Rule`
> **Status:** Active, `deployment_type: global` (ships with `enable_alerting: false`)
> **Output:** Risk only (`action.notable = 0`). Notables come from the `Threat - HDSI RBA AI ...` aggregators
> **Risk Score:** Static: `dest` (system) 60, `user` 40. A confirmed IOC match gets no multiplier; set a numeric `risk_score` in `..._risk_score` to override both
> **MITRE ATT&CK:** T1195.001 - Supply Chain Compromise: Compromise Software Dependencies and Development Tools (Initial Access); T1176.001 - Software Extensions: Browser Extensions and T1176.002 - Software Extensions: IDE Extensions (Persistence). Set per row
> **Data Model:** `Web` (full URL paths) OR `Endpoint.Processes` (command lines); either one is enough
> **Schedule:** `1-59/15 * * * *` (every 15 minutes)
> **Lookback Window:** `-20m@m` to `-5m@m`; suppression 24 h (`86400s`) per `dest,user`
> **Kill Chain Phase:** `ai_kill_chain_phase="initial_access"`
> **Last Updated:** 2026-10-09

---

## Overview

This detection fires when a host installs, runs or downloads a **known-compromised or malicious AI-ecosystem package or extension**. Examples: the Nx "s1ngularity" npm releases whose postinstall turned local Claude, Gemini and Amazon Q CLIs against their owners; a backdoored npm package aimed at Cursor users; fake ChatGPT, Claude and DeepSeek SDKs on PyPI; the trojanised Amazon Q VS Code extension 1.84.0; the malicious `postmark-mcp` MCP server; and AI-branded Chrome extensions hijacked in the 2024 Chrome Web Store campaign.

Every hit is an **indicator match** from the maintained IOC macro (`..._ioc_match`), not an AI keyword. A routine `pip install openai` never fires. That makes a hit high-confidence: the host fetched or ran a package or extension that a public advisory has named as malicious. The typical actor is a developer pulled in through a dependency or a browser that was offered a hijacked extension, so treat a hit as a possible endpoint compromise, not as a policy violation.

The rule creates risk on the host (`dest`) and, when the account is a real person, on `user`. Build agents and service accounts score the host only. It contributes to the `adversarial` vector of `Threat - HDSI RBA AI Multi-Vector Risk - Rule`.

## Detection Logic

### Plain English

1. **Web branch (main search):** `tstats` over `Web` for URLs matching `..._store_urls`: Chrome/Edge extension update and CRX downloads (they carry the extension ID), VS Code Marketplace/Open VSX downloads, and npm (`registry.npmjs.org`, `registry.yarnpkg.com`) and PyPI tarballs. `src` becomes `dest`.
2. **Process branch (`append`):** `tstats` over `Endpoint.Processes` for installer and runner command lines matching `..._install_commands` (npm install/add/exec, npx, yarn, pnpm, bun, pip/pipx, uv/uvx, `--install-extension`).
3. Inside each branch, `..._ioc_tag` lower-cases the URL or command line, folds `_` to `-`, and runs `..._ioc_match`. Only rows with an IOC label leave a branch (this keeps the subsearch far below Splunk's subsearch limits).
4. Each row gets its ATT&CK ID from the IOC label.
5. `NT AUTHORITY\*`, machine accounts (`HOST$`) and names in `..._service_accounts` (SYSTEM, LocalSystem, `root`, `jenkins`, `gitlab-runner`, `svc_*`, the Codex sandbox accounts and others) are nulled, so they never become a user risk object. Rows with neither host nor user are dropped.
6. Rows are aggregated per `user` + `dest` with the IOC list, install vector, installer and up to three evidence strings.

### Key Fields

| Field | Description | Example Value |
|---|---|---|
| `dest` | Host name (process branch) or source IP (web branch) | `dev-ws-01` / `10.20.30.40` |
| `user` | Real person; null for service, machine and build accounts | `jdoe@example.com` |
| `ioc_list` | IOC labels matched | `npm: Nx s1ngularity compromise (2025-08), weaponised local AI CLIs` |
| `install_vector` | `process_command_line` and/or `web_store_or_registry` | `web_store_or_registry` |
| `install_tool`, `parent_process_name` | Installer process and its parent (process branch) | `npm.cmd`, `cmd.exe` |
| `evidence_sample` | Up to three command lines or URLs (400 chars) | `registry.npmjs.org/nx/-/nx-21.5.0.tgz` |
| `mitre_attack` | Per-row technique | `T1195.001` |
| `dest_drill`, `user_drill` | Drilldown-safe copies (`\` and `"` become `*`; `__none__` when absent) | `corp*jdoe` |

### Thresholds

| Parameter | Default Value | Macro | Notes |
|---|---|---|---|
| Count threshold | none | n/a | A single IOC match is the signal |
| IOC list | public-advisory list (checked 2026-10) | `hdsi_ai_compromised_plugin_extension_installation_ioc_match(1)` | Add one `match($text$, "<regex>"), "<Ecosystem>: <name> (<yyyy-mm>)"` pair per advisory |
| Download hosts inspected | public npm, PyPI, VS Code/Open VSX, Chrome/Edge | `..._store_urls` | Add internal mirrors (Artifactory, Nexus, Verdaccio) |
| Installers inspected | npm/npx/yarn/pnpm/bun/pip/pipx/uv/uvx/`--install-extension` | `..._install_commands` | Add `poetry add`, `conda install` and similar if used |

## Triage Steps

> **Estimated triage time:** 15-30 minutes. Treat a hit as a possible endpoint compromise until proven otherwise. Replace `<dest>` and `<user>` with the risk event values; for `DOMAIN\user` use the `user_drill` form (`DOMAIN*user`).

### Step 1: Validate the risk event

```spl
| from datamodel:"Risk.All_Risk"
| search source="Endpoint - HDSI AI Compromised Plugin/Extension Installation - Rule" (risk_object="<dest>" OR risk_object="<user>")
| table _time risk_object risk_object_type risk_score risk_message
| sort - _time
```

- Read `ioc_list` and `evidence_sample` in the message. Note the advisory date in the label.
- For a version-pinned IOC (Nx, Ultralytics, Amazon Q extension), confirm the evidence carries the exact compromised version.

### Step 2: Identify the host and user

```spl
| inputlookup asset_lookup_by_str
| search ip="<dest>" OR dns="<dest>" OR nt_host="<dest>"
| table ip dns nt_host owner priority bunit category
```

```spl
| inputlookup identity_lookup_expanded
| search identity="<user>"
| table identity first last email managedBy priority bunit category
```

- For web-branch rows, `dest` is the source IP the proxy logged. Resolve it to a host before acting.
- A build agent (no user) is still in scope: a compromised CI dependency can steal pipeline secrets.

### Step 3: Review the install evidence

Use the query that matches `install_vector`.

Process branch (`process_command_line`):

```spl
| tstats summariesonly=t allow_old_summaries=t count min(_time) as firstTime max(_time) as lastTime from datamodel=Endpoint.Processes where (Processes.dest="<dest>" OR Processes.user="<user>") `hdsi_ai_compromised_plugin_extension_installation_install_commands` by Processes.user Processes.dest Processes.parent_process_name Processes.process_name Processes.process
| rename Processes.* as *
| eval ioc_text=" ".replace(lower(process),"_","-")." "
| eval ioc_name=`hdsi_ai_compromised_plugin_extension_installation_ioc_match(ioc_text)`
| convert ctime(firstTime) ctime(lastTime)
| table firstTime lastTime user dest parent_process_name process_name process ioc_name count
| sort - lastTime
```

Web branch (`web_store_or_registry`):

```spl
| tstats summariesonly=t allow_old_summaries=t count min(_time) as firstTime max(_time) as lastTime from datamodel=Web where (Web.src="<dest>" OR Web.user="<user>") `hdsi_ai_compromised_plugin_extension_installation_store_urls` by Web.user Web.src Web.url
| rename Web.* as *
| eval ioc_text=" ".replace(lower(url),"_","-")." "
| eval ioc_name=`hdsi_ai_compromised_plugin_extension_installation_ioc_match(ioc_text)`
| convert ctime(firstTime) ctime(lastTime)
| table firstTime lastTime user src url ioc_name count
| sort - lastTime
```

- Rows with an `ioc_name` are the hits; the rest show what else the host installed around the same time.
- Chrome extension fetches with `v=0.0.0.0` are an install or a policy force-install fetch, not proof the extension is still installed. Several hijacked extensions were later republished clean under the same ID, so check the installed version on the endpoint.
- For the Nx s1ngularity packages, look for follow-on execution of `claude`, `gemini` or `q` CLIs with permission-bypass flags and for a new public GitHub repository named like `s1ngularity-repository` in the user's account.

### Step 4: Check for related detections

```spl
| from datamodel:"Risk.All_Risk"
| search (risk_object="<dest>" OR risk_object="<user>") source="*HDSI AI*"
| stats sum(risk_score) as total_risk dc(source) as detections values(source) as sources by risk_object risk_object_type
| sort - total_risk
```

- Run over `-24h` and `-7d`. This rule alone (60/40) plus any other detection usually crosses the medium (60) user threshold.
- Look for `Endpoint - HDSI AI Unsanctioned CLI Execution - Rule`, `Endpoint - HDSI AI Agent Autonomous Action Detection - Rule` and `Endpoint - HDSI AI MCP Server Execution - Rule` on the same host after the install time, and for non-AI ES detections (credential access, exfiltration) on the host.

### Step 5: Determine sanctioned status

There is no allowlist path for IOC matches through `ai_sanctioned_entities`. The only legitimate reason for a hit is a **security research or malware-analysis sandbox** that installs samples on purpose. Confirm whether the host is such a system:

```spl
| inputlookup asset_lookup_by_str
| search (ip="<dest>" OR dns="<dest>" OR nt_host="<dest>") category=*
| table ip dns nt_host category bunit owner
```

### Step 6: Make a determination

- **True Positive:** the evidence names a compromised version or package and the host is a normal workstation, server or build agent.
- **Benign True Positive:** a sanctioned research or sandbox host (exclude it in `_filter`/`_web_filter`).
- **False Positive:** the IOC regex matched an unrelated string (report it so the IOC entry can be tightened), or an extension ID that was later republished clean and the installed version is the clean one.

---

## True Positive Indicators

- `evidence_sample` shows the exact compromised version (`nx@21.5.0`, `nx/-/nx-21.5.0.tgz`, `ultralytics==8.3.41`, `amazon-q-vscode` 1.84.0).
- The install ran as a real user on a developer workstation, or on a CI agent that holds deployment secrets.
- Follow-on activity on the host: AI CLI execution with unusual flags, outbound connections to new hosts, GitHub repository creation, credential file access.
- The browser extension is still present in the endpoint's extension inventory at the hijacked version.

---

## False Positive Scenarios

| Scenario | Likelihood | Mitigation |
|---|---|---|
| Security research or malware-analysis sandbox installs samples on purpose | Low | Exclude the host in `..._filter` (`Processes.*`) and `..._web_filter` (`Web.*`) |
| Chrome ID fetch for an extension that was republished clean under the same ID | Low | Check the installed version on the endpoint before escalating |
| A browser repeatedly fetching an extension it cannot install (policy force-install), producing a hit each day | Low | Suppression is 24 h per `dest,user`; remove the ID from browser policy |
| An unrelated string that happens to match an IOC regex | Very low (0 matches in validation; 49/49 and 19/19 regex controls passed) | Tighten the regex in `..._ioc_match`; test with `makeresults` |

---

## Response Actions

### If confirmed True Positive

1. **Contain:** isolate the host with EDR. For a CI agent, stop the pipeline and quarantine the runner.
2. **Notify:** incident response, the host owner's manager and AppSec. This is a supply-chain compromise, not an AI policy matter.
3. **Investigate:** follow the advisory's indicators (postinstall scripts, dropped files, outbound hosts, created repositories). Check every host that pulled the same version through the Web branch query over `-30d`.
4. **Remediate:** remove the package or extension, pin a clean version, rebuild the host if the payload executed, and rotate every credential reachable from it (npm, GitHub, cloud keys, AI provider API keys, browser sessions).
5. **Document:** record findings in the case management system, including the advisory reference.

### If Benign True Positive

1. Exclude the sandbox host in `..._filter` / `..._web_filter` with a comment naming the approval.
2. Document the justification.
3. Close the investigation as "Benign True Positive."

## Tuning Guidance

### Reducing false positives

- Keep the IOC list specific. Never add a generic AI keyword to `..._ioc_match`; v1.0 did, and turned every `pip install openai` into a hit.
- Add build and service account naming to `..._service_accounts` so CI installs score the host only.
- On tenants where the Web model holds inbound traffic only (Tenants B and D in validation), exclude the Web branch with `..._web_filter` or leave the rule disabled; it scans for nothing there.

### Adjusting thresholds

There is no count threshold. Test a new IOC entry before adding it:

```spl
| makeresults
| eval evidence=" npm install nx@21.5.0 "
| eval ioc_text=" ".replace(lower(evidence),"_","-")." "
| eval ioc_name=`hdsi_ai_compromised_plugin_extension_installation_ioc_match(ioc_text)`
| table evidence ioc_name
```

In the regex use `[.]` for a dot, `\x22` for a double quote and `\x5c` for a backslash. Pinned versions must reject prereleases (`-beta`, `rc`, `.dev`).

### Adding allowlist entries

IOC hits are not allowlisted through `ai_sanctioned_entities`. Exclude approved research hosts inline:

```
[hdsi_ai_compromised_plugin_extension_installation_filter]
definition = (NOT Processes.dest IN ("malware-lab-*"))
```
