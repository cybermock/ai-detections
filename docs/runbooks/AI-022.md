# AI-022 - HDSI AI Access Via VPN/Proxy Evasion

> **Detection ID:** AI-022 (runbook ID; results carry `detection_id=hdsi_ai_access_via_vpn_proxy_evasion`)
> **Search name:** `Network - HDSI AI Access Via VPN/Proxy Evasion - Rule`
> **Package:** `hdsi_ai_access_via_vpn_proxy_evasion` v1.1.0 (`deployment_type: global`, `enable_alerting: false`)
> **Status:** Active
> **Output:** Risk only (`action.notable = 0`). Aggregators raise the notable.
> **Risk Score:** `src` (system) and `user` (only when exactly one real user was seen for the source). Dynamic `risk_score = min(60, round(base × risk_multiplier))` on both objects. Base 40 / 25 / 20 / 10, +10 when Tor got through. Rows below base 20 are not emitted. Literal `_risk` fallback 25 / 25.
> **MITRE ATT&CK:** T1090 - Proxy, T1090.003 - Proxy: Multi-hop Proxy (Command and Control); T1588.007 - Obtain Capabilities: Artificial Intelligence (Resource Development)
> **Data Model:** `Network_Traffic` (NGFW App-ID), `Web` (gateway URL category), `Network_Resolution` (DNS). Any one evasion path plus any one AI path is enough.
> **Schedule:** `5 * * * *` (hourly at :05)
> **Lookback Window:** `-65m@m` to `-5m@m`
> **Suppression:** 24 h (`86400s`) per `src`
> **Kill Chain Phase:** `initial_access` (multi-vector aggregator vector: `risky_access`)
> **Last Updated:** 2026-10-09

## Overview

This detection finds a host that uses **Tor, a consumer anonymising VPN (NordVPN, ExpressVPN, Hotspot Shield, Surfshark, Proton VPN and others) or a proxy-avoidance service in the same hour as AI service activity**. A tunnel hides the AI traffic itself from the proxy, the CASB and DLP, so the organisation loses sight of what is sent to the AI provider. When the AI service was **blocked** and the evasion tool then **got through**, the user is very likely working around the AI policy on purpose.

The typical actor is an employee who installed a personal VPN client, either to reach a blocked AI service or for unrelated privacy reasons. Malware and residential-proxy SDKs bundled in free apps can produce the same evidence. Most results are governance findings ("VPN installed, AI used in the same hour"). The strongest signal is the 40 tier: AI blocked, then an evasion tool allowed.

Evidence comes from where evasion tools are actually identified: firewall App-ID, web gateway URL categories and VPN client DNS names. The six `tstats` branches (three evasion, three AI) are chained with `prestats=t append=t`, so no subsearch row limit applies.

## Detection Logic

### Plain English

1. **Evasion evidence** from three branches, each filtered inside its `tstats` where clause:
   - `Network_Traffic`: consumer VPN, Tor and proxy App-IDs (`..._evasion_app_ids`). Enterprise VPNs (`ike`, `ipsec-*`, `open-vpn`, `wireguard`, `tailscale-*`, `zerotier`, `cloudflare-warp`) are deliberately absent.
   - `Web`: anonymizer / proxy-avoidance URL categories (`..._anonymizer_categories`), minus OS privacy relays such as iCloud Private Relay (`..._web_exclusions`). The host is `url_domain`, or `site` on SSE data without a domain.
   - `Network_Resolution`: VPN vendor API and Tor Browser hostnames (`..._evasion_dns`).
2. **AI evidence** from the same three models: AI App-IDs, AI hostnames, and SSE app names.
3. Keep only sources that have both evasion and AI evidence in the window. Resolve AI rows with the common `ai_domains_filter` (PAN App-IDs are also tried without their `-base`/`-post` suffix and by first token). Drop background AI hosts (`ai_traffic_class=background`), providers in `..._sanctioned_providers` and entities approved in `ai_sanctioned_entities`, then repeat the both-sides check.
4. Aggregate to one row per `src`. `user` is set only when exactly one user was seen. Sources with more than `..._max_users_per_src` (3) users are shared egress and dropped. User-less public addresses (`..._unreliable_src`) are dropped. User-less remote-access/CGNAT pool addresses (`..._dynamic_src`, `100.64.0.0/10`) are dropped below the 40 tier.
5. Score the base tier:

   | Base | `ai_outcome` | Meaning |
   |---|---|---|
   | 40 | `AI blocked, then evasion tool allowed` / `AI blocked, evasion tool allowed` | AI was blocked and an evasion tool passed |
   | 25 | `AI allowed, evasion tool allowed (co-occurrence)` | Both seen in the same hour; not proof the AI traffic went through the tunnel |
   | 20 | `AI blocked, evasion attempt blocked or DNS only` | AI blocked; the evasion attempt was blocked, DNS-only, or a vendor site visit / installer download |
   | 10 | `AI allowed, evasion attempt blocked or DNS only` | Not emitted by default (`..._min_base_score` = 20) |
   | +10 | | Tor got through (allowed `tor` App-ID, or an allowed Tor Browser host). Blocked Tor and Tor names seen only in DNS do not add it |

6. `risk_score = min(60, round(base × risk_multiplier))` (identity `bunit` sensitivity × 1.25 for privileged users, capped at 2.0), applied to `src` and `user`.

"Passed" means an App-ID session or a Web anonymizer-category event that was not blocked. An allowed Web event whose host matches `..._web_attempt_hosts` (apex/`www` vendor sites, wildcard SNI, no host, `downloads.*`, `updates.*`, any `cdn` host) counts as an attempt, not as the tool passing.

|---|---|---|---|

## Triage Steps

> **Estimated triage time:** 15 to 25 minutes. Replace `<src>` and `<user>` with the values from the risk event. Run each search over the time of the risk event (time picker).

### Step 1: Validate the risk event and read the tier

```spl
| from datamodel:"Risk.All_Risk"
| search source="Network - HDSI AI Access Via VPN/Proxy Evasion - Rule" (risk_object="<src>" OR risk_object="<user>")
| table _time, source, risk_object, risk_object_type, risk_score, ai_outcome, evasion_list, provider_list, risk_message
| sort - _time
```

- `ai_outcome` is the most important field. "AI blocked, then evasion tool allowed" is a likely policy bypass. "AI allowed, evasion tool allowed (co-occurrence)" is a governance finding.
- Most rows carry no user (consumer-VPN App-ID sessions usually have no User-ID). Then only the host has risk; find the person in Step 2.

### Step 2: Identify the host and user

```spl
| makeresults
| eval src="<src>"
| lookup asset_lookup_by_str asset as src OUTPUT nt_host, owner, bunit, category, priority
| table src, nt_host, owner, bunit, category, priority
```

```spl
| inputlookup identity_lookup_expanded
| search identity="<user>"
| table identity, first, last, email, bunit, category, priority, managedBy
```

- If `user` is empty, use the asset owner, EDR logged-on user or VPN/DHCP records for the event time.
- A `100.64.0.0/10` or other pool address is reassigned between people: only a 40-tier row is emitted for a user-less pool address, and you must resolve the session owner at the event time.

### Step 3: Review the evidence

Firewall sessions (evasion and AI App-IDs), the rule's second drilldown:

```spl
| tstats summariesonly=t allow_old_summaries=t fillnull_value="unknown" count min(_time) as firstTime max(_time) as lastTime values(All_Traffic.dest) as dest values(All_Traffic.dest_port) as dest_port sum(All_Traffic.bytes_out) as bytes_out from datamodel=Network_Traffic where All_Traffic.src="<src>" (`hdsi_ai_access_via_vpn_proxy_evasion_evasion_app_ids` OR `hdsi_ai_access_via_vpn_proxy_evasion_ai_app_ids`) by All_Traffic.src All_Traffic.user All_Traffic.app All_Traffic.action
| rename All_Traffic.* as *
| eval mb_out=round(bytes_out/1024/1024,2)
| convert ctime(firstTime) ctime(lastTime)
| table firstTime, lastTime, src, user, app, action, dest, dest_port, count, mb_out
| sort firstTime
```

Anonymizer and AI web activity (handles proxies that fill only `url_domain` and SSE data that fills only `site`):

```spl
| tstats summariesonly=t allow_old_summaries=t fillnull_value="unknown" count min(_time) as firstTime max(_time) as lastTime values(Web.category) as category values(Web.http_user_agent) as http_user_agent from datamodel=Web where Web.src="<src>" (Web.url_domain=* OR Web.site=*) (`hdsi_ai_access_via_vpn_proxy_evasion_anonymizer_categories` OR `hdsi_ai_access_via_vpn_proxy_evasion_ai_web_names`) by Web.src Web.user Web.url_domain Web.site Web.action
| rename Web.* as *
| eval url_domain=coalesce(nullif(url_domain,"unknown"),nullif(site,"unknown"),"(no host)")
| convert ctime(firstTime) ctime(lastTime)
| table firstTime, lastTime, src, user, url_domain, category, action, count, http_user_agent
| sort - count
```

VPN and AI DNS queries:

```spl
| tstats summariesonly=t allow_old_summaries=t count min(_time) as firstTime max(_time) as lastTime from datamodel=Network_Resolution where DNS.src="<src>" (`hdsi_ai_access_via_vpn_proxy_evasion_evasion_dns` OR `hdsi_ai_access_via_vpn_proxy_evasion_ai_dns_names`) by DNS.src DNS.query
| rename DNS.* as *
| convert ctime(firstTime) ctime(lastTime)
| table firstTime, lastTime, src, query, count
| sort - count
```

What to look for:

- **Order of events.** Blocked AI first, then an allowed VPN/Tor session, then AI traffic stops on the firewall: the user moved the AI traffic into the tunnel.
- **Volume through the tunnel.** Large `mb_out` on the evasion App-ID after an AI block is the strongest sign of data leaving.
- **Installer or vendor site only.** `web:` evidence on `downloads.*`, `*cdn*` or apex vendor hosts means the user is installing or reading about a VPN, not yet using it (scored as an attempt).
- **Random-looking anonymizer domains** usually come from a residential-proxy SDK in a free app, not a user choice. Check the endpoint's installed software.

### Step 4: Check for related detections

```spl
| from datamodel:"Risk.All_Risk"
| search (risk_object="<src>" OR risk_object="<user>") source="*HDSI*"
| stats sum(risk_score) as total_risk dc(source) as detections values(source) as sources by risk_object, risk_object_type
| sort - total_risk
```

- This rule is a `risky_access` (high-impact) vector for `Threat - HDSI RBA AI Multi-Vector Risk - Rule` (3 of 6 vectors in 24 h).
- User risk counts toward `Threat - HDSI RBA AI User Risk Threshold Exceeded - Rule` (60, at least two distinct detections) and `Threat - HDSI RBA AI User Critical Risk Threshold Exceeded - Rule` (90).
- Upload, DLP or personal-account detections on the same user or host in the same day turn a governance finding into a data-exposure case.

### Step 5: Determine sanctioned status

```spl
| inputlookup ai_sanctioned_entities
| search enabled=1 (entity="<user>" OR entity="<src>")
| table entity_type, entity, provider, scope, expires, owner, reason, allow_key
```

- Also confirm with the network team whether the VPN product itself is approved (some organisations allow a consumer VPN for travel).

### Step 6: Make a determination

- **True Positive:** an unsanctioned VPN/Tor/anonymizer was used to reach AI services, especially after an AI block (40 tier).
- **Benign True Positive:** a sanctioned VPN or approved research/testing (red team, threat intel) in the same hour as allowed AI use.
- **False Positive:** shared egress, a reassigned address, an OS privacy relay or a mis-categorised host. Tune the scope macros.

## True Positive Indicators

- `ai_outcome` = "AI blocked, then evasion tool allowed" (`bypass_after_block=1`).
- Tor passed (`tor_seen=1`, base +10).
- Large outbound volume on the evasion session shortly after an AI block.
- The user has no business reason for a consumer VPN and is not in an approved programme.
- Other HDSI AI risk on the same user (uploads, personal account, DLP).

## False Positive Scenarios

Evidence from the 2026-10-09 validation on 4 production ES tenants (package README):

| Scenario | Likelihood | Mitigation |
|---|---|---|
| Personal VPN client on a corporate laptop, AI used the same hour (25 tier) | High | This is the bulk of results (Tenant A: every row in six consecutive hourly runs was 25 except two at 40 and one at 20). Treat as governance context; raise `..._min_base_score` to 40 if only bypasses matter |
| iCloud Private Relay and other OS privacy relays in the anonymizer category | High if not excluded | Excluded by `..._web_exclusions` (86% of anonymizer events on Tenant A, about 34,000 sources a day). Add Chrome IP Protection or Edge Secure Network hosts if your gateway categorises them as anonymizers |
| Reassigned remote-access VPN or CGNAT pool addresses with no user | Medium | `..._dynamic_src` drops them below the 40 tier (7 of 11 correlated sources in a 4 h Tenant A window). Add your own pool ranges |
| Explicit proxy, NAT pool, VDI or terminal server as `src` | Medium | `..._max_users_per_src`, `..._unreliable_src` (public IPv4) and the filter macros |
| Enterprise VPN / mesh (OpenVPN, WireGuard, Tailscale, ZeroTier, Cloudflare WARP) | n/a | Not in `..._evasion_app_ids` by design. Add one only after confirming it is unsanctioned |
| Vendor site visit or installer download categorised as anonymizer | Low | `..._web_attempt_hosts` scores these as attempts (10/20), not as the tool passing |
| Residential-proxy SDK in a free app | Low | Real anonymizer infrastructure but not a user choice; review installed software |

## Response Actions

### If confirmed True Positive

1. **Contain:** block the VPN/Tor App-IDs and anonymizer category for the host or user, and remove the VPN client through EDR or software management.
2. **Notify:** the user's manager and the data governance team, since AI traffic left without proxy, CASB or DLP inspection.
3. **Investigate:** estimate what went through the tunnel (session `mb_out`, timing against AI blocks). Check endpoint telemetry for files opened before the session. Check the user's other HDSI AI risk.
4. **Remediate:** enforce the VPN/anonymizer policy at the firewall, and provide an approved AI service if the user had a business need.
5. **Document:** record evidence, tier and outcome in the case.

### If Benign True Positive

1. Add the user, host or group to `ai_sanctioned_entities` with an `expires` date. An entity approved for `*` also suppresses its evasion rows.
2. For a provider licensed for everyone, add it to `hdsi_ai_access_via_vpn_proxy_evasion_sanctioned_providers`.
3. Close the related aggregator notable (if any) as benign.

## Tuning Guidance

### Reducing false positives

- Set `..._sanctioned_providers` (e.g. `"Google Gemini","Microsoft Copilot"`).
- Add DNS forwarders, explicit proxies and NAT addresses to `..._dns_filter`, `..._web_filter` or `..._filter`.
- Add remote-access VPN pools to `..._dynamic_src`.
- Use `hdsi_ai_access_via_vpn_proxy_evasion_customizations` for post-aggregation exclusions and `hdsi_ai_access_via_vpn_proxy_evasion_risk_score` (last pipe) to rescale `risk_score`.

### Adjusting thresholds

Measure the tier mix before changing `..._min_base_score` (set it to 10 temporarily). Use 24 h on small tenants and 4 to 8 h on a large NGFW tenant (8 h took 219 s on Tenant A; 24 h ran past 300 s):

```spl
| savedsearch "Network - HDSI AI Access Via VPN/Proxy Evasion - Rule"
| stats count as sources by base_score ai_outcome
```

Derive `..._max_users_per_src`:

```spl
| tstats summariesonly=t allow_old_summaries=t dc(All_Traffic.user) as users from datamodel=Network_Traffic where `hdsi_ai_access_via_vpn_proxy_evasion_ai_app_ids` All_Traffic.user=* NOT All_Traffic.user="unknown" by All_Traffic.src _time span=1h
| stats max(users) as max_users_per_hour by All_Traffic.src
| stats count as srcs by max_users_per_hour
| sort max_users_per_hour
```

### Adding allowlist entries

`ai_sanctioned_entities.csv` in `hdsi_ai_rba_common` (keys are lower case `<user, src or bunit>|<provider>` or `<entity>|*`):

```
entity_type,entity,provider,scope,expires,owner,reason,enabled,allow_key
user,jdoe,*,global,<YYYY-MM-DD>,<your_name>,<justification>,1,jdoe|*
group,threat intelligence,*,group,<YYYY-MM-DD>,<your_name>,<justification>,1,threat intelligence|*
```
