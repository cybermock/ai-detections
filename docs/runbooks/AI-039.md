# AI-039 - HDSI AI Agent Autonomous Action Detection

> **Detection ID:** AI-039 (runbook ID; results carry `detection_id=hdsi_ai_agent_autonomous_action_detection`)
> **Search name:** `Endpoint - HDSI AI Agent Autonomous Action Detection - Rule`
> **Package:** `hdsi_ai_agent_autonomous_action_detection` v1.1.0 (`deployment_type: global`, `enable_alerting: false`)
> **Status:** Active
> **Output:** Risk only (`action.notable = 0`). Aggregators raise the notable.
> **Risk Score:** `user` (user) and `dest` (system), same dynamic `risk_score` on both, one result per `risk_category`:
> `agent_activity` 10 + 5 per development category (10 to 25, no multiplier); `credential_access` 25, `persistence` 30, `system_change` 25, each × `risk_multiplier`, capped at 60. Literal `_risk` fallback 10 / 10. Service, machine and Codex sandbox accounts give host-only risk.
> **MITRE ATT&CK:** T1059 - Command and Scripting Interpreter (Execution); T1552 - Unsecured Credentials (Credential Access); T1053 - Scheduled Task/Job (Persistence); T1105 - Ingress Tool Transfer (Command and Control). Decided per result.
> **Data Model:** `Endpoint.Processes` (parent name/path and full command line)
> **Schedule:** `7 * * * *` (hourly at :07)
> **Lookback Window:** `-65m@m` to `-5m@m`
> **Suppression:** 24 h (`86400s`) per `user`, `dest`, `risk_category`
> **Kill Chain Phase:** `execution` (multi-vector aggregator: `adversarial` for `credential_access`/`persistence`/`system_change`, `local_tooling` for `agent_activity`)
> **Last Updated:** 2026-10-09

## Overview

This detection finds **AI coding agents and agent frameworks running commands on an endpoint by themselves**: Claude Code, OpenAI Codex, the GitHub Copilot agent runtime in VS Code, Gemini CLI, Aider, Goose, OpenCode, Cursor Agent, Amazon Q / Kiro, Cline, OpenHands, CrewAI, AutoGen, LangChain/LangGraph and others. A user who hands shell access to an agent hands it their credentials, network position and write access. Prompt injection, a poisoned repository or a bad plan can then become `curl | sh`, a secret read, a scheduled task or a forced push with no human typing the command.

The rule ignores the agents' own start-up probes. It emits:

- at most one low-score **`agent_activity`** risk event per user and host per day for ordinary agent work (routine commands, package installs, `git push`, downloads, recursive deletes), and
- a separate risk event for each **high-signal** category: `credential_access`, `persistence`, `system_change`. These are never allow-listed, because they are exactly what a misdirected agent does.

Most results are developers doing their jobs. The high-signal events are the ones to investigate.

## Detection Logic

### Plain English

1. Query `Endpoint.Processes` with `tstats` for processes whose parent is a known agent binary or whose parent path/command line contains an agent package (`..._agent_scope`). Claude Code shell snapshots and Codex Windows sandbox accounts (`CodexSandbox*`) also match. The Microsoft Copilot consumer app is excluded.
2. Label the agent (`agent_tool`) and map it to the common registry provider name (`Anthropic`, `OpenAI`, `GitHub Copilot`, `Google Gemini`, `Cursor`, `Amazon Q`, `Kiro`, `Aider`; other agents use their own label).
3. Drop start-up probes (`..._housekeeping(2)`, anchored to their full command shape), self-spawns (except shells and script hosts) and Claude desktop MCP server launches (covered by `hdsi_ai_mcp_server_execution`).
4. Categorise each command line (`..._categorize(1)`):

   | Tier | Category | Examples |
   |---|---|---|
   | High-signal | `credential_access` | `.env`, `.env.local`, `~/.aws/credentials`, `~/.ssh/id_*`, `.npmrc`, `cmdkey`, `gh auth token`, `az account get-access-token`, browser `Login Data` (not `.env.example`/`.sample`/`.template` copies) |
   | High-signal | `persistence` | `schtasks /create`, `Register-ScheduledTask`, `crontab -e`/`-u <user> -e`/`crontab <file>`/`... \| crontab -`, `launchctl load`, `systemctl enable`, Run keys, `New-Service`/`sc create` (not `crontab -l`) |
   | High-signal | `system_change` | `sudo`, `runas`, `Set-MpPreference`, `netsh firewall`, `net localgroup administrators /add`, `reg add`, `Set-ExecutionPolicy Bypass`, `vssadmin` |
   | Development | `network_transfer` | `curl`, `wget`, `scp`, `rclone`, `Invoke-WebRequest`, `DownloadString`, `certutil -urlcache`, `git push` |
   | Development | `destructive` | `rm -rf`, `Remove-Item -Recurse`, `rd /s`, `git reset --hard`, `git clean -f`, `git push --force`, `DROP TABLE` |
   | Development | `package_install` | `pip install`, `uv add`, `uvx`, `npm install <pkg>`, `npx -y ...`, `npx <pkg>@<ver>`, `pnpm dlx`, `winget`/`choco`/`brew`/`apt install` |

5. Null service, machine and sandbox accounts (`SYSTEM`, `NT AUTHORITY\*`, `HOST$`, `unknown`, `CodexSandbox*`) so they never become a user risk object. The sandbox account is shown in `user_display`.
6. Aggregate per `user` + `dest` + `agent_tool` + `provider` for the hour, then expand into one result per `risk_category`:
   - `agent_activity` when `action_count >= ..._min_actions` (3) or any development category is present;
   - one result for each high-signal category present.
7. Apply `ai_unsanctioned_filter` to `agent_activity` only (high-signal results use a placeholder key that no allow-list row can match).
8. Score (see header) and build `command_sample` (up to three commands for that category, most severe first, inline secrets redacted).

## Triage Steps

> **Estimated triage time:** 10 to 30 minutes (high-signal events take longer). Replace `<user>`, `<dest>` (or `<user_dd>`/`<dest_dd>` for `DOMAIN\user` values) with the values from the risk event. Run each search over the time of the risk event (time picker), unless stated otherwise.

### Step 1: Validate the risk event and its category

```spl
| from datamodel:"Risk.All_Risk"
| search source="Endpoint - HDSI AI Agent Autonomous Action Detection - Rule" (risk_object="<dest_dd>" OR risk_object="<user_dd>")
| table _time, source, risk_object, risk_object_type, risk_score, risk_category, risk_tier, agent_tool, command_sample, risk_message
| sort - _time
```

- `risk_category=agent_activity` (`routine` or `development`) is ordinary agent work: a quick review is enough unless other risk exists.
- `credential_access`, `persistence` or `system_change` (`risk_tier=sensitive`) need Steps 3 to 6.
- Each category is counted at most once per user and host per day. A second agent on the same host the same day is inside the same suppression key, so the first agent seen names the event.

### Step 2: Identify the user and host

```spl
| inputlookup identity_lookup_expanded
| search identity="<user>"
| table identity, first, last, email, bunit, category, priority, managedBy
```

```spl
| makeresults
| eval dest="<dest>"
| lookup asset_lookup_by_str asset as dest OUTPUT nt_host, owner, bunit, category, priority
| table dest, nt_host, owner, bunit, category, priority
```

- Is the user a developer, and is the host a developer workstation, build agent or server? An agent running on a server or a non-developer's laptop is unusual.
- If `user_display` shows a Codex sandbox account, the human user is not in the event; find the logged-on user on the host.

### Step 3: Review the agent's commands

This is the rule's second drilldown (24 h of agent child processes for the user or host):

```spl
| tstats summariesonly=t allow_old_summaries=t count min(_time) as firstTime max(_time) as lastTime from datamodel=Endpoint.Processes where (Processes.dest="<dest_dd>" OR Processes.user="<user_dd>") `hdsi_ai_agent_autonomous_action_detection_agent_scope` by Processes.user Processes.dest Processes.parent_process_name Processes.process_name Processes.process
| rename Processes.* as *
| convert ctime(firstTime) ctime(lastTime)
| sort - lastTime
```

What to look for:

- **`credential_access`:** which secret was read (`.env`, cloud credentials, SSH keys, tokens) and whether a `network_transfer` command followed shortly after (for example `curl -d @~/.aws/credentials`). Secret read followed by an upload is the critical pattern.
- **`persistence`:** what the scheduled task, crontab entry, service or Run key launches, and whether the user asked for it (a developer may legitimately ask an agent to create a cron job).
- **`system_change`:** Defender exclusions, firewall changes, local admin additions or execution-policy bypass are rarely part of normal coding work.
- **Downloads:** `curl ... | sh`, `iwr ... | iex` or `certutil -urlcache` pulling scripts from unfamiliar hosts.
- `command_sample` is redacted, but positional secrets (e.g. `mysql -pS3cret`) are not recognised; handle the case data accordingly.

### Step 4: Check what the agent was working on

Look at the parent command line and the working directory of the agent session (repository path), and at network activity from the host around the same time:

```spl
| tstats summariesonly=t allow_old_summaries=t count min(_time) as firstTime max(_time) as lastTime values(Processes.parent_process) as parent_process from datamodel=Endpoint.Processes where Processes.dest="<dest_dd>" `hdsi_ai_agent_autonomous_action_detection_agent_scope` by Processes.user Processes.parent_process_name
| rename Processes.* as *
| convert ctime(firstTime) ctime(lastTime)
```

- A repository the user just cloned from an unknown source, or a file that contains instructions to the agent, points to prompt injection.

### Step 5: Check for related detections

```spl
| from datamodel:"Risk.All_Risk"
| search (risk_object="<user_dd>" OR risk_object="<dest_dd>") source="*HDSI*"
| stats sum(risk_score) as total_risk dc(source) as detections values(source) as sources by risk_object, risk_object_type
| sort - total_risk
```

Daily risk budget from this rule alone, per user and host (`risk_multiplier` 1.0):

| Agent behaviour that day | Events | User risk |
|---|---|---|
| Routine commands only | `agent_activity` | 10 |
| + package installs, `git push`, downloads, `rm -rf build` | `agent_activity` | up to 25 |
| + reads `.env` or another secret file | + `credential_access` | up to 50 |
| + `sudo` / `reg add` / firewall change | + `system_change` | up to 75 |
| + scheduled task / crontab / service | + `persistence` | up to 105 |

- `Threat - HDSI RBA AI User Risk Threshold Exceeded - Rule` (60) needs at least two distinct HDSI AI detections, so this rule alone never triggers it. `Threat - HDSI RBA AI User Critical Risk Threshold Exceeded - Rule` (90) is reachable by this rule alone only when one session combines secret access, a system change and persistence.
- High-signal categories count as `adversarial` in `Threat - HDSI RBA AI Multi-Vector Risk - Rule`; `agent_activity` counts as `local_tooling`.
- `Threat - HDSI RBA AI Privilege Escalation Correlation - Rule` correlates execution-phase AI risk after a privilege change on the same account.

### Step 6: Determine sanctioned status

```spl
| inputlookup ai_sanctioned_entities
| where enabled=1 AND (lower(entity)=lower("<user>") OR lower(entity)=lower("<dest>") OR match(allow_key, "^\*\|"))
| table entity_type, entity, provider, scope, expires, owner, reason, allow_key
```

- Approvals quiet `agent_activity` only. A sanctioned agent's high-signal events still fire, by design.

### Step 7: Make a determination

- **True Positive:** the agent read secrets and sent them out, created persistence or weakened host security without the user asking, or ran on a host or account where agents are not allowed.
- **Benign True Positive:** the user asked the agent to do it (for example create a cron job for a project), or the agent programme is sanctioned and the action was expected.
- **False Positive:** a probe or tool command that was mis-categorised. Add the shape to `..._housekeeping(2)` or exclude it in `..._customizations`.

## True Positive Indicators

- `credential_access` followed by `network_transfer` to an unfamiliar host in the same session.
- `persistence` or `system_change` that the user did not request, or that runs an unknown script.
- The agent session started in a freshly cloned or untrusted repository.
- The agent ran on a server, a build host with production credentials, or a non-developer's machine.
- Agent activity outside the user's normal hours, or from an account other than the user's own.

---

## False Positive Scenarios

Evidence from the 2026-10-09 validation on 4 production ES tenants (package README):

| Scenario | Likelihood | Mitigation |
|---|---|---|
| Developer using an agent for ordinary work (routine, installs, `git push`) | High where agents are adopted | Bounded to one 10 to 25 event per user and host per day; allow-list the sanctioned programme (`*|github copilot`, `engineering|anthropic`) |
| Agent reads `.env` as part of normal project setup | Medium | Stays high-signal by design (secret exposure path). Accept 25 to 50 per host per day, or exclude a specific host/category in `..._customizations` |
| CI runner whose agent legitimately runs `sudo` | Low | `..._filter` (`NOT Processes.dest IN ("ci-runner-*")`) or `..._customizations` (`search NOT (dest="ci-runner-01" risk_category="system_change")`) |
| Framework substrings in a checkout path (e.g. tests of the `langchain` project) | Low | None seen in 30 days on the 4 tenants; add `NOT Processes.parent_process IN (...)` in `..._filter` |
| Truncated command lines (`process` cut at about 400 characters) | Medium on affected tenants | GitHub Copilot's PowerShell wrapper filled the field on Tenant C, so the real command was cut and scored as routine. Fix truncation at the source |
| Start-up probes not yet in the probe list | Low | Add the anchored shape to `..._housekeeping(2)` |

## Response Actions

### If confirmed True Positive

1. **Contain:** stop the agent process and session on the host (EDR), and isolate the host if secrets were sent out or persistence was created.
2. **Notify:** the user, their manager and the application/platform owner of any credential touched.
3. **Investigate:** list every command the agent ran (Step 3), what it downloaded or uploaded, and where. Review the repository or prompt that drove the session for injected instructions.
4. **Remediate:** rotate any credential the agent read or sent (cloud keys, tokens, SSH keys, `.env` secrets); remove scheduled tasks, cron entries, services and Run keys it created; revert Defender, firewall and policy changes. Restrict agent permissions (sandbox mode, no auto-approve for shell commands).
5. **Document:** record the commands, credentials rotated and root cause in the case.

### If Benign True Positive

1. For ordinary agent work, add an `ai_sanctioned_entities` entry for the user, host, `bunit` group or organisation (quiets `agent_activity` only).
2. For an expected high-signal action on a specific host, exclude it in `..._customizations` with a narrow condition and a comment.
3. Close the related aggregator notable (if any) as benign.

## Tuning Guidance

### Reducing false positives

- Allow-list sanctioned agent programmes in `ai_sanctioned_entities` instead of editing the package.
- Add new probe shapes to `hdsi_ai_agent_autonomous_action_detection_housekeeping(2)`, anchored to the full command.
- Use `hdsi_ai_agent_autonomous_action_detection_customizations` for host/category exclusions and `hdsi_ai_agent_autonomous_action_detection_risk_score` (last pipe) to rescale `risk_score`.

### Adjusting thresholds

Derive `..._min_actions` from 30 days of agent-hours:

```spl
| tstats summariesonly=t allow_old_summaries=t count from datamodel=Endpoint.Processes where `hdsi_ai_agent_autonomous_action_detection_agent_scope` earliest=-30d by _time span=1h Processes.user Processes.dest Processes.parent_process_name Processes.process_name Processes.process
| rename Processes.* as *
| eval cmd_n=replace(lower(process),"\x5c","/"), process_name_lc=lower(process_name), parent_lc=lower(parent_process_name)
| where NOT ((process_name_lc=parent_lc AND NOT match(parent_lc,"^(powershell|pwsh|cmd|bash|sh|zsh|dash|fish|node|python[0-9.]*|pythonw|py)([.]exe)?\z")) OR `hdsi_ai_agent_autonomous_action_detection_housekeeping(cmd_n,process_name_lc)`)
| stats dc(cmd_n) as actions sum(count) as executions by _time user dest parent_process_name
| stats count as agent_hours p50(actions) as p50 p90(actions) as p90 max(actions) as max max(executions) as max_exec by parent_process_name
```

Keep 3 while agent use is rare (fewer than about 20 agent-hours a day). Where agents are part of daily engineering, set it to about the p50. If `max_exec` is much larger than `max`, command lines are being truncated.

### Adding allowlist entries

`ai_sanctioned_entities.csv` in `hdsi_ai_rba_common` (lower-case keys `<entity>|<provider>`; provider is the registry name or the agent label, e.g. `crewai`):

```
entity_type,entity,provider,scope,expires,owner,reason,enabled,allow_key
group,engineering,Anthropic,group,<YYYY-MM-DD>,<your_name>,<justification>,1,engineering|anthropic
group,*,GitHub Copilot,global,<YYYY-MM-DD>,<your_name>,<justification>,1,*|github copilot
```
