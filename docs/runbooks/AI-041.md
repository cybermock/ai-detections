# AI-041 - HDSI AI Time-of-Day Usage Pattern Anomaly

> **Detection ID:** AI-041
> **Package:** `hdsi_ai_time_of_day_usage_pattern_anomaly` v1.1.0 (deployment type: global)
> **Search name:** `Network - HDSI AI Time-of-Day Usage Pattern Anomaly - Rule`
> **Status:** Active. Risk-only (`action.notable = 0`). Notables come from the HDSI RBA AI aggregators.
> **Risk:** `user` only, dynamic 1-40 (base 15 x highest provider `severity_weight` x `risk_multiplier`). The literal fallback is 15.
> **MITRE ATT&CK:** T1078 - Valid Accounts; T1567 - Exfiltration Over Web Service
> **Data Model:** Web
> **Schedule:** `45 4 * * *` (daily at 04:45)
> **Lookback Window:** `-15d@d` to `@d` (yesterday is the evaluated day; the 14 days before it are the baseline)
> **Suppression:** 23 h per `user` (`82800s`)
> **AI kill-chain phase:** `exfiltration` (multi-vector aggregator: `usage_anomaly`)
> **Last Updated:** 2026-10-09

---

## Overview

This rule finds identified users who made **sustained, interactive AI web use at an hour of the day that is new for them**. Each user is compared with their own 14-day hourly histogram, not with a fixed business-hours clock. Night-shift staff who always work at 02:00 stay quiet. A day worker whose account suddenly drives 60 ChatGPT requests at 03:00 is flagged.

A new hour is not malicious by itself. It can point to a shared or compromised account, an unattended script driving a person's session, or data moved when nobody is watching. It is therefore a low score (15, at most 40) that adds context to a user who is already collecting risk. The rule creates no notable.

v1.1.0 fixes the original AI-041 defect. The old baseline was built with `stats ... by user hour day`, so an hour with no activity was never a data point, and the `datapoints>=7` requirement meant a never-used hour could never be scored. That is exactly the case the rule exists for. v1.0 also returned 0 rows on all four validation tenants. It dropped every row on SSE data (no `fillnull_value`), timed out on large Web models, included the evaluated day in its own baseline and mapped to the wrong MITRE technique (T1567.002, cloud storage).

## Detection Logic

### Plain English

1. One daily `tstats` over `Web` from `-15d@d` to `@d`, in 1-hour buckets by `user`, `url_domain` and `site`, with `fillnull_value="unknown"`. The inline `hdsi_ai_time_of_day_usage_pattern_anomaly_prefilter` limits the scan to exact AI web hostnames and SSE app names. That is what makes a multi-week hourly read affordable.
2. Drop placeholder users. Set `ai_domain = coalesce(url_domain, site)`, with `ai_input_type=app` when only `site` is set (SSE app names such as "ChatGPT").
3. Resolve providers with `ai_domains_filter`. Keep only `usage_type` values in `..._usage_types` (default `"web"`). IDE assistants and API traffic run unattended, at any hour.
4. Remove `..._background_hosts` (experiment flags, static and CDN assets, telemetry, sign-in), so an idle tab left open overnight does not create an active hour.
5. Look up the identity `bunit` and remove approved user, group or provider pairs with `ai_unsanctioned_filter(user,src,provider)`.
6. Split the window. Yesterday is the evaluated day, and every earlier day is the baseline. `baseline_days` is the number of days on which the user used AI web services at all.
7. Build a **zero-filled** hourly histogram. Each baseline hour also counts for the hours either side of it (plus or minus 1 hour). Mean and stdev are taken over **all** `baseline_days`, so a day without activity at that hour counts as 0.
8. Flag an hour of the evaluated day when all of these hold:
   - `baseline_days >= 5`;
   - the user made at least 20 foreground requests in that hour;
   - the user was active within an hour of that time on at most 1 baseline day (`usual_days`);
   - the z-score against the zero-filled baseline (stdev floored at 1) is at least 3.
9. Roll up to one row per user, look up `risk_multiplier`, and score: `risk_score = min(40, max(1, round(15 x severity_weight x risk_multiplier)))`.

### Key Fields

| Field | Description | Example Value |
|---|---|---|
| `user` | Risk object (user only, never an IP) | `jdoe@example.com` |
| `eval_day` | The evaluated day (yesterday) | `2026-10-08` |
| `anomalous_hours` | New hours, in the saved-search owner's time zone | `02:00, 03:00` |

## Triage Steps

> **Estimated triage time:** 10-15 minutes. This rule raises no notable. You normally reach it from an HDSI RBA AI aggregator notable or from a user's risk timeline.

Replace `<user>` with the risk object. For Step 3 set the time picker to the rule's window (`-15d@d` to `@d` relative to the risk event).

### Step 1: Validate the risk event

```spl
| from datamodel:"Risk.All_Risk"
| search source="Network - HDSI AI Time-of-Day Usage Pattern Anomaly - Rule" risk_object="<user>"
| table _time risk_object risk_score eval_day anomalous_hours anomalous_requests usual_days baseline_days usual_hours provider_list risk_message
| sort - _time
```

- The message gives the new hours, the request count, the providers, and the user's usual hours. Hours are in the search time zone (the saved-search owner's), not the user's local time.
- Repeated events on consecutive days usually mean a lasting schedule change (new shift, travel), not a one-off.

### Step 2: Identify the user

```spl
| inputlookup identity_lookup_expanded
| search identity="<user>"
| table identity first last email managedBy bunit category priority watchlist
```

- Check the user's role, location and manager. Look for a known reason for out-of-hours work: on-call, a deadline, travel or a time-zone change.

### Step 3: Review the hourly AI activity (baseline and evaluated day)

```spl
| tstats summariesonly=t allow_old_summaries=t fillnull_value="unknown" count
    from datamodel=Web
    where Web.user="<user>" (Web.url_domain=* OR Web.site=*) `hdsi_ai_time_of_day_usage_pattern_anomaly_prefilter`
    by Web.user Web.url_domain Web.site _time span=1h
| rename Web.* as *
| eval ai_input_type=if(isnull(nullif(url_domain,"unknown")),"app","host"), url_domain=coalesce(nullif(url_domain,"unknown"),nullif(site,"unknown")), ai_domain=lower(url_domain)
| `ai_domains_filter`
| where NOT match(ai_domain, `hdsi_ai_time_of_day_usage_pattern_anomaly_background_hosts`)
| eval day=strftime(_time,"%Y-%m-%d"), hour=strftime(_time,"%H")
| chart limit=0 sum(count) over day by hour
```

- The table is one row per day and one column per hour. The new hours should be empty in the baseline rows and dense in the evaluated day's row.
- Check whether the new-hour activity is a short burst or a long session, and whether it continued into the next morning.

### Step 4: Look at what happened in the new hour

Set the time picker to the anomalous hour or hours of `eval_day`:

```spl
| tstats summariesonly=t allow_old_summaries=t fillnull_value="unknown" count sum(Web.bytes_out) as bytes_out values(Web.action) as action values(Web.http_user_agent) as http_user_agent
    from datamodel=Web
    where Web.user="<user>" (Web.url_domain=* OR Web.site=*) `hdsi_ai_time_of_day_usage_pattern_anomaly_prefilter`
    by Web.src Web.url_domain Web.site
| rename Web.* as *
| eval url_domain=coalesce(nullif(url_domain,"unknown"),nullif(site,"unknown")), mb_out=round(bytes_out/1024/1024,2)
| table src url_domain action count mb_out http_user_agent
| sort - count
```

- Compare `src` and `http_user_agent` with the user's daytime activity. A new source address, a VPN or cloud egress address, or a non-browser user agent (script, CLI, automation library) points to someone or something other than the user.
- `mb_out` in megabytes in the middle of the night is the strongest escalation signal.

Optionally, check sign-ins around the same hour:

```spl
| tstats summariesonly=t allow_old_summaries=t count values(Authentication.app) as app values(Authentication.action) as action
    from datamodel=Authentication
    where Authentication.user="<user>"
    by Authentication.src Authentication.dest _time span=1h
| rename Authentication.* as *
| sort - _time
```

### Step 5: Check related detections and the user's total

```spl
| from datamodel:"Risk.All_Risk"
| search risk_object="*<bare user>*" source="* - HDSI *"
| stats count as risk_events sum(risk_score) as total_risk values(source) as detections min(_time) as firstTime max(_time) as lastTime by risk_object risk_object_type
| convert ctime(firstTime) ctime(lastTime)
| sort - total_risk
```

- Escalate when the same user also has upload, DLP, unmanaged-device, VPN/proxy-evasion or privilege-escalation risk.

### Step 6: Check sanctioned status

```spl
| inputlookup ai_sanctioned_entities
| eval k=lower(allow_key)
| where like(k, lower("<user>|%")) OR like(k, lower("<bunit>|%")) OR like(k, "*|%")
| table entity_type entity provider scope expires owner reason enabled allow_key
```

### Step 7: Make a determination

- **True Positive:** the account was used at a new hour by someone other than the user, or to move data out of hours. Signs: a new source, an unusual user agent, a large upload, or the user denies the activity.
- **Benign True Positive:** the user really did work at that hour (evening work, travel, a deadline). This was the most common outcome in validation.
- **False Positive:** the "new hour" is an artefact. Causes: a travel or time-zone shift, a short baseline because the Web acceleration summary range is short, or an idle tab hitting an interactive host that is missing from the background regex.

---

## True Positive Indicators

- The user does not recognise the activity, or was on leave or asleep (confirmed with the manager).
- Activity at the new hour comes from a different `src`, a VPN or cloud address, or a non-browser user agent.
- Large `bytes_out` to the AI service during the new hour.
- Other risk on the same user: data access spike, high-volume upload, unmanaged device, privileged account use.

---

## False Positive Scenarios

| Scenario | Likelihood | Mitigation |
|---|---|---|
| Evening or weekend use by a day worker. On Tenant A, most rows were ChatGPT or Gemini use late in the evening or after midnight by users with daytime usual hours | High | This is the intended signal, which is why the score is low. Close it as benign unless other risk is present |
| Travel or time-zone change (the whole pattern shifts for a few days) | Medium | Expect one row on the first day. Suppression is per day per user |
| Shift workers and on-call staff | Medium | Add them to `ai_sanctioned_entities`, or exclude them in `..._filter` (for example `NOT Web.user IN ("svc_*")`) |
| Shared or service accounts | Low | Exclude them in `hdsi_ai_time_of_day_usage_pattern_anomaly_filter` |
| Idle tabs or apps polling an interactive host | Low | Extend `..._background_hosts` with the host |

---

## Response Actions

### If confirmed True Positive

1. **Contain:** if account compromise is suspected, reset credentials, revoke sessions and tokens, and review MFA registrations. Block the AI provider for the account if data movement is suspected.
2. **Notify:** the user's manager and the incident response lead. Bring in the data governance owner if data was uploaded.
3. **Investigate:** review the provider's enterprise audit log where available (prompt and file history). Review DLP and CASB events for the new hour, and authentication logs for the source of the session.
4. **Remediate:** close the access path (stolen session, shared credentials, unattended automation using a person's account).
5. **Document:** record the hour, the source, the volume and the conclusion in the case.

### If Benign True Positive

1. Record the reason (travel, deadline, on-call) in the case and close it.
2. For a lasting pattern (a permanent shift change), no action is needed: the new hours become part of the user's baseline within days. For roles that work at any hour, add an `ai_sanctioned_entities` entry or a `..._filter` exclusion.

## Tuning Guidance

### Reducing false positives

- Set `..._min_requests` from the tenant's own distribution. 20 suits verbose URL logs. SSE connection logs record about one event per session, so 20 never fires there. Use about 3.
- Raise `..._min_baseline_days` and widen `dispatch.earliest_time` together (for example `-29d@d` with 10 days) where the Web summary range allows.
- Regenerate `..._prefilter` when web rows are added to the common lookups (SPL in the package README).

### Adjusting thresholds

Requests per active user-hour over 7 days, to set `..._min_requests` near p90 to p95:

```spl
| tstats summariesonly=t allow_old_summaries=t fillnull_value="unknown" count from datamodel=Web
    where `hdsi_ai_time_of_day_usage_pattern_anomaly_prefilter` Web.user!="unknown" by Web.user Web.url_domain Web.site _time span=1h
| rename Web.* as *
| eval ai_domain=lower(coalesce(nullif(url_domain,"unknown"),nullif(site,"unknown"))), ai_input_type=if(isnull(nullif(url_domain,"unknown")),"app","host")
| `ai_domains_filter`
| search usage_type IN (`hdsi_ai_time_of_day_usage_pattern_anomaly_usage_types`)
| where NOT match(ai_domain, `hdsi_ai_time_of_day_usage_pattern_anomaly_background_hosts`)
| stats sum(count) as req by user _time
| eval day=strftime(_time,"%F") | eventstats dc(day) as active_days by user
| stats count as user_hours dc(user) as users dc(eval(if(active_days>=5,user,null()))) as users_5_days perc50(req) as p50 perc90(req) as p90 perc98(req) as p98 perc99(req) as p99
```

Web acceleration summary range (the effective baseline length):

```spl
| rest /services/admin/summarization by_tstats=t splunk_server=local count=0
| search summary.id=*Web*
| eval summary_days=round('summary.time_range'/86400,0)
| table summary.id summary.complete summary_days
```
