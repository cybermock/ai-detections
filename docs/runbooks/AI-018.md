# AI-018 - Multiple AI Services In Single Session

> **Detection ID:** AI-018 (package `hdsi_ai_multiple_services_in_single_session`, `detection_id=hdsi_ai_multiple_services_in_single_session`)
> **Search name:** `Network - HDSI AI Multiple Services In Single Session - Rule`
> **Status:** Active, version 1.1.0, `deployment_type: global`, ships with `enable_alerting: false`
> **Output:** Risk only (`action.notable = 0`). Notables come from the HDSI RBA AI aggregators.
> **Risk Score:** computed `risk_score = max(1, min(40, round(5 x provider_count x risk_multiplier)))`, applied to every emitted risk object (static `_risk` fallback: user 20, system 20). 4 providers = 20, 6 = 30. The multiplier applies only to an attributed user
> **MITRE ATT&CK:** T1588.007 - Obtain Capabilities: Artificial Intelligence (Resource Development)
> **Data Model:** `Web` (user attributed) and/or `Network_Resolution` (host attributed)
> **Schedule:** `7 * * * *` (hourly at minute 7)
> **Lookback Window:** `-65m@m` to `-5m@m` (the 60-minute "session")
> **Suppression:** `user,src` for 86400s (one risk event per entity per day)
> **Kill Chain Phase:** `recon`
> **Last Updated:** 2026-10-09

---

## Overview

This detection finds one user or host actively using several distinct AI providers (default 4) within one hour, for example ChatGPT, Claude, Gemini and Perplexity in the same hour. Breadth like this is typical of "prompt shopping": the same content, often internal data, is pasted into several services to compare answers. That spreads the data across more providers than any single-provider rule shows.

Evidence comes from Web proxy or SSE logs (user attributed) and, where no proxy sees the traffic, from DNS (host attributed). Background traffic, IDE assistants, resolvers and forwarders, shared egress addresses and roaming home-network DNS are removed so that the risk lands on one real person or one real host. The rule writes risk on `user` and/or `src` and never creates a notable on its own.

## Detection Logic

### Plain English

1. **Web branch.** `tstats` over `Web` with the inline AI pre-filter `hdsi_ai_multiple_services_in_single_session_web_prefilter`, `Web.user!="unknown"` and the tenant `..._filter`, split by `user`, `src`, `url_domain` and `site`. `ai_domain` is `url_domain`, or `site` when there is no `url_domain` (SSE and App-ID products that log only an app name, resolved through `ai_provider_apps`). Inbound server logs (WAF, load balancer, IIS) have no user and drop out.
2. **DNS branch (`append`).** `tstats` over `Network_Resolution` with the inline `..._dns_prefilter`, placeholder and loopback sources removed, and `..._dns_filter`, split by `src`, `query`, `message_type` and `vendor_product`. Query and response logs are not double counted. Roaming DNS-security clients on home-router ranges (`..._unreliable_dns_src`) are dropped.
3. **Provider resolution.** `ai_domains_filter` keeps enabled providers only. IDE assistants, tenant-bound Microsoft 365 / Security Copilot (`..._excluded_providers`), background and site rows (`..._excluded_traffic`) and telemetry, CDN and Copilot SSO names (`..._background_names`) never count.
4. **Shared-source guards.** DNS clients that resolved at least 3,000 distinct names in the hour are resolvers or NAT, and their DNS evidence is dropped. A Web address with more than 1 distinct (normalised) user in the hour is shared (NAT, SSE egress, VDI, terminal server): it never receives `src` risk and never passes DNS evidence to a user.
5. **Attribution.** A DNS-only row inherits a user only when its address is not shared and exactly one user has AI Web evidence on it in the hour. `DOMAIN\JDoe`, `jdoe@example.com` and `jdoe` are aggregated as one person; the emitted `user` keeps its original form.
6. **Evidence gate.** A provider counts after at least 3 requests from the entity in the hour.
7. **Allowlist.** `ai_unsanctioned_filter(user,src,provider)` runs per provider before counting, so an approved provider simply stops counting.
8. **Threshold.** At least 4 distinct providers per entity.
9. **Score.** `ai_risk_multiplier` for attributed users, then `risk_score = max(1, min(40, round(5 x provider_count x risk_multiplier)))`. `src` is emitted only when the entity used exactly one, unshared address. Rows with neither a user nor an emitted `src` are dropped, so no "unknown" object is scored.
10. `hdsi_ai_multiple_services_in_single_session_customizations`, then `..._risk_score` as the last pipe.

## Triage Steps

> **Estimated triage time:** 10-15 minutes. Replace `$user$` and `$src$` with the values from the risk event (or `$drill_user$` / `$drill_src$`, which already have backslashes replaced by `*`). Set the time picker to cover the risk event hour, or 24 hours for context.

### Step 1: Validate the risk event

```spl
| from datamodel:"Risk.All_Risk"
| search source="Network - HDSI AI Multiple Services In Single Session - Rule" (risk_object="$user$" OR risk_object="$src$")
| table _time, risk_object, risk_object_type, risk_score, risk_message, provider_list, evidence_type, src_display
| sort - _time
```

- Is the risk on a user (Web evidence, or DNS inherited from a single Web user) or on a host only (DNS)?
- Which providers were counted, and is the fourth one a real assistant (Perplexity, DeepL, QuillBot, Bedrock, a model hub) or something that looks incidental?

### Step 2: Identify the user or the host

```spl
| inputlookup identity_lookup_expanded
| search identity="$user$"
| table identity, first, last, email, managedBy, category, priority, bunit
```

```spl
| inputlookup asset_lookup_by_str
| search ip="$src$" OR dns="$src$" OR nt_host="$src$"
| table ip, dns, nt_host, owner, bunit, category, priority
```

- Is the person in an AI engineering, research or data-science role where comparing models is the job?
- For a host-only row, the address is a DNS client. Resolve it to a device and user for that hour (Step 4) before acting.

### Step 3: Review the AI web and DNS evidence

The rule's "View AI web activity" drilldown (by user, or by host when there is no user):

```spl
| tstats summariesonly=t allow_old_summaries=t fillnull_value="unknown" count sum(Web.bytes_out) as bytes_out min(_time) as firstTime max(_time) as lastTime values(Web.action) as action values(sourcetype) as orig_sourcetype from datamodel=Web where (Web.url_domain=* OR Web.site=*) `hdsi_ai_multiple_services_in_single_session_web_prefilter` (Web.user="$user$" OR Web.src="$src$") by Web.user Web.src Web.url_domain Web.site
| rename Web.* as *
| eval url_domain=coalesce(nullif(url_domain,"unknown"),site), ai_domain=lower(url_domain), ai_input_type=if(site=url_domain,"app","host")
| `ai_domains_filter`
| eval mb_out=round(bytes_out/1024/1024,2)
| convert ctime(firstTime) ctime(lastTime)
| table firstTime, lastTime, user, src, provider, usage_type, ai_traffic_class, url_domain, count, mb_out, action, orig_sourcetype
| sort provider - count
```

The rule's "View AI DNS names resolved" drilldown:

```spl
| tstats summariesonly=t allow_old_summaries=t fillnull_value="unknown" count min(_time) as firstTime max(_time) as lastTime values(DNS.message_type) as message_type values(DNS.vendor_product) as vendor_product from datamodel=Network_Resolution where DNS.src="$src$" `hdsi_ai_multiple_services_in_single_session_dns_prefilter` by DNS.src DNS.query
| rename DNS.* as *
| eval ai_domain=query, ai_input_type="dns"
| `ai_domains_filter`
| convert ctime(firstTime) ctime(lastTime)
| table firstTime, lastTime, src, provider, usage_type, ai_traffic_class, ai_match, query, message_type, vendor_product, count
| sort provider - count
```

- Look at `mb_out` per provider: uploads to several providers in the same hour point at the same content being pasted or attached into each.
- Interactive names (`chatgpt.com`, `claude.ai`, `gemini.google.com`) mean use. Marketing or pricing pages that crossed 3 requests are weak evidence.
- `action=blocked` on most rows means the proxy stopped the traffic; the risk still shows intent.

### Step 4: For host-only rows, find the person behind the address

```spl
| tstats summariesonly=t allow_old_summaries=t count min(_time) as firstTime max(_time) as lastTime from datamodel=Authentication where Authentication.src="$src$" Authentication.action="success" by Authentication.user Authentication.dest Authentication.app
| rename Authentication.* as *
| convert ctime(firstTime) ctime(lastTime)
| sort - count
```

- Use the risk event hour. DHCP, VPN or EDR logs give the most reliable host-to-user mapping.
- Roaming home-router ranges (`192.168.0.0/16`, `10.0.0.0/24` from Umbrella / Cloud Security / Secure Access) are already excluded, but other pooled addresses can still change hands.

### Step 5: Check related AI risk

```spl
| from datamodel:"Risk.All_Risk"
| search (risk_object="$user$" OR risk_object="$src$") source="* - HDSI AI * - Rule"
| stats sum(risk_score) as total_risk dc(source) as detections values(source) as sources values(ai_kill_chain_phase) as phases by risk_object, risk_object_type
| sort - total_risk
```

```spl
`notable`
| search search_name="Threat - HDSI RBA AI *" ("$user$" OR "$src$")
| table _time, search_name, rule_title, urgency, status_label, owner
```

- Breadth alone is low risk (20 to 40). It matters when the same user also has upload, DLP or personal-email risk on the same day.
- The user threshold aggregators raise a medium notable at 60 points from at least 2 detections and a high notable at 90.

### Step 6: Determine sanctioned status

```spl
| inputlookup ai_sanctioned_entities
| where enabled=1
| table entity_type, entity, provider, scope, expires, owner, reason, allow_key
| sort entity_type, entity
```

- Is one of the counted providers licensed for everyone (`*|<provider>`)? Then it should not have counted. Check the expiry.
- Is the user's `bunit` an approved evaluation group (`<bunit>|*`)?

### Step 7: Make a determination

- **True Positive:** an unsanctioned user pasting or uploading the same work content into several consumer AI services, especially with `mb_out` on more than one provider or alongside upload or DLP risk.
- **Benign True Positive:** AI engineering or research staff comparing models, or a power user of mainstream assistants that are approved. Allowlist the group or the licensed provider.
- **False Positive:** a shared or pooled address that the guards did not catch (forwarder below 3,000 names an hour, VDI or NAT not seen in Web), or background names that crossed the request gate. Exclude the address in `..._dns_filter` or `..._filter`, or report the name for the background list.

---

## True Positive Indicators

- Upload volume (`mb_out`) to two or more providers within the hour.
- Consumer or lesser-known providers (QuillBot, DeepL, Perplexity, regional chatbots) alongside the mainstream ones, with no approved use case.
- The user handles sensitive data (finance, legal, HR, source code) and has no approved AI evaluation role.
- Same-day risk from `Network - HDSI AI High Volume Upload To AI Service - Rule`, `Network - HDSI AI Personal Email To AI Service Upload Correlation - Rule` or a DLP rule.
- The entity repeats the pattern on several days.

---

## False Positive Scenarios

| Scenario | Likelihood | Mitigation |
|---|---|---|
| Power users of ChatGPT + Claude + Gemini plus one more assistant | Medium | Approve licensed providers organisation-wide (`*\|<provider>`) or add them to `..._excluded_providers`; then consider lowering the threshold |
| AI engineering and research staff comparing models and SDKs (Bedrock, Vertex AI, model hubs) | Medium | Group row `<bunit>\|*` in `ai_sanctioned_entities` |
| DNS forwarder or NAT address below the 3,000-names guard | Low | `NOT DNS.src IN (...)` in `..._dns_filter` |
| Pooled DHCP, Wi-Fi or VPN address used by two people in one hour | Low | Confirm with Step 4; exclude the pool in `..._dns_filter` if it recurs |
| Marketing or pricing pages of a provider crossing 3 requests | Low | Raise `..._min_requests`, or add the name to `..._background_names` |

---

## Response Actions

### If confirmed True Positive

1. **Contain:** remind the user of the AI use policy and point them at the approved assistant. Where the proxy allows, block or warn on the unsanctioned providers for that user.
2. **Notify:** the user's manager and the data owner if sensitive content is suspected.
3. **Investigate:** review uploads per provider (Step 3), and check for DLP, high-volume upload and personal-email risk for the same day.
4. **Remediate:** consolidate on approved providers, and add the unapproved ones to the proxy or SSE policy.
5. **Document:** record the providers, the volume and the decision in the case.

### If Benign True Positive

1. Add the user, group or licensed provider to `ai_sanctioned_entities` with an expiry.
2. Record the business justification in `reason`.
3. Close any related aggregator notable as benign.

## Tuning Guidance

### Reducing false positives

| Macro | Ships as | Use |
|---|---|---|
| `hdsi_ai_multiple_services_in_single_session_filter` | `()` | Inline exclusions for both Web `tstats`, e.g. `NOT Web.user IN ("svc_*")` or `NOT sourcetype IN ("aws:waf")` |
| `..._dns_filter` | `()` | Inline exclusions for both DNS `tstats`, e.g. resolver or NAT addresses below the guard |
| `..._excluded_providers` | GitHub Copilot, Cursor, Windsurf, Tabnine, Sourcegraph, Microsoft 365 Copilot, Microsoft Security Copilot | Providers that never count. `"__none__"` counts all |
| `..._excluded_traffic` | background and site rows, `usage_type="ide"` | Registry rows that are not evidence of use |
| `..._background_names` | Copilot SSO, Perplexity Comet hosts, telemetry, sentry, collector, segment, CDN labels | Names that never count |
| `..._unreliable_dns_src` | Umbrella / Cloud Security / Secure Access in `192.168.0.0/16` or `10.0.0.0/24` | `false()` keeps everything |
| `..._web_prefilter`, `..._dns_prefilter` | 123 name terms and 86 app names | Regenerate when `ai_provider_domains` or `ai_provider_apps` change (SPL in the package README) |
| `..._customizations` / `..._risk_score` | `search *` | Post-aggregation hook / last pipe |

### Adjusting thresholds

Measure the hourly provider distribution per host with the rule's own exclusions over 24 hours:

```spl
| tstats summariesonly=t allow_old_summaries=t fillnull_value="unknown" count from datamodel=Network_Resolution where `hdsi_ai_multiple_services_in_single_session_dns_prefilter` NOT DNS.src IN ("unknown","-","0.0.0.0","127.0.0.1","::1") by DNS.src DNS.query DNS.message_type DNS.vendor_product _time span=1h
| rename DNS.* as *
| stats max(count) as count values(vendor_product) as vendor_product by src query _time
| where NOT (`hdsi_ai_multiple_services_in_single_session_unreliable_dns_src`)
| eval ai_domain=query, ai_input_type="dns"
| `ai_domains_filter`
| where NOT provider IN (`hdsi_ai_multiple_services_in_single_session_excluded_providers`) AND NOT (`hdsi_ai_multiple_services_in_single_session_excluded_traffic`) AND NOT (`hdsi_ai_multiple_services_in_single_session_background_names`)
| stats sum(count) as requests by src provider _time
| where requests>=`hdsi_ai_multiple_services_in_single_session_min_requests`
| stats dc(provider) as providers by src _time
| stats count as host_hours dc(src) as hosts by providers
| sort providers
```

Pick the smallest `..._min_providers` that gives a reviewable number of entities a day. With 24-hour suppression, entities a day is about risk events a day.

### Adding allowlist entries

```
entity_type,entity,provider,scope,expires,owner,reason,enabled,allow_key
group,*,OpenAI,global,2099-12-31,security,chatgpt_enterprise,1,*|openai
group,ai-research,*,group,2027-03-31,security,ai_evaluation_team,1,ai-research|*
user,jdoe@example.com,*,global,2027-03-31,security,ai_evaluation_team,1,jdoe@example.com|*
```

User keys match the emitted `user` string (lowercased). If a person appears as both `DOMAIN\jdoe` and `jdoe@example.com`, add a row for each form, or use a group row.

## Validation (2026-10-09)

Read-only live tests on 4 production ES tenants, over the exact scheduled window for 4-8 weekday business hours plus a 24-hour hourly replay. The search and all 3 drilldowns parse on all four; no run returned FATAL or ERROR.

| Tenant | Evidence | Scheduled hours | 24h replay | Notes |
|---|---|---|---|---|
| A | Firewall URL and enterprise-browser Web with users; about 1.1B DNS events a day, mostly from resolvers | 1 row in 8 hours (DNS host, 4 providers, score 20) | not replayed (Web guard volume) | Every multi-provider DNS candidate was a forwarder or NAT (6,000-63,000 names an hour), dropped by the guard |
| B | Mostly inbound Web plus a small SSE proxy; about 53M DNS events a day from a roaming DNS-security service | 1 row in 4 hours (DNS host, score 20) | 11 hosts at 4 providers before the roaming exclusion | The roaming exclusion removed 314 of 395 AI-resolving sources in one hour |
| C | SSE with app names and the public egress IP as `src`; mostly forwarder DNS | 0 | 0 | 58 addresses had several Web users (up to 546); the guard keeps them out of `src` risk |
| D | Inbound IIS only; little AI DNS | 0 | 0 | Expected silence |

The final version (roaming exclusion, identity normalisation, regenerated pre-filters) returned 0 rows on all four tenants over a 4-hour window; with the threshold lowered to 2, Tenant B returned 17 host rows, which shows the pipeline works. Expected volume: Tenant A about 0-2 a day; Tenant B fewer than the 11 hosts a day measured before the roaming exclusion (most of those were home-router addresses); C and D none.
