# AI-040 - User Peer Group AI Usage Anomaly

> **Detection ID:** AI-040
> **Package:** `hdsi_ai_user_peer_group_usage_anomaly` v1.1.0 (`deployment_type: global`, ships `enable_alerting: false`)
> **Search name:** `Identity - HDSI AI User Peer Group Usage Anomaly - Rule`
> **Status:** Active. Risk-only (`action.notable = 0`). Notables come from the HDSI RBA AI aggregators
> **Risk object:** `user` only (the `DOMAIN\user` form when one was seen that day, else the first form; `user_key` is the bare account name). No system risk
> **Risk score:** dynamic, `min(60, max(15, round(base x risk_multiplier)))`, base 20 (requests outlier), 30 (bytes outlier), 40 (both). Literal fallback 20
> **MITRE ATT&CK:** T1567 Exfiltration Over Web Service (bytes outliers); T1588.007 Obtain Capabilities: Artificial Intelligence (requests-only outliers)
> **Data Model:** `Network_Traffic` (NGFW App-ID with User-ID) and/or `Web` (proxy/SSE with users)
> **Schedule:** `30 4 * * *` (daily at 04:30)
> **Lookback Window:** `-1d@d` to `@d` (yesterday)
> **Suppression:** 7 days per `user` (`604800s`)
> **Kill Chain Phase:** `exfiltration` (bytes outlier) or `collection` (requests-only outlier)
> **Last Updated:** 2026-10-09

---

## Overview

This daily detection finds users whose AI usage yesterday was **far above that of their peers**. It compares each person's AI requests and AI upload volume (`bytes_out`) with the other AI users of the same identity business unit (`bunit`). Users whose `bunit` is unknown or has fewer than 10 AI users are compared with each other in one residual group per data source (`org-wide, no qualifying bunit`).

A user is reported only when the value is a robust statistical outlier (log-scale median/MAD), at least 10 times the peer median, **and** above an absolute floor (2,500 requests or 100 MB a day). Heavy AI use far beyond colleagues is a useful insider-risk and data-exposure signal, but in validation most findings were power users and developers using API and agentic coding clients, so this is context for RBA, not an incident on its own. The rule writes risk on the user and never raises a notable.

In practice, where identities have no meaningful `bunit`, almost everyone falls into the residual group and the rule behaves as an absolute daily-volume threshold ranked by peer z-score (see False Positive Scenarios).

## Detection Logic

### Plain English

1. **Collect.** A `tstats` over `Network_Traffic` reads only AI App-IDs (`..._nt_scope`), and an appended `tstats` over `Web` reads only AI hosts and SSE app names (`..._web_scope`), per user, for yesterday. Both lists are literal macros generated from the common lookups. In `Web`, `ai_domain` is `url_domain`, or `site` when `url_domain` is empty.
2. **Resolve** (`..._resolve`). Drops unattributed users (empty, `unknown`, `-`, IP addresses, machine accounts ending in `$`) and service accounts (`..._service_accounts` regex), resolves the provider with `ai_domains_filter`, drops background hosts (telemetry, auth, CDN, extension streams) and organisation-wide sanctioned providers, and sums requests and `bytes_out` per person (`user_key`) and data source. `DOMAIN\user` and `user@domain` rows of one person count once.
3. **Peer statistics** (`..._peer_stats`). Peer group = the identity `bunit` when it has at least `..._min_peer_size` (10) AI users in that source that day; everyone else forms the residual group. Robust z = `0.6745 x (log10(value+1) - median) / MAD`, MAD floored at 0.1, for requests (`rz_requests`) and bytes (`rz_bytes`, null where the source logs no bytes).
4. **Decision.** Outlier when the group has 10+ users and either requests >= 2,500, >= 10x the peer median and `rz_requests` >= 3.5, or MB out >= 100, >= 10x the peer median and `rz_bytes` >= 3.5.
5. **Approvals.** `ai_unsanctioned_filter` runs on `user` and on the bare `user_key`, before the per-person dedup. A person seen in both sources is then reported once, on the more extreme row.
6. **Scoring.** Base 20/30/40 x `risk_multiplier` (identity `bunit` sensitivity, x1.25 privileged, cap 2.0), between 15 and 60.

## Triage Steps

> **Estimated triage time:** 10-20 minutes

Replace `$user_key$` with the finding's `user_key` (bare account name). The searches filter on `*<user_key>` / `<user_key>@*` and then on the computed key, so `DOMAIN\user` findings work without putting a backslash inside a quoted value. Set the time picker to the evaluated day unless noted.

### Step 1: Validate the risk event

```spl
| from datamodel:"Risk.All_Risk"
| search source="*HDSI AI*" (risk_object="*$user_key$" OR risk_object="$user_key$@*")
| eval user=risk_object
| `hdsi_ai_user_peer_group_usage_anomaly_user_key`
| search user_key="$user_key$"
| table _time, source, risk_score, risk_object, risk_object_type, risk_message
| sort - _time
```

Set the time picker to 7 days. This is drilldown 1: it shows this finding and every other HDSI AI risk event for the person.

- Read `outlier_reason`, the counts against the peer median, and the peer group.
- `org-wide, no qualifying bunit` means the comparison is with the whole residual population, not with colleagues.

### Step 2: Review the AI traffic behind the finding

NGFW App-ID (drilldown 3):

```spl
| tstats summariesonly=t allow_old_summaries=t count sum(All_Traffic.bytes_out) as bytes_out min(_time) as firstTime max(_time) as lastTime values(All_Traffic.src) as src values(All_Traffic.dest) as dest values(All_Traffic.action) as action
    from datamodel=Network_Traffic
    where (All_Traffic.user="*$user_key$" OR All_Traffic.user="$user_key$@*") `hdsi_ai_user_peer_group_usage_anomaly_nt_scope`
    by All_Traffic.user All_Traffic.app
| rename All_Traffic.* as *
| `hdsi_ai_user_peer_group_usage_anomaly_user_key`
| search user_key="$user_key$"
| eval ai_domain=app, ai_input_type="app"
| `ai_domains_filter`
| eval mb_out=round(bytes_out/1048576,2)
| convert ctime(firstTime) ctime(lastTime)
| table firstTime, lastTime, user, src, dest, app, provider, action, count, mb_out
| sort - count
```

Web/SSE (drilldown 2). `url_domain` falls back to `site` for SSE app names:

```spl
| tstats summariesonly=t allow_old_summaries=t fillnull_value="unknown" count sum(Web.bytes_out) as bytes_out min(_time) as firstTime max(_time) as lastTime values(Web.src) as src values(Web.action) as action
    from datamodel=Web
    where (Web.user="*$user_key$" OR Web.user="$user_key$@*") `hdsi_ai_user_peer_group_usage_anomaly_web_scope`
    by Web.user Web.url_domain Web.site
| rename Web.* as *
| `hdsi_ai_user_peer_group_usage_anomaly_user_key`
| search user_key="$user_key$"
| eval ai_input_type=if(url_domain="unknown","app","host"), url_domain=coalesce(nullif(url_domain,"unknown"),site), ai_domain=lower(url_domain)
| `ai_domains_filter`
| eval mb_out=round(tonumber(bytes_out)/1048576,2)
| convert ctime(firstTime) ctime(lastTime)
| table firstTime, lastTime, user, src, provider, url_domain, site, action, count, mb_out
| sort - count
```

The leading-wildcard pre-filter makes these take 1-2 minutes on a large tenant.

- Which App-ID or host carried the volume? `anthropic-api-base`, `openai-api` and similar API App-IDs from a developer workstation usually mean an agentic coding client (such as Claude Code) that resends the working context on every turn. Chat upload App-IDs mean files or pastes into a chat service.
- Is the provider sanctioned for the organisation?

### Step 3: Is this a one-day spike or a steady power user?

```spl
| tstats summariesonly=t allow_old_summaries=t count sum(All_Traffic.bytes_out) as bytes_out
    from datamodel=Network_Traffic
    where (All_Traffic.user="*$user_key$" OR All_Traffic.user="$user_key$@*") `hdsi_ai_user_peer_group_usage_anomaly_nt_scope` earliest=-14d@d latest=@d
    by _time span=1d All_Traffic.user All_Traffic.app
| rename All_Traffic.* as *
| `hdsi_ai_user_peer_group_usage_anomaly_user_key`
| search user_key="$user_key$"
| eval mb_out=bytes_out/1048576
| timechart span=1d sum(count) as sessions sum(mb_out) as mb_out
```

- Every day near the same level: a steady heavy user (role or tooling). Review whether to approve the person or the provider.
- One day far above the user's own normal: treat as a spike and cross-check AI-017 (Usage Volume Anomaly), which compares the user with their own history.

### Step 4: Identify the user

```spl
| inputlookup identity_lookup_expanded
| search identity="$user_key$" OR email="$user_key$@*"
| table identity, first, last, email, bunit, category, priority, managedBy
```

- Is the user a developer, data scientist or another AI-heavy role? Is the account actually a service or automation account that the naming regex missed?

### Step 5: Check related AI risk and sanctioned status

```spl
| inputlookup ai_sanctioned_entities
| search enabled=1 (entity="$user_key$" OR entity="*")
| table entity_type, entity, provider, scope, expires, owner, reason, allow_key
```

- Approvals must use the bare `user_key` (`jsmith|anthropic` or `jsmith|*`). An entry with the full `DOMAIN\user` only matches on days when that form is the finding's `user`.
- In Step 1, look for upload, DLP, data-access or personal-account detections for the same person; they raise the priority. The user aggregators raise notables at 60 (AI-RISK-001) and 90 (AI-RISK-002) rolling 24-hour AI risk from at least two distinct detections.

### Step 6: Make a determination

- **True Positive:** a person (not a service account) sent an unusual volume to an unsanctioned AI service, with no role reason, especially with co-occurring data-exposure detections.
- **Benign True Positive:** a developer or AI-heavy role using an agentic or API client, or heavy use of an approved assistant. Approve the person, the `bunit` or the provider.
- **False Positive:** a service or automation account not matched by the naming regex, or ambient App-ID traffic attributed to AI (for example a large Google upload classified as Gemini).

---

## True Positive Indicators

- `outlier_reason` includes `bytes_out`, with hundreds of MB to a chat upload App-ID or chat host rather than an API client.
- A one-day spike (Step 3) rather than a steady pattern.
- The provider is unsanctioned or consumer-grade.
- Co-occurring data-access, upload, DLP or personal-account detections.
- The user's role gives no reason for heavy AI use.

## False Positive Scenarios

Evidence from read-only validation on 4 production ES tenants (Tenant A-D), 2026-10-09 (evaluated day 2026-10-08).

| Scenario | Likelihood | Mitigation |
|---|---|---|
| Developers using API and agentic coding clients: 14 of 16 bytes-only findings on Tenant A involved Anthropic App-IDs (105-2,300 sessions, 143-752 MB); `anthropic-api-base` alone had 92 users that day, 15 over 100 MB | High where developers use agents | Approve the people or units (`<user_key>|anthropic`, `<bunit>|*`), add the provider to `..._sanctioned_providers` if it is approved organisation-wide, or accept as intended risk |
| Ambient App-IDs: the NGFW `google-gemini` App-ID was seen for about 75,000 users a day on Tenant A; one finding had 91 Gemini sessions and 244 MB | Medium | Add `"Google Gemini"` to `..._sanctioned_providers` if it is the sanctioned enterprise assistant |
| No meaningful `bunit`: on Tenant A 30 of 33 findings were scored against a residual group, so the floors decide, not the peer comparison | High | Expected until identities carry a coarse `bunit`; set the floors with the Threshold SPL (raising `..._min_mb` to 250 would have halved the bytes-only findings that day) |
| Power users of mainstream assistants (13 requests-only findings with 2,700-12,600 rows/sessions) | Medium | They score the lowest base (20, `collection`); raise `..._min_requests` if they are too many |
| Service accounts not named by the regex | Low | Add them to `..._filter` / `..._web_filter`, or adapt `..._service_accounts` |
| Two different people with the same bare account name in different domains merged on `user_key` | Low | Handle in `..._customizations` if the organisation has such collisions |

## Response Actions

### If confirmed True Positive

1. **Contain:** restrict the user's access to the provider (proxy/SSE or firewall policy) while investigating; revoke API keys the user created for an unsanctioned provider.
2. **Notify:** the user's manager and the data protection team according to policy.
3. **Investigate:** determine what was sent (SSE/DLP content logs, endpoint telemetry, repository access for coding agents) and for how long (Step 3 over 30 days).
4. **Remediate:** move the use to an approved provider or enterprise tenant; review source-code exposure if an unsanctioned coding agent was used.
5. **Document:** record the peer comparison, provider, volume and disposition.

### If Benign True Positive

1. Approve the person (`<user_key>|<provider>` or `<user_key>|*`), the unit (`<bunit>|<provider>`) or the provider (`..._sanctioned_providers`, or `*|<provider>` for single-provider findings) with an expiry and reason.
2. The 7-day suppression already limits repeats; approval removes the person from the statistics.

## Tuning Guidance

### Reducing false positives

- Set `hdsi_ai_user_peer_group_usage_anomaly_sanctioned_providers` to the organisation's approved assistants (quoted provider names, e.g. `"Google Gemini","Anthropic"`).
- Adapt `..._service_accounts` to the naming standard (`"^$"` keeps every account).
- Exclude inbound Web sourcetypes in `..._web_filter` (`NOT sourcetype IN ("aws:elb:accesslogs","aws:waf")`): on a tenant whose Web model is mostly inbound load-balancer and WAF logs, the Web pre-filter took 4-5 minutes and found no user.
- Add tenant `bunit` values or segments to `ai_department_sensitivity` (common package) to make `risk_multiplier` escalate sensitive units; it was 1.00 on every finding in validation.
- Regenerate `..._domains` and `..._apps` after the common lookups gain domains or app names (README has the SPL).

### Adjusting thresholds

Run the README Threshold SPL for each of the last 7 days. Per data source it returns user count, peer groups, request and MB medians, p99 and maximum, and the number of outliers at the shipped floors. Keep `..._min_requests` and `..._min_mb` above the p99 of a normal day, and aim for a handful of users a day.

### Adding allowlist entries

```
entity_type,entity,provider,scope,expires,owner,reason,enabled,allow_key
user,jsmith,Anthropic,provider,2027-03-31,<your_name>,<justification>,1,jsmith|anthropic
```

Use the bare `user_key`, lowercased.

## Data Requirements

| Requirement | Details |
|---|---|
| Data Model | `Network_Traffic` and/or `Web` (at least one, with a populated `user` on egress traffic) |
| Required Fields | Network_Traffic: `user`, `app`, `bytes_out`, `src`. Web: `user`, `url_domain` and/or `site`, `bytes_out`, `src` |

| Acceleration | Required (`summariesonly=t`, no raw fallback) |
| Lookups | Common package `hdsi_ai_rba_common`: `ai_provider_domains`, `ai_provider_apps`, `ai_sanctioned_entities`, `ai_department_sensitivity`; ES `identity_lookup_expanded` (`bunit`, looked up by user then bare name) |

Validation (2026-10-09, 4 production ES tenants): the search and its 3 drilldowns parse on all tenants. Tenant A returned 33 rows for 2026-10-08 in about 5 minutes (30 NGFW, 3 URL-log; 13 requests-only, 16 bytes-only, 4 both; scores 20/30/40; `risk_multiplier` 1.00 on all). Tenants B, C and D returned 0 rows (no user-attributed AI egress on B and D; on C the heaviest user stayed below both floors). The drilldowns were also run on Tenant A with the real tokens of a `DOMAIN\user` finding and returned the person's rows.
