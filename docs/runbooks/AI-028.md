# AI-028 - HDSI AI Unsanctioned Web Access

> **Detection ID:** AI-028
> **Package:** `hdsi_ai_unsanctioned_web_access` v1.1.0 (deployment type: global)
> **Search name:** `Network - HDSI AI Unsanctioned Web Access - Rule`
> **Status:** Active. Risk-only (`action.notable = 0`). Notables come from the HDSI RBA AI aggregators.
> **Risk:** `user`, dynamic 3-30 (base 15 x provider `severity_weight` x `risk_multiplier`, halved when every request was blocked). System risk on the internal `src` is opt-in (off by default).
> **MITRE ATT&CK:** T1588.007 - Obtain Capabilities: Artificial Intelligence (Resource Development)
> **Data Model:** Web
> **Schedule:** `17 * * * *` (hourly at :17)
> **Lookback Window:** `-65m@m` to `-5m@m`
> **Suppression:** 24 h per `risk_entity` + `provider`
> **AI kill-chain phase:** `recon` (shadow-AI usage; not ATT&CK Reconnaissance)
> **Last Updated:** 2026-10-09

---

## Overview

This is the base "shadow AI" signal of the suite. It finds users who reach AI web apps that the organisation has not sanctioned: chat assistants (ChatGPT, Claude, Gemini, Copilot, Grok, Perplexity, DeepSeek and others) and AI writing, image, video, voice and app-builder tools. It reads proxy, NGFW URL-filtering, SSE/CASB and enterprise-browser logs in the CIM `Web` model. Each hostname, or SSE app name, is resolved through the common AI provider lookups (`ai_provider_domains`, `ai_provider_apps`).

Unsanctioned AI use is the most common way company data reaches a third-party model. One event is low risk on its own. The score is deliberately small (at most 30) and is written at most once per user and provider per day. It is meant to add up with stronger signals, such as upload volume, DLP hits, new-hour use or a new device, in the user risk aggregators.

v1.1.0 replaces the old consolidated rule. That rule grouped every web domain, wrote `$token$` risk scores that ES does not support, scored an `unknown` user, used the AI site as the system risk object and mapped to the wrong MITRE technique. AI-001, AI-002 and AI-003 were folded into this rule earlier (see `AI-001-002-003.md`).

## Detection Logic

### Plain English

1. **Main branch:** `tstats` over `Web`, limited by `hdsi_ai_unsanctioned_web_access_scope` to AI web hosts and their subdomains in `url_domain` or `site`, plus SSE app names in `site`. `fillnull_value="unknown"` keeps rows where only one of `url_domain` or `site` is set.
2. **URL fallback branch:** a second `tstats` (an `append` capped at 180 s and 50,000 rows) reads sources that log the AI host only inside `Web.url`. It matches URL prefixes and extracts the host. Rows the main branch already counted are excluded, so nothing is counted twice.
3. **Normalise** (`hdsi_ai_unsanctioned_web_access_prepare`):
   - placeholder, IP-address and GUID-based pseudo users are set to null;
   - IPv4-mapped IPv6 `src` is read as IPv4, and `src_public` is computed;
   - `ai_domain` is `url_domain`, else `site`, and `ai_input_type` is `host` or `app`.
4. Drop rows with neither a user nor an internal `src`. This removes inbound load-balancer, WAF and IIS logs.
5. Resolve the provider with `ai_domains_filter` and keep only `usage_type=web`. API, IDE, CLI and model-registry traffic belongs to other rules.
6. Drop providers listed in `hdsi_ai_unsanctioned_web_access_sanctioned_providers`.
7. Aggregate by `risk_entity` (the user, else the internal `src`), `provider` and `usage_type`. A hostname match needs at least `..._min_events` (3) events in the hour. An SSE app-name match counts from one event.
8. Drop a provider when every host seen is non-interactive. A host is non-interactive when the registry marks it `background` or `site` (for example `ab.chatgpt.com`, `gemini.gstatic.com`), or when it matches `..._auxiliary_hosts` (the Edge Copilot `ms-sso` sign-in frame).
9. Keep `src` only when exactly one internal source was seen. Clear it when more than `..._max_users_per_src` (3) users share that source (NAT, VDI, terminal server).
10. Resolve `bunit` from the identity (by user) or the asset (by `src`). Then remove approved users, hosts, business units and organisation-wide approvals with `ai_unsanctioned_filter(user,src,provider)`.
11. Score: `risk_score = min(30, max(3, round(15 x severity_weight x (0.5 if blocked_only) x risk_multiplier)))`.

### Key Fields

| Field | Description | Example Value |
|---|---|---|
| `risk_entity` | The user, or the internal `src` of an opt-in system-only row. This is the suppression key with `provider` | `jdoe@example.com` |
| `user` / `user_display` | Attributed user (`not attributed` when absent) | `EXAMPLE\jdoe` |
| `src` / `src_display` / `src_ip_list` | Single non-shared internal source, display value, and every source seen | `10.20.30.40` |
| `risk_src` | System risk object, set only when system risk is enabled | (empty by default) |
| `provider` | Resolved AI provider | `OpenAI` |
| `interactive_domains` / `ai_domain_list` | Interactive AI hosts or app names seen (up to 5 in the message) | `chatgpt.com` |
| `ai_host_source` | Where the host came from: `url_domain`, `site` or `url` (fallback branch) | `url` |
| `ai_match` | How the provider matched: `exact`, `subdomain`, `cloud_pattern` or `app_name` | `subdomain` |
| `event_count` / `bytes_out` | Web events and bytes sent in the window | `42` / `183204` |
| `web_actions` / `blocked_only` | Logged actions; 1 when every request was blocked | `allowed` / `0` |
| `sourcetypes` | Contributing sourcetypes | `pan:threat` |
| `severity_weight` / `risk_multiplier` / `risk_score` | Provider weight, identity multiplier and final score | `1.0` / `1.0` / `15` |

| Parameter | Default | Macro | Notes |
|---|---|---|---|

## Triage Steps

> **Estimated triage time:** 5-10 minutes. This rule raises no notable. You normally reach it from an HDSI RBA AI aggregator notable or from the risk timeline of a user.

Replace `<user>`, `<provider>` and `<bunit>` with values from the risk event. Set the time picker to cover the risk event (for example the last 7 days).

### Step 1: Validate the risk event

```spl
| from datamodel:"Risk.All_Risk"
| search source="Network - HDSI AI Unsanctioned Web Access - Rule" risk_object="<user>"
| table _time risk_object risk_object_type risk_score provider risk_message
| sort - _time
```

- The risk message names the provider, the hosts, the event count, the actions and the sourcetypes.
- One event per provider per day is expected. Several providers on the same day show broader adoption, not a burst.
- The user may appear in two spellings (`DOMAIN\user` from an on-premises NGFW, a UPN from a cloud feed). The HDSI RBA AI user aggregators merge them. Search with `risk_object="*<bare user>*"` to see both.

### Step 2: Identify the user

```spl
| inputlookup identity_lookup_expanded
| search identity="<user>"
| table identity first last email managedBy bunit category priority watchlist
```

- Find the role, business unit (`bunit`) and manager. ES identities have no `department` field. `bunit` drives both group approvals and the risk multiplier.
- If nothing is returned, try the bare account name (no `DOMAIN\` or `@suffix`).

### Step 3: Review the AI web activity

```spl
| tstats summariesonly=t allow_old_summaries=t fillnull_value="unknown" count sum(Web.bytes_out) as bytes_out sum(Web.bytes_in) as bytes_in values(Web.url) as url values(Web.action) as action values(Web.http_user_agent) as http_user_agent min(_time) as firstTime max(_time) as lastTime
    from datamodel=Web
    where Web.user="<user>" (`hdsi_ai_unsanctioned_web_access_scope` OR (sourcetype IN (`hdsi_ai_unsanctioned_web_access_url_sourcetypes`) Web.url IN (`hdsi_ai_unsanctioned_web_access_urls`)))
    by sourcetype Web.user Web.src Web.url_domain Web.site
| rename Web.* as *
| eval ai_input_type=if(url_domain="unknown" AND site!="unknown","app","host"),
       ai_domain=case(url_domain!="unknown",url_domain, site!="unknown",site, true(),lower(replace(mvindex(url,0),"^(?:[A-Za-z][A-Za-z0-9+.-]*://)?(?:[^/@?#]*@)?([^/:?#&;\s]+).*$","\1")))
| `ai_domains_filter`
| eval mb_out=round(bytes_out/1024/1024,2), mb_in=round(bytes_in/1024/1024,2), url=mvindex(url,0,4)
| convert ctime(firstTime) ctime(lastTime)
| table firstTime lastTime user src provider ai_domain ai_traffic_class action count mb_out mb_in sourcetype http_user_agent url
| sort - mb_out
```

- The query handles all three ways a source can log the AI service: a host in `url_domain`, a host or SSE app name in `site`, or a host only inside `url`.
- Look at `mb_out`. Megabytes sent to a chat host suggest file or document uploads, not a few prompts. Check whether `Network - HDSI AI High Volume Upload To AI Service - Rule` also fired.
- `action` shows whether the proxy allowed the traffic. A user who keeps retrying a blocked category is showing intent and policy pressure.
- `http_user_agent` separates a browser from a desktop client or script.

### Step 4: Check related detections and the user's total

```spl
| from datamodel:"Risk.All_Risk"
| search risk_object="*<bare user>*" source="* - HDSI *"
| stats count as risk_events sum(risk_score) as total_risk values(source) as detections min(_time) as firstTime max(_time) as lastTime by risk_object risk_object_type
| convert ctime(firstTime) ctime(lastTime)
| sort - total_risk
```

- On its own this rule contributes 3-30 points per provider per day.
- These co-occurring rules raise concern: high-volume upload, DLP violation on upload, gradual exfiltration, time-of-day anomaly, access from an unmanaged device, VPN/proxy evasion.

### Step 5: Check sanctioned status

```spl
| inputlookup ai_sanctioned_entities
| eval k=lower(allow_key)
| where like(k, lower("<user>|%")) OR like(k, lower("<bunit>|%")) OR like(k, "*|%")
| table entity_type entity provider scope expires owner reason enabled allow_key
```

```spl
| rest /servicesNS/-/-/admin/macros splunk_server=local count=0
| search title="hdsi_ai_unsanctioned_web_access_sanctioned_providers"
| table title definition eai:acl.app updated
```

- An entry that has expired (`expires` in the past) or is disabled (`enabled=0`) does not suppress.
- If the provider is sanctioned for the organisation but the rule still fires, the provider name in the macro or the `*|<provider>` key does not match the `provider` value exactly. Fix the tuning.

### Step 6: Make a determination

- **True Positive:** an unsanctioned provider is used for work without approval, especially with uploads or alongside a data-exposure rule.
- **Benign True Positive:** the use is real and approved (pilot, licensed tool, sanctioned team), but the approval is missing from `ai_sanctioned_entities` or the sanctioned-providers macro.
- **False Positive:** the rule fired on traffic that is not use. Examples: an embedded widget or link preview on a non-AI site, an inbound source that maps an authenticated user into `Web.user`, a non-interactive host missing from the registry.

---

## True Positive Indicators

- The provider is not on the organisation's approved list, and the user is not in a sanctioned group or pilot.
- `mb_out` is well above a few prompts, or a data-exposure rule fired for the same user the same day.
- Allowed traffic to a provider the proxy is meant to block (a policy gap), or repeated blocked attempts followed by allowed use from another source.
- The user works with regulated or sensitive data (`bunit` with a high sensitivity in `ai_department_sensitivity`).

---

## False Positive Scenarios

| Scenario | Likelihood | Mitigation |
|---|---|---|
| A provider is sanctioned but not configured. Out of the box every enabled AI web provider counts: on Tenant A, OpenAI, Google Gemini and Microsoft Copilot were 244 of 266 user-provider pairs in a 4 h run | High until configured | Set `hdsi_ai_unsanctioned_web_access_sanctioned_providers`, or add `*\|<provider>` rows to `ai_sanctioned_entities` (the row applies to every AI rule) |
| Approved individual or team use | Medium | Add `<user>\|<provider>` or `<bunit>\|<provider>` rows, with an `expires` date |
| Background or embedded traffic (the Edge Copilot sidebar sign-in frame, static assets, experiment flags) | Low after v1.1 | Mark the host `traffic_class=background` in `ai_provider_domains` (common package), or extend `..._auxiliary_hosts` |
| Blocked attempts only | Medium where the AI category is blocked | Scored at half weight on purpose. To ignore them, add `\| where blocked_only=0` in `..._customizations` |
| Inbound web logs that carry an authenticated user | Low | Exclude the sourcetype in `hdsi_ai_unsanctioned_web_access_filter` |
| Enterprise-browser pseudo-identities (`<guid>+<id>@<domain>`) | Low | These are dropped by `..._invalid_users`. Extend the regex for kiosk or service accounts |
| One person under two user spellings (UPN and `DOMAIN\user`) | Medium on mixed cloud and on-premises feeds | Not a false positive. The aggregators merge the spellings; improve ES identity correlation |

## Response Actions

### If confirmed True Positive

1. **Contain:** block the provider or AI category for the user or group in the proxy, NGFW or SSE policy. Where a sanctioned alternative exists, point the user to it.
2. **Notify:** inform the user's manager and the data governance or AI governance owner. Include the provider, dates and upload volume.
3. **Investigate:** use Step 3 to find what was sent (`mb_out`, URLs). Check DLP, CASB or SSE file-upload events for the same user and window. Look for the same provider in the DNS rule (`Network - HDSI AI DNS Queries To AI Domains - Rule`) from the user's hosts.
4. **Remediate:** if sensitive data was uploaded, follow the data-handling incident process. That may mean a deletion request to the provider and a review of the account's history in the provider's enterprise console, if one exists.
5. **Document:** record the provider, the evidence and the decision in the case.

### If Benign True Positive

1. Add a row to `ai_sanctioned_entities` (common package) with the narrowest scope that fits: user, host, `bunit` or `*`. Give it an `expires` date, an `owner` and a `reason`.
2. For an organisation-wide approval that should apply to this rule only, add the provider to `hdsi_ai_unsanctioned_web_access_sanctioned_providers`.
3. Close the parent aggregator notable as Benign True Positive, with the reference to the approval.

## Tuning Guidance

### Reducing false positives

- Agree the sanctioned-provider list before enabling. This single step removed about 95 % of the volume in validation (about 2,370 to about 110 user-provider pairs a day on Tenant A).
- Narrow `hdsi_ai_unsanctioned_web_access_url_sourcetypes` to the sourcetypes that log the host only in the URL (discovery SPL in the package README). Set it to `"__none__"` when there are none.
- Exclude inbound or server sourcetypes that carry users in `hdsi_ai_unsanctioned_web_access_filter`, for example `NOT sourcetype IN ("aws:elb:accesslogs","aws:waf")`.
- Leave system risk off unless the ES asset lookup covers the client ranges. None of the HDSI RBA AI aggregators read system risk.

### Adjusting thresholds

Once the rule is enabled, see which providers drive the volume and whether they should be sanctioned:

```spl
| from datamodel:"Risk.All_Risk"
| search source="Network - HDSI AI Unsanctioned Web Access - Rule"
| stats count as risk_events dc(risk_object) as users sum(risk_score) as total_risk avg(risk_score) as avg_score by provider
| sort - risk_events
```

To derive `..._min_events` and the system-only gate before enabling, run the 7-day hourly profile in the package README (Threshold section). It uses the rule's own preparation macro.

### Adding allowlist entries

Lookup `ai_sanctioned_entities` (common package `hdsi_ai_rba_common`). `allow_key` is lowercase `<entity>|<provider>`, or `<entity>|*` for every provider:

```
entity_type,entity,provider,scope,expires,owner,reason,enabled,allow_key
user,jdoe@example.com,OpenAI,provider,2027-03-31,secops,Approved ChatGPT Enterprise pilot,1,jdoe@example.com|openai
group,engineering,Anthropic,provider,2027-03-31,secops,Claude for engineering,1,engineering|anthropic
group,*,Microsoft Copilot,provider,2099-12-31,secops,Organisation licence,1,*|microsoft copilot
```

`provider` must match the name in `ai_provider_domains` or `ai_provider_apps`. To stop treating a domain as AI everywhere, set its row to `enabled=0` in the common lookup instead.
