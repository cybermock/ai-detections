# AI-012 - HDSI AI DNS Queries To AI Domains

> **Detection ID:** AI-012 (`detection_id=hdsi_ai_dns_queries_to_ai_domains`)
> **Search name:** `Network - HDSI AI DNS Queries To AI Domains - Rule`
> **Package:** `saved_searches/packages/hdsi_ai_dns_queries_to_ai_domains` (version 1.1.0, `deployment_type: global`, ships `enable_alerting: false`)
> **Status:** Active, risk only (`action.notable = 0`, `action.risk = 1`). Notables come from the `HDSI RBA AI` aggregators.
> **Risk Score:** system (`src`) only, 5 to 30 (computed `risk_score`; the literal `_risk` fallback is 10). No user risk object.
> **MITRE ATT&CK:** T1588.007 - Obtain Capabilities: Artificial Intelligence (Resource Development)
> **Data Model:** `Network_Resolution` (accelerated)
> **Schedule:** `35 1 * * *` (daily at 01:35)
> **Lookback Window:** `-1d@d` to `@d` (the previous calendar day)
> **Suppression:** `src` for 72000 s (20 h), so one risk event per host per day
> **Kill Chain Phase:** Reconnaissance (`ai_kill_chain_phase=recon`)
> **Last Updated:** 2026-10-09

---

## Overview

This detection finds hosts whose DNS queries show that someone on them is **using an AI service**: chat sites (ChatGPT, Claude, Gemini, Perplexity, DeepSeek, Grok and many more), model APIs (`api.openai.com`, `api.anthropic.com`, OpenRouter, Deepgram), cloud AI endpoints (AWS Bedrock and SageMaker, GCP Vertex AI, Azure OpenAI, Azure AI Foundry and Azure AI Services), local-LLM tooling (Ollama) and model registries (Hugging Face). DNS is the most portable AI-usage signal in the suite. It exists wherever client DNS is logged, it needs no proxy or TLS inspection, and it sees desktop apps, SDKs and scripts that never touch a web proxy.

The rule writes **one modest risk event per host per day** on `src`. It is context for the host's risk timeline and an input to the multi-vector aggregator (`shadow_usage` vector). On its own it is not an incident: it says that AI was used from a host, not what was sent to it. The CIM `Network_Resolution` model has no user field, so the rule never writes user risk and never feeds the user threshold aggregators.

Version 1.1.0 replaced a 5-minute rule that counted resolvers and forwarders as clients, counted query and response logs twice, reported browser prefetch as usage, re-scored organisation-licensed GitHub Copilot and wrote risk on the user `unknown`. On the validation tenants that version would have produced an estimated 350 to 8,000 risk events a day, mostly noise.

## Detection Logic

### Plain English

1. Run `tstats` over `Network_Resolution` for the previous day, split by `src`, `query`, `message_type` and `vendor_product`. An inline pre-filter (`hdsi_ai_dns_queries_to_ai_domains_query_prefilter`) keeps only names that contain an AI provider domain or a cloud AI endpoint pattern. Placeholder and loopback sources are dropped.
2. Take the **largest** per-type, per-product count for each `src`/`query` rather than the sum, so a source that logs both query and response, or two sensors that log the same client, is not double counted.
3. Resolve each name to a provider with the common `ai_domains_filter` (`ai_input_type="dns"`). Trailing-dot (`chatgpt.com.`), `www.` and SRV names are normalised. Providers in `..._excluded_providers` (coding assistants scored by AI-019, plus Microsoft 365 and Security Copilot) are removed.
4. **Evidence gate** per host, provider and day. Background names (update checks, prefetch, SSO, telemetry, CDN hosts such as `bzrcdn.openai.com`, `ab.chatgpt.com`, `gemini.gstatic.com`) never count. A provider counts as used when its API, local-LLM, model-registry or CLI names were queried at least once, or its other web/IDE names at least 10 times.
5. **Shared-source guard:** a DNS client that resolved 10,000 or more distinct names that day is a resolver, forwarder, proxy, mail relay or NAT egress. All its rows are dropped.
6. **Roaming-address guard:** rows from roaming DNS-security clients (Cisco Umbrella / Cloud Security / Secure Access) whose `src` is a home-router address (`192.168.0.0/16`, `10.0.0.0/24`) are dropped, because those addresses are shared by unrelated laptops.
7. Look up the asset `bunit` and remove approved hosts and asset groups with `ai_unsanctioned_filter(user,src,provider)`.
8. Aggregate to one row per host and score it.

### Scoring

- `base_score = round(10 x highest provider severity_weight) + 3 per additional provider`
- `risk_score = min(30, base_score)`
- Typical single-provider scores: chat sites 5 to 10, Model Registry (Hugging Face) 9, model APIs and cloud AI endpoints 10 to 12 (Anthropic and Vertex AI 12, Azure AI Services 8), Local LLM (Ollama) 11, CLI names 5.

## Triage Steps

> **Estimated triage time:** 5 to 10 minutes. This is host-level context. Spend time on it only when the host also carries other HDSI AI risk or the provider is unexpected for the host's role.

### Step 1: Validate the risk event

Set the time picker to the last 7 days.

```spl
| from datamodel:"Risk.All_Risk"
| search source="Network - HDSI AI DNS Queries To AI Domains - Rule" risk_object="$src$"
| table _time, risk_object, risk_object_type, risk_score, provider_list, usage_type_list, dns_query_count, evidence_query_count, ai_domain_sample, vendor_product, risk_message
| sort - _time
```

- Is this a one-day event or a daily habit? A host that appears every day is a regular AI user.
- `usage_type_list` containing `api`, `local_llm` or `model_registry` means a tool or script talked to the service, not only a browser.

### Step 2: Identify the host and the person behind it

```spl
| inputlookup asset_lookup_by_str where ip="$src$" OR dns="$src$" OR nt_host="$src$"
| table ip, dns, nt_host, owner, bunit, category, priority
```

DNS has no user, so find who used the host that day from authentication or firewall User-ID data:

```spl
| tstats summariesonly=t allow_old_summaries=t count min(_time) as firstTime max(_time) as lastTime from datamodel=Authentication where Authentication.src="$src$" Authentication.action="success" by Authentication.user Authentication.app
| rename Authentication.* as *
| append [| tstats summariesonly=t allow_old_summaries=t count min(_time) as firstTime max(_time) as lastTime from datamodel=Network_Traffic where All_Traffic.src="$src$" All_Traffic.user=* NOT All_Traffic.user="unknown" by All_Traffic.user | rename All_Traffic.* as * | eval app="firewall User-ID"]
| convert ctime(firstTime) ctime(lastTime)
| sort - count
```

- A server (category, naming, no interactive logons) calling Bedrock, Vertex AI, SageMaker or Deepgram is usually an application workload. Find its owner.
- A workstation with one interactive user gives you the person to talk to.

### Step 3: Review the AI names the host resolved

This is the rule's second drilldown, with a column that shows which names were treated as background.

```spl
| tstats summariesonly=t allow_old_summaries=t count min(_time) as firstTime max(_time) as lastTime values(DNS.message_type) as message_type values(DNS.vendor_product) as vendor_product from datamodel=Network_Resolution where DNS.src="$src$" `hdsi_ai_dns_queries_to_ai_domains_query_prefilter` by DNS.src DNS.query
| rename DNS.* as *
| eval ai_domain=query, ai_input_type="dns"
| `ai_domains_filter`
| eval background=if(`hdsi_ai_dns_queries_to_ai_domains_background_names`, "yes", "no")
| convert ctime(firstTime) ctime(lastTime)
| table firstTime, lastTime, src, provider, usage_type, ai_match, query, background, message_type, vendor_product, count
| sort provider - count
```

- `ws.chatgpt.com` (the live chat socket), `api.*` names and model-download names (`cdn-lfs.huggingface.co`) are strong evidence of real use.
- Only the bare site name, a little over 10 times, with nothing else, is the weakest case (browser-integrated assistants such as Gemini in Chrome or Copilot in Edge).

### Step 4: Rule out a shared source

```spl
| tstats summariesonly=t allow_old_summaries=t dc(DNS.query) as distinct_names count from datamodel=Network_Resolution where DNS.src="$src$" by DNS.src DNS.vendor_product _time span=1d
| rename DNS.* as *
| eval day=strftime(_time, "%Y-%m-%d")
| table day, src, vendor_product, distinct_names, count
```

- A busy workstation resolves a few hundred to a few thousand names a day. A value approaching the 10,000 guard points to a jump host, terminal server, proxy or NAT address: the AI use belongs to several people.
- If `vendor_product` is a roaming DNS-security client and `src` is a private address outside the guarded ranges (for example `172.16.x` at home), the address may still be shared. Pivot on the roaming identity in the raw DNS-security events before attributing the activity.

### Step 5: Check related HDSI AI risk on the host and its user

```spl
| from datamodel:"Risk.All_Risk"
| search source="* - HDSI AI * - Rule" risk_object IN ("$src$", "<user from step 2>")
| stats sum(risk_score) as total_risk dc(source) as detections values(source) as sources values(provider) as providers by risk_object, risk_object_type
| sort - total_risk
```

- Web, process or upload detections for the same provider (AI-028, AI-005, AI-007, AI-044) turn this DNS context into confirmed use.
- The multi-vector aggregator (AI-RISK-005) counts this rule as one `shadow_usage` vector for the host.

### Step 6: Check approval status

```spl
| inputlookup ai_sanctioned_entities
| eval key_entity=mvindex(split(allow_key, "|"), 0)
| where enabled="1" AND (key_entity=lower("$src$") OR key_entity=lower("<asset bunit>") OR key_entity="*")
| table entity_type, entity, provider, scope, expires, owner, reason, allow_key
```

- An approval that exists but did not apply usually means the provider string differs (the key uses the lowercased `provider` value the rule emits) or the approval has expired.
- Providers licensed for everyone (ChatGPT Enterprise, Gemini for Workspace) belong in `hdsi_ai_dns_queries_to_ai_domains_excluded_providers`, not in per-host approvals.

### Step 7: Make a determination

- **True Positive:** the host used an AI service that is not approved for it or its owner, or a server calls an AI API that nobody owns.
- **Benign True Positive:** real use that is approved or expected (an approved research host, a known application workload, a provider licensed for everyone).
- **False Positive:** the evidence is prefetch or background only, or `src` is a shared address (resolver, egress, roaming home address) that the guards did not catch.

---

## True Positive Indicators

- API, local-LLM or model-registry names (`api.anthropic.com`, `bedrock-runtime.*`, `registry.ollama.ai`, `cdn-lfs.huggingface.co`) from a host whose role does not need them.
- Several providers on one host on the same day (+3 per additional provider), especially consumer chat sites next to an approved enterprise tool.
- `ws.chatgpt.com` or comparable chat-socket names: someone held live chat sessions.
- The same host also carries web, process, upload or DLP risk from other HDSI AI detections.
- The host is in a sensitive business unit (finance, legal, HR, R&D) or holds regulated data.
- A server calling a cloud AI endpoint that no application owner can explain.

## False Positive Scenarios

Evidence from read-only tests on 4 production ES tenants (2026-10-09).

| Scenario | Likelihood | Mitigation |
|---|---|---|
| Browser-integrated assistants (Gemini in Chrome, Copilot in Edge/Windows) resolve service names without a prompt. Single-provider Gemini and consumer Copilot rows were 27 of 79 daily rows on Tenant A and 18 of 45 on Tenant C, mostly just above the threshold | High | Raise `..._min_queries` if these rows dominate; measure with the Threshold SPL below |
| Sanctioned enterprise AI looks the same as personal use. On Tenant B, 987 of 1,500 daily rows (66%) were OpenAI only | High where a provider is licensed | Add the provider to `..._excluded_providers` |
| Roaming DNS-security clients log the laptop's home-router address, shared by unrelated laptops (37% and 33% of `192.168.x`/`10.0.0.x` addresses on Tenant B carried several identities) | High on roaming tenants | Keep `..._unreliable_src` on; fix in the TA by mapping the roaming device identity to `src` |
| Shared DNS clients (resolvers, forwarders, proxies, NAT egress) below the 10,000-name guard | Medium | Add them to `hdsi_ai_dns_queries_to_ai_domains_filter` (`NOT DNS.src IN (...)`) |
| Server workloads calling Vertex AI, Bedrock, SageMaker or Deepgram (10 to 12 points a day) | Medium | Intended visibility. Approve known workloads per host in `ai_sanctioned_entities` |
| Exact-only web providers such as `replit.com` pass on query count alone (19 of 183 hosts on Tenant C were above 10 a day) | Low | Raise `..._min_queries` or exclude the provider |
| DHCP churn: the same IP is a different device on another day | Low | Use the asset and Authentication pivots in Step 2 for the specific day |

## Response Actions

### If confirmed True Positive

1. **Contain:** if the provider is prohibited, block it in the DNS-security product or web proxy for the host or its user group. For an unowned server workload, revoke or rotate the cloud AI credentials it uses and identify the code calling the endpoint.
2. **Notify:** the host owner and their manager, and the data governance or AI governance owner.
3. **Investigate:** use Step 5 to find upload, DLP or process detections for the same host or user. For local-LLM or model-registry activity, check AI-011 (Local LLM Framework Execution), AI-013 (LLM Model File Download) and AI-014 (Local LLM Listening Port).
4. **Remediate:** steer the user to the approved AI service; update the acceptable-use exception list if the use is legitimate but unapproved.
5. **Document:** record the host, user, provider and outcome in the case.

### If Benign True Positive

1. Approve the host or asset group in `ai_sanctioned_entities` (common package), for example:
   ```
   system,10.20.30.40,OpenAI,provider,2099-12-31,security,approved_research_host,1,10.20.30.40|openai
   group,research,Anthropic,group,2099-12-31,security,approved,1,research|anthropic
   ```
2. For providers licensed for the whole organisation, add them to `hdsi_ai_dns_queries_to_ai_domains_excluded_providers` instead.
3. Record the business justification in the `reason` field and set a realistic `expires` date.

## Tuning Guidance

### Reducing false positives

- Exclude known resolvers, forwarders, proxies and VDI pools inline in `hdsi_ai_dns_queries_to_ai_domains_filter`, e.g. `NOT DNS.src IN ("10.1.1.10","10.1.1.11")`.
- Put organisation-wide licensed providers into `hdsi_ai_dns_queries_to_ai_domains_excluded_providers` (use `"__none__"` to keep every provider).
- Add other roaming DNS products to the `vendor_product` regex in `hdsi_ai_dns_queries_to_ai_domains_unreliable_src` (e.g. `zscaler|cloudflare`).
- Add new background names to `hdsi_ai_dns_queries_to_ai_domains_background_names`; `false()` counts every name.
- Override `risk_score` (at most 100) in `hdsi_ai_dns_queries_to_ai_domains_risk_score`, the last pipe, or post-filter rows in `hdsi_ai_dns_queries_to_ai_domains_customizations`.

### Adjusting thresholds

Split prefetch-like hosts (one name) from real users (several names) per provider. Run over one full day:

```spl
| tstats summariesonly=t allow_old_summaries=t count from datamodel=Network_Resolution where `hdsi_ai_dns_queries_to_ai_domains_query_prefilter` by DNS.src DNS.query _time span=1d
| rename DNS.* as *
| eval ai_domain=query, ai_input_type="dns"
| `ai_domains_filter`
| stats sum(count) as count dc(ai_domain) as names by _time, src, provider
| eval kind=if(names=1, "single name", "several names")
| stats count as host_days p50(count) as p50 p90(count) as p90 by provider, kind
| sort provider, kind
```

Size the shared-source guard: pick a value just above the busiest real workstation or server that should still be scored.

```spl
| tstats summariesonly=t allow_old_summaries=t dc(DNS.query) as names from datamodel=Network_Resolution where NOT DNS.src IN ("unknown","-","0.0.0.0","127.0.0.1","::1") by DNS.src
| eval band=case(names<1000,"a <1k", names<3000,"b 1-3k", names<5000,"c 3-5k", names<10000,"d 5-10k", names<20000,"e 10-20k", names<50000,"f 20-50k", true(),"g 50k+")
| stats count as clients by band
```

### Pre-filter maintenance

`hdsi_ai_dns_queries_to_ai_domains_query_prefilter` is a literal list generated from `ai_provider_domains`. A name added to the lookup is never seen until the pre-filter is regenerated with the SPL in the package README.
