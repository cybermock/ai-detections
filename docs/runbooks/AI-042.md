# AI-042 - New AI Provider Adoption Velocity

> **Detection ID:** AI-042 (package `hdsi_ai_new_provider_adoption_velocity`, `detection_id=hdsi_ai_new_provider_adoption_velocity`)
> **Search name:** `Network - HDSI AI New Provider Adoption Velocity - Rule`
> **Status:** Active, version 1.1.0, `deployment_type: global`, ships with `enable_alerting: false`
> **Output:** Risk only (`action.notable = 0`). Notables come from the HDSI RBA AI aggregators.
> **Risk Score:** one risk object per row. User (Web path): 25 base, computed up to 60. Host `src` (DNS path): 15 base, computed up to 40, no multiplier. Static `_risk` fallback: user 25, system 15
> **MITRE ATT&CK:** T1588.007 - Obtain Capabilities: Artificial Intelligence (Resource Development)
> **Data Model:** `Network_Resolution` (host risk) and/or `Web` (user risk), accelerated for at least 21 days
> **Schedule:** `45 2 * * *` (daily at 02:45)
> **Lookback Window:** `-21d@d` to `@d` (7-day velocity window plus a 14-day baseline)
> **Suppression:** `user,src,new_providers` for 259200s (72 hours; a growing burst is reported again)
> **Kill Chain Phase:** `recon`
> **Last Updated:** 2026-10-09

---

## Overview

This detection finds a user or host that starts using several AI providers it has never touched before, in a short burst. Examples: a user who tries ChatGPT, Gemini and Perplexity for the first time in the same week, or a workstation that starts calling the Anthropic API, AWS Bedrock and GitHub Copilot on the same day. One new AI tool is ordinary. A burst of several is a change in behaviour: someone is shopping for AI capability, possibly ahead of moving data into those services.

A provider is "new" when the entity never touched it in the 14-day baseline and it became actively used in the last 7 days. Because a DNS client address is not a stable person, a host must adopt its new providers on one day; a user has the whole 7-day window. A data path with less than 7 days of baseline fails closed instead of calling everything new. The rule writes one risk event on the user (Web) or the host (DNS) on the daily run after the entity crosses the threshold. It never creates a notable on its own.

## Detection Logic

### Plain English

1. **DNS path.** `tstats` over `Network_Resolution` by day, `src`, `query` and `message_type`, pre-filtered by `hdsi_ai_new_provider_adoption_velocity_dns_names` (exact names of every enabled `ai_provider_domains` row with `www.` and trailing-dot forms, 51 recurring service subdomains, and prefixes for regional Bedrock, SageMaker and Vertex AI). Placeholder, loopback and home-LAN (`192.168.*`, `..._dns_src_scope`) sources are excluded inline. Gives system risk on `src`.
2. **Web path (`append`).** `tstats` over `Web` by day, `user`, `url_domain` and `site`, pre-filtered by `..._web_scope`. `ai_domain` is `url_domain`, or `site` (SSE app name) when there is no `url_domain`. Placeholder and IP-address users are dropped. Gives user risk.
3. **Daily evidence gate.** A provider is *active* on a day if its runtime API names had at least 3 DNS queries (or 1 Web event), an SSE app session was matched, or its other non-background names had at least 10 DNS queries or 3 Web events. Background names (telemetry, CDN, static, experiment hosts) never make a provider active.
4. **New.** `first_touch` (any query, including background) falls inside the last 7 days, and the provider was active at least once.
5. **Coverage guard.** A path is dropped unless its first well-covered day is at least 14 days old (7 + 7).
6. **Shared-source guards.** DNS clients that touched 15 or more providers are resolvers or egress and are dropped. Hosts must have touched some AI provider before the window.
7. **Exclusions and approvals.** `..._excluded_providers` (Microsoft 365 Copilot, Microsoft Security Copilot) are removed. `bunit` comes from `asset_lookup_by_str` (hosts) or `identity_lookup_expanded` (users), then `ai_unsanctioned_filter(user,src,provider)` removes approved pairs.
8. **Host burst.** For a host, new providers count only if they became active on the same day as its latest adoption.
9. **Threshold.** At least 3 new providers, with the latest adoption in the last 2 complete days (a skipped run is caught up).
10. **Score.** `base = 25 (user) or 15 (host) + 5 per provider above 3 (max 15) + 5 if any provider is new to the organisation + 5 if any new provider was used through its runtime API`. Users are multiplied by `risk_multiplier`. `risk_score = round(min(60 user / 40 host, base x multiplier))`.
11. `..._customizations`, then `..._risk_score` as the last pipe.

## Triage Steps

> **Estimated triage time:** 15-25 minutes. Replace `$entity$` with the risk object (`user` for a Web row, `src` for a DNS row). For a `DOMAIN\user` value, replace the backslash with `*` inside quoted search terms. Set the time picker to the last 21 days so the baseline is visible.

### Step 1: Validate the risk event

```spl
| from datamodel:"Risk.All_Risk"
| search source="Network - HDSI AI New Provider Adoption Velocity - Rule" risk_object="$entity$"
| table _time, risk_object, risk_object_type, risk_score, risk_message, provider_list, api_provider_list, org_new_provider_list, latest_adoption
| sort - _time
```

- Is the object a user (Web path) or a host address (DNS path)?
- Which providers are new? Are they consumer chat services, developer runtimes (API, CLI, local LLM) or a mix?
- Is any provider new to the whole organisation (`org_new_provider_list`)? That is a new shadow-AI service to review for policy, not only for this entity.

### Step 2: Identify the user or the host

```spl
| inputlookup identity_lookup_expanded
| search identity="$entity$"
| table identity, first, last, email, managedBy, category, priority, bunit
```

```spl
| inputlookup asset_lookup_by_str
| search ip="$entity$" OR dns="$entity$" OR nt_host="$entity$"
| table ip, dns, nt_host, owner, bunit, category, priority
```

- An asset-inventory match does not prove a single user. On Tenant B, 6 of the 9 addresses an earlier version reported were in the asset inventory, and 8 of the 9 had several users.

### Step 3: Review the adoption timeline

For a host (the rule's "View AI DNS names resolved per day" drilldown):

```spl
| tstats summariesonly=t allow_old_summaries=t count from datamodel=Network_Resolution where DNS.src="$entity$" `hdsi_ai_new_provider_adoption_velocity_dns_names` by DNS.src DNS.query _time span=1d
| rename DNS.* as *
| eval ai_domain=query, ai_input_type="dns"
| `ai_domains_filter`
| stats sum(count) as count dc(_time) as days min(_time) as firstTime max(_time) as lastTime values(ai_domain) as ai_domains by src provider usage_type
| convert timeformat="%Y-%m-%d" ctime(firstTime) ctime(lastTime)
| table firstTime, lastTime, days, src, provider, usage_type, count, ai_domains
| sort firstTime
```

For a user (the rule's "View AI web activity per day" drilldown):

```spl
| tstats summariesonly=t allow_old_summaries=t fillnull_value="unknown" count from datamodel=Web where Web.user="$entity$" `hdsi_ai_new_provider_adoption_velocity_web_scope` by sourcetype Web.user Web.url_domain Web.site _time span=1d
| rename Web.* as *
| eval url_domain=coalesce(nullif(url_domain,"unknown"),nullif(site,"unknown")), ai_domain=lower(url_domain), ai_input_type=if(site=url_domain,"app","host")
| `ai_domains_filter`
| stats sum(count) as count dc(_time) as days min(_time) as firstTime max(_time) as lastTime values(url_domain) as url_domain values(sourcetype) as sourcetype by user provider usage_type
| convert timeformat="%Y-%m-%d" ctime(firstTime) ctime(lastTime)
| table firstTime, lastTime, days, user, provider, usage_type, count, url_domain, sourcetype
| sort firstTime
```

- Providers whose `firstTime` is in the last 7 days are the new ones; the others are the baseline.
- `usage_type` `api`, `cli`, `local_llm` or `model_registry` means developer tooling (SDK calls, model pulls), not a browser chat.
- One busy day versus steady daily use tells you whether this was a trial or a new habit.

### Step 4: For host rows, find the person behind the address on the burst day

```spl
| tstats summariesonly=t allow_old_summaries=t count min(_time) as firstTime max(_time) as lastTime from datamodel=Authentication where Authentication.src="$entity$" Authentication.action="success" by Authentication.user Authentication.dest Authentication.app _time span=1d
| rename Authentication.* as *
| sort - _time
| convert ctime(firstTime) ctime(lastTime)
```

- Look at the `latest_adoption` day. DHCP, VPN or EDR logs give the most reliable mapping.
- On roaming DNS-security tenants the address is the client's internal address and can pass between people within a week. A same-day burst usually belongs to one person, but confirm before acting.

### Step 5: Check related AI risk

```spl
| from datamodel:"Risk.All_Risk"
| search risk_object="$entity$" source="* - HDSI AI * - Rule"
| stats sum(risk_score) as total_risk dc(source) as detections values(source) as sources values(ai_kill_chain_phase) as phases by risk_object, risk_object_type
| sort - total_risk
```

```spl
`notable`
| search search_name="Threat - HDSI RBA AI *" "$entity$"
| table _time, search_name, rule_title, urgency, status_label, owner
```

- Velocity alone scores 15 to 60. It matters when the same entity also has upload, DLP, MCP or agent risk.

### Step 6: Determine sanctioned status

```spl
| inputlookup ai_sanctioned_entities
| where enabled=1
| table entity_type, entity, provider, scope, expires, owner, reason, allow_key
| sort entity_type, entity
```

- Is one of the new providers being rolled out to everyone? Approve it organisation-wide (`*|<provider>`) or add it to `..._excluded_providers`.
- Is the host or `bunit` an approved engineering group?

### Step 7: Make a determination

- **True Positive:** an entity outside an approved engineering role adopting several unapproved AI services, particularly consumer services new to the organisation, or followed by upload activity.
- **Benign True Positive:** developer onboarding or a tool trial (the 3 Tenant B rows were each one person adding developer tools on one day), or an organisation-wide rollout. Approve the host, group or provider.
- **False Positive:** a pooled address mixing two people on the same day, or a provider that was already in use through a subdomain outside the pre-filter. Exclude the pool in `..._filter`, or add the subdomain to the pre-filters.

---

## True Positive Indicators

- Several new consumer chat services in the same week, with no business case.
- A provider new to the whole organisation (`org_new_provider_list` not `none`).
- New runtime API use (`api_provider_list`) on a host outside engineering, such as a finance or HR workstation calling model APIs.
- Same-week upload, DLP or personal-email risk for the same entity.
- A user who recently resigned or is on a watch list.

---

## False Positive Scenarios

| Scenario | Likelihood | Mitigation |
|---|---|---|
| Developer onboarding or tool trials (Anthropic API + Bedrock + GitHub Copilot on one day) | Medium | Approve engineering hosts or groups in `ai_sanctioned_entities` |
| Organisation-wide rollout of an AI tool | Medium during rollouts | `*\|<provider>` row, or `..._excluded_providers` |
| The "mainstream trio" (Gemini + Copilot + ChatGPT) surfaced by a browser or OS update | Medium for users | Approve licensed providers organisation-wide; the evidence gate already removes pure prefetch |
| Pooled DHCP, Wi-Fi or VPN address mixing two people's adoptions on one day | Low | Exclude the pool in `..._filter`; confirm with Step 4 |
| A provider used in the baseline only through a subdomain outside the pre-filter | Low | Add the subdomain to `extra` in the pre-filter regeneration SPL (package README) |

## Response Actions

### If confirmed True Positive

1. **Contain:** point the user at the approved AI tools. Block or warn on unapproved providers in the proxy or SSE policy if the organisation does not allow them.
2. **Notify:** the user's manager. For a provider new to the organisation, notify AI governance.
3. **Investigate:** review the new providers' traffic for uploads, and check the entity's upload, DLP and endpoint AI risk for the same week.
4. **Remediate:** decide whether each new provider is allowed, and update proxy policy and the provider registry accordingly. Revoke any personal API keys used on corporate hosts.
5. **Document:** record the providers, the decision per provider and the owner in the case.

### If Benign True Positive

1. Add the host, user, `bunit` or provider to `ai_sanctioned_entities` with an expiry.
2. Record the business justification in `reason`.
3. Close any related aggregator notable as benign.

## Tuning Guidance

### Reducing false positives

| Macro | Ships as | Use |
|---|---|---|
| `hdsi_ai_new_provider_adoption_velocity_filter` | `()` | DNS-path exclusions (`DNS.*`), e.g. resolvers, proxies, DHCP/VPN/VDI pools |
| `..._dns_src_scope` | `(NOT DNS.src="192.168.*")` | Home-LAN addresses from roaming clients. Replace with `()` if your LAN uses 192.168 |
| `..._web_filter` | `()` | Web-path exclusions (`Web.*`). `(Web.user="__web_path_disabled__")` switches the Web path off where `Web` holds only inbound traffic |
| `..._excluded_providers` | Microsoft 365 Copilot, Microsoft Security Copilot | Providers that never count |
| `..._needs_baseline` | `entity_type="system"` | Entities that must have earlier AI activity |
| `..._dns_names`, `..._web_scope` | generated pre-filters | Regenerate when `ai_provider_domains` grows (SPL in the package README) |
| `..._customizations` / `..._risk_score` | `search *` | Post-aggregation hook / last pipe |

Customer-named Azure AI endpoints (`*.openai.azure.com`, `*.services.ai.azure.com`, `*.cognitiveservices.azure.com`) are opt-in because a leading wildcard is costly (about 35 s per 7 days on the largest DNS tenant). See the package README.

### Adjusting thresholds

Copy the rule's SPL, remove the final threshold `where`, run it over the scheduled window (`-21d@d` to `@d`) and append:

```spl
| eval latest_ok=if(latest_adoption>=relative_time(now(),"-2d@d"),1,0)
| stats count by entity_type new_providers latest_ok
```

On the richest DNS tenant, the 2-day report window held 171 hosts with 1 new provider, 38 with 2 and 9 with 3 or more. A threshold of 2 would report about 5 times as many hosts.

If a data model is accelerated for only about a week, the path fails closed. Extend acceleration to 21 days, or scale down together: `dispatch.earliest_time = -8d@d`, `..._window_days = 3`, `..._min_baseline_days = 4` (noisier).

### Adding allowlist entries

```
entity_type,entity,provider,scope,expires,owner,reason,enabled,allow_key
user,jdoe,Anthropic,provider,2027-03-31,security,approved_pilot,1,jdoe|anthropic
group,research,*,group,2027-03-31,security,ai_research_team,1,research|*
group,*,GitHub Copilot,global,2099-12-31,security,copilot_rollout,1,*|github copilot
```

Group keys use the identity `bunit` (users) or the asset `bunit` (hosts).

Read-only live tests on 4 production ES tenants over the scheduled window (`-21d@d` to `@d`). The search and all 3 drilldowns parse on all four; no FATAL or ERROR.

| Tenant | Data | Rows | Runtime | Notes |
|---|---|---|---|---|
| A | About 1.1B DNS events a day; NGFW and enterprise-browser Web with users; both accelerated for 7 days only | 0 | about 200 s | Both paths correctly fail closed. With the short-window settings: about 3 user rows a day (e.g. Gemini + Copilot + OpenAI) |
