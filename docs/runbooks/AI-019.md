# AI-019 - Code Assistant Network Connection

> **Detection ID:** AI-019 (package `hdsi_ai_code_assistant_network_connection`, `detection_id="hdsi_ai_code_assistant_network_connection"`)
> **Search name:** `Network - HDSI AI Code Assistant Network Connection - Rule`
> **Status:** Active, `deployment_type: global` (ships with `enable_alerting: false`)
> **Output:** Risk only (`action.notable = 0`). Notables come from the `Threat - HDSI RBA AI ...` aggregators
> **Risk Score:** Dynamic on `src` (system) and, when exactly one firewall user is seen, `user`: `risk_score = min(50, round(base x risk_multiplier))`, base 25 (active personal-tier Copilot), 15 (other coding assistant), 5 (every firewall session blocked). Literal `_risk` fallback 15 / 15
> **MITRE ATT&CK:** T1588.007 - Obtain Capabilities: Artificial Intelligence (Resource Development)
> **Data Model:** `Network_Traffic` (firewall App-ID) OR `Network_Resolution` (client DNS); either one is enough
> **Schedule:** `20 1 * * *` (daily at 01:20)
> **Lookback Window:** `-1d@d` to `@d` (the previous calendar day); suppression 20 h (`72000s`) per `src`
> **Kill Chain Phase:** `ai_kill_chain_phase="execution"`
> **Last Updated:** 2026-10-09

---

## Overview

This detection reports hosts, and users where the firewall knows them, that ran an **AI coding assistant** during the previous day: GitHub Copilot, Cursor, Windsurf (Codeium), JetBrains AI Assistant, Amazon Q Developer and Kiro, Gemini Code Assist, Tabnine, Sourcegraph Cody, OpenAI Codex, Supermaven and Augment Code. These tools send open source files and repository context to a third-party model, so unsanctioned use is a source-code exposure and governance problem.

The organisation's own GitHub Copilot Business/Enterprise seats are treated as sanctioned and removed. **Personal-tier Copilot** (a personal GitHub account on a corporate machine) scores higher, because the code then leaves the organisation's data-retention and training controls. The typical actor is a developer adopting a tool on their own; a compromised account is unlikely to show up here.

The rule emits one risk event per host per day. It is an informational usage signal: it never raises a notable by itself. It feeds the `shadow_usage` vector of `Threat - HDSI RBA AI Multi-Vector Risk - Rule` and the user risk-threshold aggregators.

v1.0 of this rule (IDE process names in `Network_Traffic.app`, AI hostnames in `dest`, hard-coded `user="unknown"`) returned 0 rows on all four validation tenants. The current logic uses firewall App-ID values and DNS names that only the assistants resolve.

## Detection Logic

### Plain English

1. **App-ID branch:** `tstats` over `Network_Traffic` for sessions whose `app` matches `hdsi_ai_code_assistant_network_connection_app_ids` (for example `github-copilot`, `github-copilot-business`, `cursor`, `codeium`, `openai-codex`, `amazon-codewhisperer`), split by `src`, `user`, `app`.
2. **DNS branch (`append`):** `tstats` over `Network_Resolution` for queries in `hdsi_ai_code_assistant_network_connection_dns_endpoints` (vendor API hostnames, each with and without the trailing root dot), split by `src`, `query`.
3. `hdsi_ai_code_assistant_network_connection_tool_map` turns each App-ID or hostname into `tool`, `provider` and Copilot `license_tier` (`personal`, `organisation`, `unknown`). Unmapped rows are dropped.
4. If the firewall saw exactly one user for a source that day, that user is copied onto the source's DNS rows.
5. A source that resolved org-tier Copilot names at any time that day has its generic Copilot endpoints treated as org-tier too. A source whose only unknown-tier Copilot evidence is telemetry or experiment lookups (idle install) is dropped.
6. Tools in `hdsi_ai_code_assistant_network_connection_sanctioned_tools` (ships as org-tier Copilot) are removed, then `ai_unsanctioned_filter(user,src,provider)` applies the `ai_sanctioned_entities` approvals.
7. Rows are aggregated to one row per `src`. A source with more than `max_users_per_src` (3) firewall users is treated as shared egress and dropped. Optional `unreliable_src` drops roaming addresses with no user (ships off).
8. `ai_risk_multiplier` adds `risk_multiplier` (ES identity `bunit` sensitivity, x1.25 privileged, capped 2.0) and the score is computed.

### Key Fields

| Field | Description | Example Value |
|---|---|---|
| `src` | Host (system risk object) | `10.20.30.40` |
| `user` | Firewall User-ID, only when exactly one user was seen for `src` | `jdoe@example.com` |
| `user_display` | `user`, or "N users: ...", or "no user attribution" | `no user attribution` |
| `tool_list` | Coding assistants seen | `GitHub Copilot (personal), Cursor` |
| `provider` | Registry provider string (used by approvals) | `GitHub Copilot` |
| `license_tiers` | Copilot tier(s) seen | `personal, unknown` |
| `copilot_personal_active` | 1 when `api.`/`proxy.individual.githubcopilot.com` was seen | `1` |
| `evidence_type` | `firewall App-ID`, `DNS` or both | `DNS` |
| `endpoint_sample` | First five App-IDs or hostnames | `api.individual.githubcopilot.com, api2.cursor.sh` |
| `event_count`, `action`, `allowed` | Session/query count, firewall actions, 1 if any session was allowed | `412`, `allow`, `1` |
| `base_score`, `risk_multiplier`, `risk_score` | Scoring inputs and result | `25`, `1.0`, `25` |

### Thresholds

| Parameter | Default Value | Macro | Notes |
|---|---|---|---|
| Users per source | `3` | `hdsi_ai_code_assistant_network_connection_max_users_per_src` | More distinct firewall users on one `src` in a day means proxy/NAT/VDI; the row is dropped |
| Sanctioned tools | `"GitHub Copilot (Business/Enterprise)"` | `hdsi_ai_code_assistant_network_connection_sanctioned_tools` | Add `"GitHub Copilot"` where Copilot is licensed company-wide and the firewall cannot see the tier |
| Unreliable source | `false()` | `hdsi_ai_code_assistant_network_connection_unreliable_src` | Eval expression; matching rows without a user are dropped |
| Score cap | `50` | (in SPL) | Override in `hdsi_ai_code_assistant_network_connection_risk_score` |

## Triage Steps

> **Estimated triage time:** 5-10 minutes. Run the searches over the rule's window (the previous day) or `-7d` for history. Replace `<src>`, `<user>` and `<provider>` with the values from the risk event.

### Step 1: Validate the risk event

```spl
| from datamodel:"Risk.All_Risk"
| search source="Network - HDSI AI Code Assistant Network Connection - Rule" risk_object="<src>"
| table _time risk_object risk_object_type risk_score risk_message
| sort - _time
```

- Read `risk_message`: it names the tools, evidence type, license tier and sample endpoints.
- A risk event every day for the same host is normal for an active user of the tool. The question is whether the tool is approved.

### Step 2: Identify the host and user

```spl
| inputlookup asset_lookup_by_str
| search ip="<src>" OR dns="<src>" OR nt_host="<src>"
| table ip dns nt_host owner priority bunit category
```

```spl
| inputlookup identity_lookup_expanded
| search identity="<user>"
| table identity first last email managedBy priority bunit category
```

- `user` is set only when the firewall saw one user for the host. DNS-only tenants raise system risk only.
- If `src` is a home-network address (`192.168.x.x`) or IPv6 with no user, it is probably a roaming DNS security client and may not be one stable host (see False Positive Scenarios).

### Step 3: Review the evidence

Firewall App-ID sessions (same as the rule's second drilldown):

```spl
| tstats summariesonly=t allow_old_summaries=t count min(_time) as firstTime max(_time) as lastTime values(All_Traffic.dest) as dest values(All_Traffic.action) as action sum(All_Traffic.bytes_out) as bytes_out from datamodel=Network_Traffic where All_Traffic.src="<src>" `hdsi_ai_code_assistant_network_connection_app_ids` by All_Traffic.src All_Traffic.user All_Traffic.app
| rename All_Traffic.* as *
| eval mb_out=round(bytes_out/1024/1024,2)
| convert ctime(firstTime) ctime(lastTime)
| table firstTime lastTime src user app action dest count mb_out
| sort - count
```

DNS evidence, labelled with the rule's own tool map:

```spl
| tstats summariesonly=t allow_old_summaries=t count min(_time) as firstTime max(_time) as lastTime from datamodel=Network_Resolution where DNS.src="<src>" `hdsi_ai_code_assistant_network_connection_dns_endpoints` by DNS.src DNS.query
| rename DNS.* as *
| eval ai_endpoint=query
| `hdsi_ai_code_assistant_network_connection_tool_map`
| convert ctime(firstTime) ctime(lastTime)
| table firstTime lastTime src query tool provider license_tier count
| sort - count
```

- `api.individual.githubcopilot.com` or `proxy.individual.githubcopilot.com` means **active personal-tier Copilot** (completions or chat). `exp.`/`telemetry.individual` alone means a personal account is signed in but idle.
- Org-tier and personal-tier names on the same host usually mean a personal GitHub account on a corporate machine.
- Every firewall session `blocked` means the tool is installed but your policy stopped it (base 5).
- `q.<region>.amazonaws.com` is shared with the AWS console's Amazon Q chat, so it means Amazon Q use, not necessarily an IDE.

### Step 4: Check for related detections

```spl
| from datamodel:"Risk.All_Risk"
| search (risk_object="<src>" OR risk_object="<user>") source="*HDSI AI*"
| stats sum(risk_score) as total_risk dc(source) as detections values(source) as sources by risk_object risk_object_type
| sort - total_risk
```

- Run over `-24h`. The user aggregators fire at 60 (medium, at least two distinct HDSI AI detections) and 90 (critical) in a rolling 24 h (`medium_risk_threshold` / `high_risk_threshold` in `ai_detection_config`).
- Process-level corroboration: `Endpoint - HDSI AI Unsanctioned Desktop App Execution - Rule` (Cursor, Windsurf desktop apps) and `Endpoint - HDSI AI Unsanctioned CLI Execution - Rule`.
- Escalate when coding-assistant use coincides with data-exposure detections (high-volume upload, API key exposure, model file exfiltration).

### Step 5: Determine sanctioned status

```spl
| inputlookup ai_sanctioned_entities
| eval allow_key=lower(allow_key)
| search allow_key IN ("<src>|<provider>", "<user>|<provider>", "<src>|*", "<user>|*", "*|<provider>")
| table entity_type entity provider scope expires owner reason enabled allow_key
```

- Use the lower-cased provider string: `github copilot`, `cursor`, `windsurf`, `amazon q`, `jetbrains ai`, `google gemini`, `openai`, `tabnine`, `sourcegraph`, `kiro`.
- Also check whether the tool is licensed company-wide and only missing from `hdsi_ai_code_assistant_network_connection_sanctioned_tools`.

### Step 6: Make a determination

- **True Positive:** an unsanctioned assistant, or personal-tier Copilot on a corporate host, used against company source code.
- **Benign True Positive:** the tool is approved for this user, host or team (add an approval).
- **False Positive:** the `src` is not one host (roaming address, DNS forwarder, shared egress), or the endpoint is not evidence of tool use (vendor site, AWS console Amazon Q).

---

## True Positive Indicators

- `copilot_personal_active=1`: completions or chat through a personal GitHub Copilot account.
- A tool that is not on the organisation's approved list, with a high daily `event_count` (sustained use, not a one-off install).
- The host belongs to a team that handles regulated or crown-jewel source code, or the user is privileged (`risk_multiplier` > 1).
- The same host also shows organisation-tier Copilot (personal account used alongside the corporate seat).
- Other HDSI AI data-exposure detections for the same user or host in the same 24 h.

## False Positive Scenarios

| Scenario | Likelihood | Mitigation |
|---|---|---|
| Copilot licensed company-wide, but the firewall App-ID cannot see the tier (`github-copilot` covers personal and business). On Tenant A this was 116-132 hosts a day at 15 points | High (App-ID tenants) | Add `"GitHub Copilot"` to `..._sanctioned_tools`; personal-tier Copilot stays reported |
| Roaming DNS security clients log the device's home-LAN or IPv6 address. About half the daily rows on Tenants B and C had such a `src` with no user | High (roaming-DNS tenants) | Map the DNS service's device identity to `src` in the TA, or set `..._unreliable_src` (for example `cidrmatch("192.168.0.0/16",src) OR match(src,":")`) where those ranges are not corporate LANs |
| An internal DNS forwarder appears as the DNS client | Medium | Exclude it in `hdsi_ai_code_assistant_network_connection_dns_filter` |
| VS Code signed in to a personal GitHub account but Copilot idle (`exp.`/`telemetry.individual`) | Medium | Scores 15, not 25. Confirm with Step 3; approve or ask the user to sign out |
| AWS console Amazon Q chat (shares `q.<region>.amazonaws.com`); on Tenant B 6 of 21 Amazon Q sources showed no IDE indicator | Medium | Treat as Amazon Q use; approve `amazon q` if the console assistant is allowed |
| Kiro installed but unused (its telemetry host is still counted; 6 hosts a day on Tenant B) | Low | Approve the host or accept the 15-point signal |
| Approved developer pilot | Medium | Add `user`/`system`/group approval rows (below) |

## Response Actions

### If confirmed True Positive

1. **Contain:** block the tool's App-ID or API hostnames for the host or user, or require the organisation-tier Copilot seat (GitHub enterprise policy blocking personal Copilot on managed devices).
2. **Notify:** the user's manager and the engineering/AppSec owner of the affected repositories.
3. **Investigate:** determine which repositories were open in the IDE during the window, whether any contained secrets or regulated data, and how long the tool has been in use (rerun Step 3 over `-30d`).
4. **Remediate:** remove the unsanctioned extension or IDE, rotate any secrets present in the repositories, and point the user to the approved assistant.
5. **Document:** record findings in the case management system.

### If Benign True Positive

1. Add an approval row to `ai_sanctioned_entities` (common package) with an `expires` date, or add a company-wide tool to `hdsi_ai_code_assistant_network_connection_sanctioned_tools`.
2. Document the business justification in the `reason` field.
3. Close the investigation as "Benign True Positive."

## Tuning Guidance

### Reducing false positives

- Set `..._sanctioned_tools` to every tool licensed for everyone. Prefer adding `"GitHub Copilot"` there over a `*|github copilot` approval: the approval also removes personal-tier Copilot and quiets GitHub Copilot in the suite's DNS and firewall rules.
- Add internal resolvers to `..._dns_filter` and approved developer VDI subnets to `..._filter` (`All_Traffic.*` names).
- Decide on `..._unreliable_src` for roaming-DNS tenants; it ships off because on Tenant A the same expression would have dropped 21 of 224 real rows.
- Add your NGFW's App-ID names to `..._app_ids`; every new DNS endpoint needs a matching `..._tool_map` pattern or its rows are silently dropped.

### Adjusting thresholds

Derive `max_users_per_src` from one or more full days; set it just below the first count that belongs to known shared infrastructure:

```spl
| tstats summariesonly=t allow_old_summaries=t dc(All_Traffic.user) as users from datamodel=Network_Traffic where `hdsi_ai_code_assistant_network_connection_app_ids` All_Traffic.user=* NOT All_Traffic.user="unknown" by All_Traffic.src _time span=1d
| stats max(users) as max_users_per_day by All_Traffic.src
| stats count as srcs by max_users_per_day
| sort max_users_per_day
```

In validation the only App-ID tenant with User-ID had 116 sources with 1 user, 3 with 2 and 1 with 4; the default of 3 drops only the last.

### Adding allowlist entries

The provider part of the key is the lower-cased `provider` string. Host, user, `bunit` group and organisation (`*`) keys are supported:

```
entity_type,entity,provider,scope,expires,owner,reason,enabled,allow_key
system,dev-ws-01,Cursor,provider,2099-12-31,security,approved_cursor_pilot,1,dev-ws-01|cursor
user,jdoe@example.com,Cursor,provider,2026-12-31,security,approved_cursor_pilot,1,jdoe@example.com|cursor
```

A user key also removes the DNS rows of a host where the firewall saw only that user that day. A host with no firewall user, or several, keeps its DNS rows: approve the host instead.
