# AI-011 - Local LLM Framework Execution

> **Detection ID:** AI-011
> **Package:** `hdsi_ai_local_llm_framework_execution` (v1.1.0, deployment type `global`, ships `enable_alerting: false`)
> **Search name:** `Endpoint - HDSI AI Local LLM Framework Execution - Rule`
> **Status:** Active (risk-only: `action.risk = 1`, `action.notable = 0`)
> **Risk Score:** dynamic `risk_score = min(60, round(base x risk_multiplier))`, base 30 (server mode) or 20 (interactive), applied to `user` (when attributable) and `src` (system). Literal `_risk` fallback: user 20, system 15
> **MITRE ATT&CK:** T1588.007 - Obtain Capabilities: Artificial Intelligence (Resource Development)
> **Data Model:** `Endpoint.Processes`
> **Schedule:** `17 * * * *` (hourly at minute 17)
> **Lookback Window:** `-65m@m` to `-5m@m`
> **Suppression:** 24 hours (`86400s`) on `user,src`
> **Kill Chain Phase:** `staging` (multi-vector aggregator vector: `local_tooling`)
> **Last Updated:** 2026-10-09

---

## Overview

This detection finds endpoints running a local large language model runtime: Ollama, LM Studio (app and `lms` CLI), llama.cpp (`llama-server`, `llama-cli`, `llama-run`), llamafile, Jan, GPT4All, KoboldCpp, LocalAI, vLLM, Hugging Face Text Generation Inference, Apple MLX LM and Open WebUI. Python-hosted servers (vLLM, MLX LM, Open WebUI, llama-cpp-python) are found by command line.

Local runtimes bypass every web, CASB and AI-gateway control. Prompts and data never leave the host, so DLP and provider contracts do not apply; the models are unvetted downloads; and in server mode the runtime exposes an unauthenticated inference API that other hosts may reach. The rule writes risk on the user when the process ran under an attributable human account, and on the system. It creates no notable; the AI risk aggregators decide when accumulated risk becomes one.

Typical actors: developers, data scientists and power users experimenting with local models (often legitimate and allow-listable); shadow-IT GPU servers; occasionally an attacker staging an offline model.

## Detection Logic

### Plain English

1. `tstats` on `Endpoint.Processes` selects known runtime executable names (case-insensitive, including `ollama app.exe`, `ollama_llama_server.exe`, `LM Studio.exe` and `koboldcpp*` builds) **or** command lines of the Python-hosted servers (`*vllm serve*`, `*vllm.entrypoints*`, `*mlx_lm.server*`, `*open-webui serve*`, `*llama_cpp.server*`). It groups by `user`, `dest` and `process_name`, keeping `process`, `process_path` and `parent_process_name`.
2. Aliases and command-line matches are normalised to a canonical tool key. Command-line hits count only when the process itself is an interpreter or the runtime launcher (`python*`, `py`, `uvicorn`, `gunicorn`, `vllm`, `mlx_lm.*`, `open-webui`), so `grep`, `pgrep -f` or an editor that mentions the strings is ignored.
3. `hdsi_ai_local_llm_framework_execution_ambiguous_name_check` drops the generic names `lms`, `chat.exe` and `jan` unless the path or command line proves that tool (`.lmstudio` or an LM Studio folder; a `gpt4all`/`nomic.ai` folder; a real Jan install location). `LMS.exe` is also Intel's Local Manageability Service.
4. `ai_process_filter` resolves the key through `ai_tool_processes`; only enabled `usage_type=local_llm` rows with a `dest` remain.
5. `llm_mode=server` when the tool is a server (Ollama, llama-server, vLLM, TGI, LocalAI, Open WebUI, MLX server) or the command line has `serve`, `server`, `--host`, `--listen` or `--port`; otherwise `interactive`.
6. `hdsi_ai_local_llm_framework_execution_nonhuman_accounts` maps service, machine and shared accounts (`SYSTEM`, `LOCAL SERVICE`, `HOST$`, `root`, `ollama`, `ec2-user`, `svc_*`, ...) to no user, so only system risk is written for them.
7. Roll up to one row per `user` + `src`, remove sanctioned entities (`ai_unsanctioned_filter(user,src,provider)`), apply `ai_risk_multiplier` and score.

### Key Fields

| Field | Description | Example Value |
|---|---|---|
| `src` | Host that ran the runtime (system risk object) | `ws-0142` |
| `user` | Attributable human account (user risk object), empty for service/shared accounts | `jdoe` |
| `user_display` | `user`, or "an unattributed account" | `an unattributed account` |
| `tools` | Canonical runtime(s) | `ollama` |
| `llm_mode` | `server` or `interactive` | `server` |
| `process_names`, `process_path`, `process`, `parent_process_name` | Process evidence (up to 5 values) | `ollama.exe`, `C:\Users\...\Ollama\ollama.exe`, `ollama.exe serve` |
| `count`, `firstTime`, `lastTime` | Process events in the window | `3` |
| `sensitivity_level`, `risk_multiplier`, `risk_score` | Identity sensitivity, multiplier, final score | `standard`, `1.0`, `30` |
| `detection_id`, `ai_activity`, `ai_kill_chain_phase` | Constant tags | `hdsi_ai_local_llm_framework_execution`, `local_llm_execution`, `staging` |

### Thresholds

None. Any execution of an enabled `local_llm` tool is reportable. Volume is bounded by the 24-hour suppression on `user,src`: an always-on `ollama serve` yields at most one risk event per user and host per day.

## Triage Steps

> **Estimated triage time:** 10-15 minutes. Replace `$src$` and `$user$` with the values from the risk event. Run risk queries with the time picker on the last 24 hours (7 days for history).

### Step 1: Read the risk event

```spl
| from datamodel:"Risk.All_Risk"
| search source="Endpoint - HDSI AI Local LLM Framework Execution - Rule" (risk_object="$src$" OR risk_object="$user$")
| table _time risk_object risk_object_type risk_score risk_message
| sort - _time
```

- The message names the tool, the mode, the host, the account and the process names.
- A system-only event (no user risk object) means the runtime ran as a service or shared account.

### Step 2: Review the process evidence on the host (7 days)

```spl
| tstats summariesonly=t allow_old_summaries=t fillnull_value="unknown" count min(_time) as firstTime max(_time) as lastTime values(Processes.process) as process values(Processes.process_path) as process_path values(Processes.parent_process_name) as parent_process_name
    from datamodel=Endpoint.Processes
    where Processes.dest="$src$" earliest=-7d (Processes.process_name IN ("ollama*","lmstudio*","lm studio*","lm-studio*","lms","lms.exe","llamafile*","jan","jan.exe","gpt4all*","chat.exe","llama-*","koboldcpp*","localai","local-ai","text-generation-launcher","vllm","open-webui*","mlx_lm.*") OR Processes.process IN ("*vllm serve*","*vllm.entrypoints*","*mlx_lm*","*open-webui serve*","*llama_cpp.server*"))
    by Processes.dest Processes.user Processes.process_name
| rename Processes.* as *
| convert ctime(firstTime) ctime(lastTime)
| table firstTime lastTime dest user process_name process_path process parent_process_name count
| sort - count
```

- Install location: a per-user folder (`AppData\Local\Programs\...`, `~/.lmstudio`) is a user install; `Program Files`, `/usr/local/bin` or a service suggests a managed or admin install.
- Parent process: an installer, a terminal or the user's shell is ordinary; an Office application, script host or remote-management tool is unusual.
- Command line: `serve`, `--host 0.0.0.0` or `--listen` means the runtime is serving an API.
- First seen: a runtime that first appeared today is a new adoption; one present for weeks is established use.

### Step 3: Check whether the runtime is listening on the network

```spl
| tstats summariesonly=t allow_old_summaries=t count values(Ports.process_id) as process_id values(sourcetype) as sourcetype
    from datamodel=Endpoint.Ports
    where (host="$src$" OR host="$src$.*") Ports.dest_port IN (11434,1234,1337,4891,5001,8000,8080) earliest=-24h
    by host Ports.dest Ports.dest_port Ports.transport Ports.state
| rename Ports.dest as bind_addr, Ports.* as *
```

- A bind address other than loopback (`0.0.0.0`, `*`, `::`, the host name or an interface IP) means other hosts can use the unauthenticated API. `Network - HDSI AI Local LLM Listening Port Detected - Rule` (AI-014) raises this with process attribution.

### Step 4: Look for model downloads by the same user or host

```spl
| from datamodel:"Risk.All_Risk"
| search (risk_object="$user$" OR risk_object="$src$") source="* - HDSI AI * - Rule"
| stats sum(risk_score) as total_risk dc(source) as detections values(source) as sources values(ai_kill_chain_phase) as phases by risk_object risk_object_type
| sort - total_risk
```

- `Network - HDSI AI LLM Model File Download - Rule` (AI-013) on the same user or host shows which model source was used.
- Several `local_tooling` detections plus a high-impact vector (uploads, risky access, adversarial) raise the multi-vector notable.

### Step 5: Identify the owner and check sanctioned status

```spl
| inputlookup asset_lookup_by_str
| search ip="$src$" OR dns="$src$" OR nt_host="$src$"
| table ip dns nt_host owner bunit category priority
```

```spl
| inputlookup ai_sanctioned_entities
| where enabled=1 AND (lower(entity)=lower("$user$") OR lower(entity)=lower("$src$") OR entity="*" OR entity_type="group") AND (provider="*" OR lower(provider)="local llm")
| table entity_type entity provider scope expires owner reason allow_key
```

- Data-science, ML-engineering and GPU hosts are commonly approved. A missing or expired entry for an approved team is a tuning gap.

### Step 6: Make a determination

- **True Positive:** an unapproved user or host runs a local LLM runtime, especially in server mode or on a host that handles sensitive data.
- **Benign True Positive:** approved research or engineering use. Allow-list it with an expiry.
- **False Positive:** the matched process is not a local LLM (a generic name with a misleading path). Report it so the corroboration patterns can be tightened.

---

## True Positive Indicators

- A per-user install on a standard corporate workstation in a business unit with no AI approval.
- `llm_mode=server`, particularly with a non-loopback bind address (AI-014 on the same host).
- A recent model download on the same user or host (AI-013), or large uploads of internal data around the same time.
- Runtime started by an unusual parent (script host, remote-management tool) or on a server that should not run interactive tools.

---

## False Positive Scenarios

| Scenario | Likelihood | Mitigation |
|---|---|---|
| Intel Local Manageability Service `LMS.exe` (225 hosts, about 66k inventory events a day on Tenant C, no user or path) | Was the only 7-day match before v1.1 | Dropped by the ambiguous-name check. Do not remove the check |
| Generic `chat.exe` or `jan` from another product | Low | Requires a GPT4All/nomic.ai or Jan install path. Extend the pattern in `_ambiguous_name_check` only for your real install paths |
| Sanctioned data-science workstations and GPU servers | Medium | Add them to `ai_sanctioned_entities` (provider `Local LLM` or `*`), not to the filter macro, so the exemption expires |
| Runtime as a service account accumulating user risk | Low | Add your service-account naming convention to `_nonhuman_accounts`; matching rows still give system risk |
| A tool that only mentions a runtime on its command line (`grep vllm`, `pgrep -f llama_cpp.server`) | None after v1.1 | Command-line hits count only for interpreter/launcher processes |

---

## Response Actions

### If confirmed True Positive

1. **Contain:** if the runtime is serving on the network, stop it or block its port on the host firewall. Remove or quarantine the runtime through endpoint management if policy forbids it.
2. **Notify:** inform the user's manager and the AI governance owner.
3. **Investigate:** identify the models present (Ollama `~/.ollama/models`, LM Studio `~/.lmstudio/models`, Hugging Face cache) and their source (AI-013). Check whether sensitive data was processed locally or exposed through the API, and whether other hosts connected to the port.
4. **Remediate:** uninstall, or move the use case to a sanctioned AI platform. Enforce application control for local LLM runtimes if policy requires it.
5. **Document:** record the tool, mode, models and disposition.

### If Benign True Positive

1. Add the user, host or `bunit` group with provider `Local LLM` (or `*`) to `ai_sanctioned_entities` with an `expires` date, for example:
   ```
   entity_type,entity,provider,scope,expires,owner,reason,enabled,allow_key
   system,ml-gpu-07,Local LLM,provider,2027-03-31,<owner>,<approved GPU workstation>,1,ml-gpu-07|local llm
   ```
2. Document the justification in `reason`.

## Tuning Guidance

### Reducing false positives

- Exclude approved ML labs inside the `tstats` where clause with `hdsi_ai_local_llm_framework_execution_filter`, for example `NOT Processes.dest IN ("ml-lab-*")`. Prefer the sanctioned-entities lookup for named people and hosts.
- Extend `_ambiguous_name_check` patterns only if your build installs LM Studio, GPT4All or Jan to a non-standard path.
- Add your service-account convention to `_nonhuman_accounts` (for example `^svc-`).
- Override the score at the last pipe, `hdsi_ai_local_llm_framework_execution_risk_score`: `eval risk_score=10` in a research tenant, or `eval risk_score=if(llm_mode="server",50,risk_score)` where exposed inference APIs are a policy violation.

### Checking coverage before enablement

The rule is only useful where `Endpoint.Processes` covers workstations and carries `process_path` or `process`:

```spl
| tstats summariesonly=t allow_old_summaries=t count dc(Processes.dest) as hosts
    from datamodel=Endpoint.Processes
    where earliest=-24h
    by sourcetype
| sort - count
```

A tenant that forwards process events only from servers (Tenant B) is blind to this activity; DNS there showed the Ollama site queried by about 160 sources in 7 days that the rule could not see. That is an onboarding gap, not a rule change.
