# AI-043 - AI Usage Following Data Access Spike

> **Detection ID:** AI-043
> **Package:** `hdsi_ai_usage_following_data_access_spike` v1.1.0 (`deployment_type: global`, ships `enable_alerting: false`)
> **Search name:** `Endpoint - HDSI AI Usage Following Data Access Spike - Rule`
> **Status:** Active. Risk-only (`action.notable = 0`). Notables come from the HDSI RBA AI aggregators
> **Risk object:** `user` only (normalised: lowercase, no `DOMAIN\`, no `@suffix`). No system risk
> **Risk score:** dynamic, `min(70, round(base x risk_multiplier x severity_weight))`, base 40 (+10 at 5x `min_files`, +10 at 10x `min_upload_mb`). Literal fallback 40
> **MITRE ATT&CK:** T1039 Data from Network Shared Drive, T1005 Data from Local System (Collection); T1567 Exfiltration Over Web Service (Exfiltration)
> **Data Model:** `Endpoint.Filesystem` plus `Network_Traffic` (firewall App-ID) and/or `Web` (proxy/SSE)
> **Schedule:** `13 * * * *` (hourly at minute 13)
> **Lookback Window:** `-65m@m` to `-5m@m`
> **Suppression:** 4 hours per `user` (`14400s`)
> **Kill Chain Phase:** `collection` (feeds the collection phase of AI-RISK-003)
> **Last Updated:** 2026-10-09

---

## Overview

This detection finds a user who **touches an unusually large number of distinct document and data files and, in the same hour, uploads data to an AI service** (ChatGPT, Gemini, Claude, Perplexity, DeepSeek or an AI API). Collecting files from a share or a local disk and then pasting or attaching them into an AI assistant is a common way for sensitive data to leave the organisation, deliberately or carelessly.

The file side comes from file-share or endpoint per-file auditing in `Endpoint.Filesystem` (Windows 5145/4663, EDR file events, or Microsoft 365 SharePoint/OneDrive events where the add-on maps them). Operating-system, software, servicing and profile paths and binary extensions are excluded, so the count reflects documents and data rather than patching. The upload side comes from firewall App-ID sessions with User-ID (`Network_Traffic`) or proxy/SSE logs with byte counts (`Web`). The two sides are joined on a normalised user name, because file auditing logs the file server as `dest` while network logs record the client as `src`.

The rule writes risk on the user only. It never raises a notable on its own. A single event (typically 40 at provider weight 1.0, lower for low-weight providers, at most 70) is meant to combine with other AI detections in the risk index. AI-RISK-003 (Data Collection Kill Chain) raises a notable when an upload-phase detection follows this collection-phase detection for the same user.

## Detection Logic

### Plain English

1. **File branch.** `tstats` over `Endpoint.Filesystem` counts distinct `file_path` values per user in the window. Only names with an extension count. Actions in `..._excluded_actions` (deleted, failure, blocked, denied, acl_modified), Splunk's own `audittrail` sourcetype, OS/software/profile/replication paths (`..._excluded_paths`) and binary, installer, temporary and shell-metadata extensions (`..._excluded_extensions`) are dropped inside the `where` clause, together with the tenant filter.
2. **User normalisation.** Users are lowercased and stripped of `DOMAIN\` and `@suffix`. Machine accounts (`*$`), `SYSTEM`, service identities and placeholders (`unknown`, `-`) are dropped. A user with at least `..._min_files` (100) distinct files is a spike.
3. **Upload branches** (appended). Firewall App-ID sessions (pre-filtered by `..._app_ids`) and Web requests (`url_domain`, or the SSE app name in `site` when `url_domain` is empty) sum `bytes_out` per user for sessions that were not blocked. `ai_domains_filter` resolves the provider, only `..._usage_types` (web, api, cli, model_registry) count, Microsoft 365 Copilot is excluded, and approved entities are removed with `ai_unsanctioned_filter`. Each branch keeps users at or above `..._min_upload_mb` (5 MB).
4. **Correlation.** The user must appear in the file branch and an upload branch, and the first file access must come before the last upload. Users who uploaded from more than `..._max_upload_srcs` (5) addresses are dropped as shared or generic accounts. If the firewall and the proxy both saw the uploads, the larger total is used, not the sum.
5. **Scoring.** Base 40, +10 when files >= 5x `min_files`, +10 when the upload >= 10x `min_upload_mb`, multiplied by `risk_multiplier` (identity `bunit` sensitivity, x1.25 privileged, cap 2.0) and the highest provider `severity_weight` (0.3 to 1.2), capped at 70.

## Triage Steps

> **Estimated triage time:** 15-25 minutes

Replace `$user$` with the risk object (the normalised key, e.g. `jsmith`). Set the time picker to the alert hour plus a margin, or as noted per step.

### Step 1: Validate the risk event

```spl
| from datamodel:"Risk.All_Risk"
| search source="Endpoint - HDSI AI Usage Following Data Access Spike - Rule" risk_object="$user$"
| table _time, risk_object, risk_object_type, risk_score, risk_message
| sort - _time
```

- Read the risk message: file count, file hosts, MB uploaded, provider and uploading addresses.
- `upload_srcs` = `none logged` means the firewall session had no source address; the user is still attributed.
- Repeated hourly events (every 4 hours after suppression) for the same pair of file host and provider suggest a steady background process (see False Positive Scenarios), not a one-off collection.

### Step 2: Identify the user

```spl
| inputlookup identity_lookup_expanded
| search identity="$user$"
| table identity, first, last, email, bunit, category, priority, managedBy
```

- Is this a person, or a service, backup, scanning or migration account?
- Does the role routinely handle large file sets (records management, legal discovery, data analyst)?

### Step 3: Review the files that were counted

Use drilldown 2 (**View counted file access by $user$**), or:

```spl
| tstats summariesonly=t allow_old_summaries=t count dc(Filesystem.file_path) as files values(Filesystem.file_path) as file_path values(Filesystem.action) as action min(_time) as firstTime max(_time) as lastTime
    from datamodel=Endpoint.Filesystem
    where Filesystem.user="*$user$*" Filesystem.file_name="*.*"
      NOT Filesystem.action IN (`hdsi_ai_usage_following_data_access_spike_excluded_actions`)
      NOT sourcetype IN (`hdsi_ai_usage_following_data_access_spike_excluded_sourcetypes`)
      NOT Filesystem.file_path IN (`hdsi_ai_usage_following_data_access_spike_excluded_paths`)
      NOT Filesystem.file_name IN (`hdsi_ai_usage_following_data_access_spike_excluded_extensions`)
    by Filesystem.user Filesystem.dest sourcetype
| rename Filesystem.* as *
| eval ukey=lower(replace(replace(trim(user),"^.*\x5c",""),"@.*",""))
| search ukey="$user$"
| eval file_sample=mvindex(file_path,0,19)
| convert ctime(firstTime) ctime(lastTime)
| sort - files
| table firstTime, lastTime, user, dest, sourcetype, files, count, action, file_sample
```

- Are the files business documents and data (spreadsheets, exports, contracts, source code, HR or finance folders)?
- Are they in one sensitive share, or spread across application caches and profile folders that the exclusions missed?
- The wildcard pre-filter can pull in similar names; the `ukey` filter keeps only this user (`smith` does not match `jsmith`).

### Step 4: Review the AI upload

Firewall App-ID source (drilldown 3):

```spl
| tstats summariesonly=t allow_old_summaries=t count sum(All_Traffic.bytes_out) as bytes_out sum(All_Traffic.bytes_in) as bytes_in values(All_Traffic.dest) as dest values(All_Traffic.action) as action min(_time) as firstTime max(_time) as lastTime
    from datamodel=Network_Traffic
    where All_Traffic.user="*$user$*" All_Traffic.bytes_out>0
    by All_Traffic.src All_Traffic.user All_Traffic.app
| rename All_Traffic.* as *
| eval ukey=lower(replace(replace(trim(user),"^.*\x5c",""),"@.*",""))
| search ukey="$user$"
| eval mb_out=round(bytes_out/1024/1024,2), mb_in=round(bytes_in/1024/1024,2)
| convert ctime(firstTime) ctime(lastTime)
| sort - mb_out
| head 50
| table firstTime, lastTime, src, user, app, action, count, mb_out, mb_in, dest
```

Proxy/SSE source (drilldown 4). `url_domain` is coalesced with `site`, because some SSE products (app name in `site`) and proxies leave `url_domain` empty:

```spl
| tstats summariesonly=t allow_old_summaries=t count sum(Web.bytes_out) as bytes_out sum(Web.bytes_in) as bytes_in values(Web.url) as url values(Web.http_method) as http_method values(Web.dest) as dest min(_time) as firstTime max(_time) as lastTime
    from datamodel=Web
    where Web.user="*$user$*" (Web.url_domain=* OR Web.site=*)
    by Web.user Web.src Web.url_domain Web.site
| rename Web.* as *
| eval ukey=lower(replace(replace(trim(user),"^.*\x5c",""),"@.*",""))
| search ukey="$user$"
| eval url_domain=coalesce(url_domain,site), mb_out=round(bytes_out/1024/1024,2), mb_in=round(bytes_in/1024/1024,2)
| convert ctime(firstTime) ctime(lastTime)
| sort - mb_out
| head 50
| table firstTime, lastTime, user, src, url_domain, count, mb_out, mb_in, http_method, dest, url
```

- Which App-ID or host carried the bytes? Chat upload App-IDs (`openai-chatgpt-uploading`, `claude-upload`, `google-gemini-uploading`) are stronger evidence than generic or API App-IDs.
- An API App-ID such as `anthropic-api-base` from a server or a developer workstation is usually an integration or a coding agent (see False Positive Scenarios).
- Do the timestamps show files first and uploads shortly after?

### Step 5: Check for related AI risk and aggregator notables

```spl
| from datamodel:"Risk.All_Risk"
| search risk_object="$user$" source="*HDSI AI*"
| stats count as events, sum(risk_score) as total_risk, dc(source) as detections, values(source) as sources, min(_time) as first_seen, max(_time) as last_seen by risk_object, risk_object_type
| convert ctime(first_seen) ctime(last_seen)
```

Run it over the last 24 hours, then 7 days.

- An upload-phase detection (AI-007 High Volume Upload, AI-044 Gradual Exfiltration, AI-020 DLP Violation (incubating, not released), AI-027 Personal Email Correlation) for the same user raises the priority and is what AI-RISK-003 correlates.
- The user aggregators raise notables at 60 (AI-RISK-001) and 90 (AI-RISK-002) rolling 24-hour AI risk from at least two distinct detections.

### Step 6: Determine sanctioned status

```spl
| inputlookup ai_sanctioned_entities
| search enabled=1 (entity="$user$" OR entity="*")
| table entity_type, entity, provider, scope, expires, owner, reason, allow_key
```

- The rule calls `ai_unsanctioned_filter(ukey,src,provider)` with the **normalised** key, so a user approval must be written as the bare lowercase name (`jsmith|openai`). Entries written as `CORP\jsmith` or `jsmith@corp.example` never match this rule.
- Host approvals (`<src>|<provider>`) and identity-group approvals (`<bunit>|<provider>`) also apply.

### Step 7: Make a determination

- **True Positive:** a person collected business data and uploaded a meaningful volume to an unsanctioned AI service within the hour, with no approved workflow.
- **Benign True Positive:** the pairing is real but approved or expected (an approved data-science or AI integration workflow, an approved API integration host). Approve it in `ai_sanctioned_entities`.
- **False Positive:** the file count is background activity (deployment tooling, caches, sync clients) that the exclusions missed, or the account is shared. Tune the exclusions (see Tuning Guidance).

---

## True Positive Indicators

- The counted files are business documents or data exports from a share the user rarely touches, or from a sensitive folder (HR, finance, legal, source code).
- The upload went to a chat upload App-ID or a chat host, in the minutes after the file access, from a single workstation.
- The user has other AI risk in the same day: upload volume, DLP, personal email correlation, or after-hours use.
- The user is in a sensitive `bunit`, or is leaving the organisation (check HR context).
- Repeated pairs on different days, each with different files.

## False Positive Scenarios

Evidence from read-only validation on 4 production ES tenants (Tenant A-D), 2026-10-09.

| Scenario | Likelihood | Mitigation |
|---|---|---|
| Software deployment, patching or profile creation counted as file access (before v1.1, about 90% of files in 100-file user-hours on Tenant A were servicing, `WinSxS`, default-profile, `AppData`, `Program Files` and `ProgramData`) | Low after v1.1 | Already excluded by `..._excluded_paths` / `..._excluded_extensions`. Add your own deployment paths (e.g. `D:\Apps\`) |
| Periodic background pair: a shared account touching about 300 cache files every hour and sending about 1.5 MB to Gemini from 31 addresses (seen on Tenant A in an early round) | Low | Removed by the path exclusions, the 5 MB threshold and the `..._max_upload_srcs` guard. Treat any steady every-hour pair the same way |
| API integration servers and coding agents (`anthropic-api-base` carried about 1.7 GB in 6 hours on Tenant A) whose service account also has file auditing | Medium where such hosts exist | Approve the host (`<src>|anthropic`) or exclude it in `..._network_filter` |
| Backup, indexing, antivirus or migration accounts browsing whole shares | Medium | Exclude them in `..._filter` (`NOT Filesystem.user IN ("svc_backup*")`) |
| Collection at 10:50 and upload at 11:10 (crosses the hourly window) | n/a (missed, not false) | Known limitation of the one-hour window |
| Wrong data in `Endpoint.Filesystem` (logon/share-level events on Tenant A, Splunk `audittrail` on Tenants C and D, SharePoint `action=unknown` on Tenant D) | Low | The extension rule, action deny list and sourcetype exclusion handle what was seen; review your own sourcetype mix |

## Response Actions

### If confirmed True Positive

1. **Contain:** block or restrict the user's access to the AI provider (proxy/SSE or firewall policy). If the uploads continue, consider suspending the session pending review.
2. **Notify:** the user's manager, the data owner of the share, and the data protection or privacy team according to policy.
3. **Investigate:** identify which files were uploaded (SSE/DLP content logs, endpoint telemetry, browser history). Check for the same user's activity in the previous days with the Step 5 search over 7-30 days.
4. **Remediate:** if the provider is a consumer service, request deletion of the conversation data where the provider allows it. Offer the approved AI service if one exists. Review the user's share permissions.
5. **Document:** record files, provider, volume, timeline and disposition in the case.

### If Benign True Positive

1. Add the approval to `ai_sanctioned_entities` (common package) with an expiry: bare user key (`jsmith|openai`), host (`<src>|anthropic`), group (`<bunit>|<provider>`) or organisation-wide (`*|<provider>`).
2. Record the business justification in `reason`.
3. Close the aggregator notable (if any) as benign.

## Tuning Guidance

### Reducing false positives

- Exclude backup, scanning, indexing and migration accounts in `hdsi_ai_usage_following_data_access_spike_filter` (`Filesystem.*` field names).
- Add deployment or application paths to `..._excluded_paths` and bulk-touched extensions to `..._excluded_extensions`.
- Exclude VDI, NAT or integration-server ranges in `..._network_filter` (`All_Traffic.*`) or `..._web_filter` (`Web.*`). Add inbound server sourcetypes (load balancer, WAF, IIS) to `..._web_filter` to make the Web branch faster.
- Add `"ide"` to `..._usage_types` only if coding assistants should count; leave Microsoft 365 Copilot in `..._excluded_providers` unless you want tenant-boundary uploads counted.
- Override the score in `hdsi_ai_usage_following_data_access_spike_risk_score` (last pipe, keep 1-100).

### Adjusting thresholds

The package README (Threshold section) has the full copy-paste SPL for both thresholds. The file-count distribution, per user-hour, with the rule's exclusions:

```spl
| tstats summariesonly=t allow_old_summaries=t values(Filesystem.file_path) as file_path
    from datamodel=Endpoint.Filesystem
    where Filesystem.file_name="*.*"
      NOT Filesystem.action IN (`hdsi_ai_usage_following_data_access_spike_excluded_actions`)
      NOT sourcetype IN (`hdsi_ai_usage_following_data_access_spike_excluded_sourcetypes`)
      NOT Filesystem.file_path IN (`hdsi_ai_usage_following_data_access_spike_excluded_paths`)
      NOT Filesystem.file_name IN (`hdsi_ai_usage_following_data_access_spike_excluded_extensions`)
      `hdsi_ai_usage_following_data_access_spike_filter`
    by _time span=1h Filesystem.user
| rename Filesystem.* as *
| eval ukey=lower(replace(replace(trim(user),"^.*\x5c",""),"@.*",""))
| where NOT match(ukey,"\$$") AND NOT ukey IN ("unknown","-","n/a","null","none","system","local service","network service","anonymous logon")
| stats dc(file_path) as files by _time ukey
| stats count as user_hours, dc(ukey) as users, perc95(files) as p95, perc99(files) as p99, max(files) as max, count(eval(files>=100)) as ge100
```

Set `..._min_files` near the 99th percentile (never below about 25). On a tenant whose only per-file data is SharePoint (Tenant D: at most 11 files per user-hour), lower it to about 25 if the SharePoint path should be able to fire. Re-derive `..._min_upload_mb` per upload source after any change to `ai_provider_apps` or `ai_provider_domains`.
