# AI-044 - HDSI AI Gradual Data Exfiltration Via AI

> **Detection ID:** AI-044 (`detection_id=hdsi_ai_gradual_data_exfiltration_via_ai`)
> **Search name:** `Network - HDSI AI Gradual Data Exfiltration Via AI - Rule`
> **Package:** `saved_searches/packages/hdsi_ai_gradual_data_exfiltration_via_ai` (version 1.1.0, `deployment_type: global`, ships `enable_alerting: false`)
> **Status:** Active, risk only (`action.notable = 0`, `action.risk = 1`). Notables come from the `HDSI RBA AI` aggregators.
> **Risk Score:** 25 to 60 on the `user`, or on `src` (system) when no user is known; each row carries exactly one risk object (computed `risk_score`; literal `_risk` fallback 25 per object)
> **MITRE ATT&CK:** T1567 - Exfiltration Over Web Service; T1030 - Data Transfer Size Limits (Exfiltration)
> **Data Model:** `Network_Traffic` (firewall App-ID, preferred) and/or `Web` (proxy/SSE with byte counts), accelerated for at least 7 days
> **Schedule:** `20 1 * * 6` (weekly, Saturday at 01:20)
> **Lookback Window:** `-7d@d` to `@d` (the 7 complete days Saturday to Friday)
> **Suppression:** `user,src` for 518400 s (6 days), so at most one event per entity per weekly run
> **Kill Chain Phase:** Exfiltration (`ai_kill_chain_phase=exfiltration`)
> **Last Updated:** 2026-10-09

---

## Overview

This detection finds a user who keeps uploading data to AI services across a week, or a known, inventoried host with no user attribution doing the same. It looks for a **large total spread over several days** (default 250 MB on at least 3 days, no single day over half of the total), not one burst. That is the low-and-slow pattern that stays under per-hour upload thresholds such as the 50 MB/h default of AI-007 (`Network - HDSI AI High Volume Upload To AI Service - Rule`).

The business risk is gradual leakage of source code, documents or customer data into AI services, by an insider who knows that large single uploads are watched, or by a well-meaning employee whose daily workflow sends company data to an unapproved service. The rule writes one modest risk event per qualifying entity per week and creates no notable. It feeds the user threshold aggregators, the data-collection kill-chain aggregator (exfiltration stage) and the multi-vector aggregator (`data_exposure` vector).

Version 1.1.0 runs weekly instead of daily (a 7-day window on a very large firewall data model is expensive), does not score pool, NAT or shared addresses as hosts, and counts App-ID variants that carry most AI upload volume.

## Detection Logic

### Plain English

1. **Firewall branch:** `tstats` over `Network_Traffic`, pre-filtered inline to exact AI App-IDs (`..._app_ids`), excluding blocked sessions, summing `bytes_out` per user, src, App-ID and day. App-IDs with no `ai_provider_apps` row are mapped to the provider's domain by `..._app_id_aliases` (ships with `kimi` to `kimi.com`).
2. **Web branch (`append`):** the same daily sum from `Web`, pre-filtered to exact AI domains and SSE app names (`..._web_ai_terms`) in `url_domain` or `site`. The provider is resolved from `url_domain`, or from `site` when `url_domain` is empty. Rows are reduced to one per user, src, provider and day inside the subsearch.
3. **Provider resolution** with `ai_domains_filter`. Only usage types `web`, `api`, `cli`, `model_registry` count; IDE coding assistants and Microsoft 365 Copilot are left out by default. Background (telemetry, CDN) and download-site traffic is dropped.
4. Placeholder users and sources become null; approved users, hosts and groups are removed by `ai_unsanctioned_filter(user,src,provider)`.
5. **Entity** = the user when known, otherwise `src`. Per day, the larger of the firewall and proxy totals is kept, so a session seen by both is not counted twice.
6. **Weekly totals:** `window_mb`, `active_days` (days with at least 1 MB), `max_day_mb`, `max_day_share`, `last_day_mb` (Friday, context only), `src_count`, `daily_mb` (per-day MB list).
7. **Firing conditions:** `window_mb >= 250`, `active_days >= 3`, `max_day_share <= 0.5`; a user seen on more than 20 hosts is dropped as a shared identity; a host-only `src` is scored only when it resolves in `asset_lookup_by_str` and its largest day is no more than 1 GB.

### Scoring

- Tier base: 25 (low, at least 1x `_cumulative_mb`), 35 (medium, 2x), 45 (high, 4x).
- Multiplied by `risk_multiplier` (identity `bunit` sensitivity, x1.25 for privileged identities, capped at 2.0) and by the highest provider `severity_weight` (API usage weighs 1.2).
- `risk_score = min(60, round(base x risk_multiplier x severity_weight))`.

## Triage Steps

> **Estimated triage time:** 20 to 30 minutes. Involve the insider-risk process before contacting the user if the pattern looks deliberate.

### Step 1: Validate the risk event and read the daily pattern

Set the time picker from the start of the rule's window to now (the rule writes its event at about 01:20 on Saturday, after the window ends). Use `entity_search` (backslashes doubled) for `DOMAIN\user` entities.

```spl
| from datamodel:"Risk.All_Risk"
| search source="Network - HDSI AI Gradual Data Exfiltration Via AI - Rule" risk_object="$entity_search$"
| table _time, risk_object, risk_object_type, risk_score, exfil_tier, window_mb, active_days, daily_mb, max_day_mb, max_day_share, provider, evidence, src_count, src_sample, src_asset, src_category, risk_message
| sort - _time
```

- `daily_mb` shows the shape without a drilldown: a steady daily amount (a workflow or a scheduled job) reads differently from a rising one (someone working through a data set).
- Did the entity also fire in previous weeks? A repeated weekly pattern is a habit; a first week is a change.

### Step 2: Identify the user or host

```spl
| inputlookup identity_lookup_expanded where identity="$user$"
| table identity, first, last, email, managedBy, bunit, category, priority, watchlist, startDate, endDate
```

For a host-only entity:

```spl
| inputlookup asset_lookup_by_str where ip="$src$" OR dns="$src$" OR nt_host="$src$"
| table ip, dns, nt_host, owner, bunit, category, priority
```

- Developers and data scientists are the usual heavy API uploaders. Finance, legal, HR and sales roles uploading hundreds of MB a week are unusual.
- An `endDate` in the near future (notice period) or a watchlist entry raises the priority sharply.
- A host-only row on a terminal server, RDS or VDI host (`src_category`) describes several people; identify who was logged on per day.

### Step 3: Daily AI App-ID upload volume

The rule's second drilldown. On a very large firewall data model one entity over 7 days can take more than 5 minutes; start with one or two days from `daily_mb`.

```spl
| tstats summariesonly=t allow_old_summaries=t count sum(All_Traffic.bytes_out) as bytes_out sum(All_Traffic.bytes_in) as bytes_in values(All_Traffic.dest) as dest values(All_Traffic.action) as action from datamodel=Network_Traffic where (All_Traffic.user="$entity_search$" OR All_Traffic.src="$entity_search$") `hdsi_ai_gradual_data_exfiltration_via_ai_app_ids` by All_Traffic.user All_Traffic.src All_Traffic.app _time span=1d
| rename All_Traffic.* as *
| eval day=strftime(_time, "%Y-%m-%d"), mb_out=round(bytes_out/1024/1024, 2), mb_in=round(bytes_in/1024/1024, 2)
| sort 0 day - mb_out
| table day, user, src, app, action, count, mb_out, mb_in, dest
```

- App-IDs tell you the channel: `anthropic-api-base`, `openai-base`/`openai-api`, `deepseek-api` are API traffic (scripts, agentic coding tools); `openai-chatgpt-uploading`, `claude-upload`, `google-gemini-uploading` are file uploads in the chat UI.
- `mb_out` much larger than `mb_in` is upload-heavy; chat and API use is normally request/response balanced or download-heavy.

### Step 4: Daily AI web upload volume

The rule's third drilldown, for proxy or SSE evidence:

```spl
| tstats summariesonly=t allow_old_summaries=t count sum(Web.bytes_out) as bytes_out sum(Web.bytes_in) as bytes_in values(Web.http_method) as http_method values(Web.dest) as dest from datamodel=Web where (Web.user="$entity_search$" OR Web.src="$entity_search$") `hdsi_ai_gradual_data_exfiltration_via_ai_web_ai_terms` by Web.user Web.src Web.url_domain Web.site _time span=1d
| rename Web.* as *
| eval url_domain=coalesce(url_domain, site), day=strftime(_time, "%Y-%m-%d"), mb_out=round(bytes_out/1024/1024, 2), mb_in=round(bytes_in/1024/1024, 2)
| sort 0 day - mb_out
| table day, user, src, url_domain, count, mb_out, mb_in, http_method, dest
```

- SSE products (`site` holds the app name) often record file names, activity (upload, post) and instance (personal or corporate account) in their own console. Pull those for the busiest days.

### Step 5: What is producing the uploads on the host?

Agentic coding tools and scripts send file and repository context with every request. Check the processes on the source host during the busiest days (use the asset name from Step 2 as `dest`):

```spl
| tstats summariesonly=t allow_old_summaries=t count min(_time) as firstTime max(_time) as lastTime values(Processes.process) as process from datamodel=Endpoint.Processes where Processes.dest="<host name>" (Processes.process_name IN ("claude*","codex*","gemini*","aider*","ollama*","python*","node*","curl*","powershell*","pwsh*") OR Processes.process="*openai*" OR Processes.process="*anthropic*") by Processes.dest Processes.user Processes.process_name
| rename Processes.* as *
| convert ctime(firstTime) ctime(lastTime)
| sort - count
```

- An AI CLI or an IDE agent run by the developer explains API volume. A script reading a document share or database export and posting it to an API does not.

### Step 6: Correlate with data access and other risk

```spl
| from datamodel:"Risk.All_Risk"
| search source="* - HDSI AI * - Rule" risk_object IN ("$entity_search$", "<other account formats>")
| stats sum(risk_score) as total_risk dc(source) as detections values(source) as sources values(provider) as providers min(_time) as first max(_time) as last by risk_object, risk_object_type
| convert ctime(first) ctime(last)
| sort - total_risk
```

- AI-043 (Usage Following Data Access Spike), AI-025 (Copy-Paste Correlation To AI Service), AI-038 or the incubating AI-020 (DLP) or AI-007 (hourly upload burst) for the same entity turn volume into evidence of what was sent.
- The data-collection kill-chain aggregator (AI-RISK-003) raises a notable when a collection detection precedes an exfiltration detection for the same entity.

### Step 7: Check approval status

```spl
| inputlookup ai_sanctioned_entities
| eval key_entity=mvindex(split(allow_key, "|"), 0)
| where enabled="1" AND (key_entity=lower("$entity$") OR key_entity=lower("<bunit>") OR key_entity="*")
| table entity_type, entity, provider, scope, expires, owner, reason, allow_key
```

### Step 8: Make a determination

- **True Positive:** sustained uploads of company data to an AI service that is not approved for the user, or of data the user should not share with any AI service.
- **Benign True Positive:** approved developer or data-science API use, an approved enterprise AI workspace, a known integration server.
- **False Positive:** the entity is not one person (shared identity, pool address that slipped through), or the volume is not user content (a mis-classified telemetry or download host).

---

## True Positive Indicators

- The user's role does not explain API or bulk upload use (non-technical role, no approved AI project).
- Upload channels into consumer chat accounts (`*-uploading`, `claude-upload`) rather than an enterprise workspace.
- A rising daily pattern, or uploads that start soon after access to a sensitive repository, share or export (AI-043).
- The user is leaving, on a performance plan, or on a watchlist.
- Volume to a provider without a data-processing agreement (DeepSeek, Kimi/Moonshot or other unvetted services).
- Corroborating DLP, copy-paste or file-access detections in the same week.

---

## False Positive Scenarios

Evidence from read-only tests on 4 production ES tenants (2026-10-09). Tenant A (about 2.6 million AI App-ID sessions a day from about 75,000 users) produced 23 entities in a 7-day reconstruction, all users, mostly API uploads; Tenants B, C and D produced 0 at the defaults.

| Scenario | Likelihood | Mitigation |
|---|---|---|
| Developers using AI APIs or agentic coding tools (0.3 to 3.6 GB a week each on Tenant A, mostly Anthropic and OpenAI API App-IDs) | High | Approve users or groups in `ai_sanctioned_entities`, or raise `_cumulative_mb`. Scores stay 25 to 60 so the aggregators decide |
| Heavy chat users uploading files or screenshots every day | Medium | Same as above; consider an enterprise workspace and exclude it in `_excluded_providers` |
| Pool, VPN, CGNAT, NAT or RDS addresses (73 of 76 host-only addresses above the daily pace on Tenant A were not in the asset inventory; one inventoried RDS host uploaded 7.5 GB a day) | Medium | Handled by `_host_requires_asset` and `_host_max_day_mb`; use `..._customizations` (e.g. `search NOT src_category="*session host*"`) for inventoried multi-user hosts |
| The same traffic as two entities: an inventoried host from the firewall (no User-ID) and a user from the proxy | Low | Triage both together; exclude the host in `..._filter` if the proxy always attributes users |
| Microsoft 365 Copilot traffic (about 1.4 GB a day through an SSE app name in validation) | High if not excluded | Excluded by default in `_excluded_providers` |

### Known blind spots

- A drip that crosses the Saturday boundary is split between two weekly windows. On small tenants the rule can run daily over the same 7-day window (`cron_schedule = 20 1 * * *`).
- A new firewall App-ID not in `_app_ids` is not counted at all; review the firewall's AI App-ID list periodically.
- The Web branch uses exact domains only; a proxy that logs only subdomains (`files.oaiusercontent.com`) is not counted by it.
- The Web branch is an `append` subsearch (50,000 rows, 1,200 s); if it hits either limit the Web evidence is cut short without a warning.
- Detection latency is up to a week; same-day bursts are AI-007's job.

## Response Actions

### If confirmed True Positive

1. **Contain:** block the provider (or the upload App-IDs) for the user at the firewall, proxy or SSE. Revoke or rotate any AI API keys found on the host or in the user's repositories (AI-033).
2. **Preserve:** export the risk event, the daily App-ID and web volumes, SSE activity records and endpoint process history for the window before the user is contacted.
3. **Notify:** the insider-risk or HR process and legal first when intent is suspected; otherwise the user's manager and the data owner.
4. **Investigate:** establish what was uploaded (SSE file names, DLP events, endpoint file access) and whether the provider retains or trains on the data; request deletion through the provider's account if possible.
5. **Remediate:** move legitimate use to an approved enterprise AI service with data-retention controls.
6. **Document:** record the entity, volumes, providers, data involved and actions.

### If Benign True Positive

1. Approve the user, host or group in `ai_sanctioned_entities`, for example:
   ```
   user,jsmith@example.com,Anthropic,provider,2027-03-31,security,approved_api_development,1,jsmith@example.com|anthropic
   group,engineering,OpenAI,group,2027-03-31,security,approved_api_development,1,engineering|openai
   system,10.20.30.40,*,global,2027-03-31,security,approved_ai_integration_server,1,10.20.30.40|*
   ```
2. For a provider covered by an enterprise agreement for everyone, add it to `hdsi_ai_gradual_data_exfiltration_via_ai_excluded_providers`.
3. Record the justification and an expiry.

## Tuning Guidance

### Reducing false positives

- Exclude NAT pools, guest egress, VDI subnets and approved integration servers in `..._filter` (firewall) and `..._web_filter` (Web).
- Add `"ide"` to `..._usage_types` only if coding assistants must be measured too.
- Use `..._customizations` for post-scoring filters, e.g. `search entity_type="user"` to score users only.
- Override `risk_score` (1 to 100) in `hdsi_ai_gradual_data_exfiltration_via_ai_risk_score`.

### Adjusting thresholds

Use the Threshold SPL in the package README: it is the rule's own pipeline without the weekly MB condition and returns, per entity type, the median and 90th percentile weekly MB and how many entities reach 100, 250, 500 and 1,000 MB. Run it over `-7d@d` to `@d` and pick the lowest threshold that gives a reviewable weekly count (for example 10 to 25 entities); do not go below 100 MB. On a very large firewall data model it takes as long as the rule itself (an estimated 20 to 30 minutes on Tenant A), so schedule it rather than running it ad hoc.

Check that acceleration covers 7 days:

```spl
| rest /services/admin/summarization by_tstats=t splunk_server=local count=0
| search summary.id="*Network_Traffic*" OR summary.id="*Web*"
| table summary.id, summary.time_range, summary.complete
```

### App-ID maintenance

When an App-ID is enabled or added in `ai_provider_apps`, add it to `..._app_ids`. Map App-IDs that have no lookup row in `..._app_id_aliases`.
