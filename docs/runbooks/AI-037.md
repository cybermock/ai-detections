# AI-037 - HDSI AI Agent Framework Execution

> **Detection ID:** AI-037 (runbook ID; results carry `detection_id=hdsi_ai_agent_framework_execution`)
> **Search name:** `Endpoint - HDSI AI Agent Framework Execution - Rule`
> **Package:** `hdsi_ai_agent_framework_execution` v1.1.0 (`deployment_type: global`, `enable_alerting: false`)
> **Status:** Active
> **Output:** Risk only (`action.notable = 0`). Aggregators raise the notable.
> **Risk Score:** static: `user` (user) 40, `src` (system) 30. `user` is null for service, system and machine accounts, so those rows give host-only risk. No `risk_score` override ships (the `..._risk_score` hook can set one).
> **MITRE ATT&CK:** T1059 - Command and Scripting Interpreter, T1059.006 - Python (Execution); T1588.007 - Obtain Capabilities: Artificial Intelligence (Resource Development)
> **Data Model:** `Endpoint.Processes` (process name and full command line)
> **Schedule:** `2-59/15 * * * *` (every 15 minutes, at :02, :17, :32, :47)
> **Lookback Window:** `-20m@m` to `-5m@m`
> **Suppression:** 24 h (`86400s`) per `user`, `src`
> **Kill Chain Phase:** `execution` (multi-vector aggregator vector: `local_tooling`)
> **Last Updated:** 2026-10-09

---

## Overview

This detection finds endpoints **launching an autonomous AI agent or agent-orchestration framework**: CrewAI, AutoGen Studio, LangGraph / LangServe, OpenHands (formerly OpenDevin), SWE-agent, MetaGPT, GPT-Engineer, AutoGPT, and older projects such as BabyAGI, SuperAGI, AgentGPT, Devika and Smol Developer. These frameworks let an LLM plan and run multi-step tasks. Many of them run shell commands, edit files and call external APIs without a human approving each step.

An unsanctioned framework is both a shadow-AI finding (company data and credentials handed to an external model through an agent) and a possible execution channel. The typical actor is a developer or data scientist evaluating a framework. Less often it is an automated job, or an attacker using an agent framework as tooling.

The rule matches a framework in two ways: the framework's own CLI as the process name (`crewai.exe`, `autogenstudio`, `langgraph`, `openhands`, `sweagent`, `gpte`, `metagpt`...), or a launcher (`python`, `uv`/`uvx`, `pipx`, `poetry`, `docker`, `podman`) with a framework-specific pattern on its command line.

## Detection Logic

### Plain English

1. Query `Endpoint.Processes` with `tstats` for processes whose `process_name` is a framework CLI (`..._cli_names`), or whose `process_name` is a launcher (`..._launchers`) **and** whose command line matches a framework pattern (`..._cmdline_patterns`). Group by user, host, process name and command line.
2. Drop package management and tests: `pip`/`uv`/`poetry`/`conda`/`npm` install, add, sync and similar subcommands, `python -m pip|venv|pytest|unittest`, and `docker pull|images|ps|logs|rm|...`.
3. Map each command to a `provider` (the framework) and an `agent_class`: `agent_orchestration` for CrewAI, AutoGen, LangGraph and LangChain; `autonomous_agent` for the others. Commands that match no framework are dropped.
4. Null `user` for `unknown`, empty, `SYSTEM`, `root`, `NT AUTHORITY\*`, `LOCAL SERVICE`/`NETWORK SERVICE` and machine accounts (`*$`). Rows without a usable host are dropped. `src` is the host (`dest` in the data model).
5. Remove approvals with `ai_unsanctioned_filter(user,src,provider)`.
6. Aggregate per `user` + `src` and emit with the static scores (user 40, system 30).

### Key Fields

| Field | Description | Example Value |
|---|---|---|
| `user` / `user_display` | Human user (risk object), or `an unattributed or system account` | `jdoe` |
| `src` | Host that ran the framework (risk object) | `ds-ws-031` |
| `provider` | Framework name(s) | `CrewAI` |
| `agent_class` | `agent_orchestration` or `autonomous_agent` | `agent_orchestration` |
| `process_name`, `process` | Launcher/CLI and up to five command lines | `crewai.exe`, `crewai.exe run` |
| `parent_process_name` | Parent (context only; fill varies by tenant) | `powershell.exe` |
| `count` | Process launches in the window | `3` |
| `mitre_attack` | ATT&CK IDs | `T1059, T1059.006, T1588.007` |

### Thresholds

The rule has no count threshold: one framework launch is enough. Scope is controlled by macros:

| Parameter | Default | Macro | Notes |
|---|---|---|---|
| Framework CLI names | 34 names (with `.exe` variants) | `hdsi_ai_agent_framework_execution_cli_names` | Exact `process_name` matches. Add new framework CLIs here |
| Launchers inspected | `python*`, `pythonw*`, `py.exe`, `uv`, `uvx`, `pipx`, `poetry`, `docker`, `podman` | `hdsi_ai_agent_framework_execution_launchers` | Their command line is checked against the patterns |
| Command-line patterns | framework-specific `*pattern*` list | `hdsi_ai_agent_framework_execution_cmdline_patterns` | Keep them specific; bare words cause false positives |

## Triage Steps

> **Estimated triage time:** 10 to 20 minutes. Replace `<user>` and `<src>` with the values from the risk event. Run each search over the time of the risk event (time picker), unless stated otherwise.

### Step 1: Validate the risk event

```spl
| from datamodel:"Risk.All_Risk"
| search source="Endpoint - HDSI AI Agent Framework Execution - Rule" (risk_object="<src>" OR risk_object="<user>")
| table _time, source, risk_object, risk_object_type, risk_score, provider, agent_class, process_name, risk_message
| sort - _time
```

- A user plus system pair (40 + 30) means a real person ran the framework. A system-only event (30) means a service, system or machine account did: usually an automated job or a container host.

### Step 2: Identify the user and host

```spl
| inputlookup identity_lookup_expanded
| search identity="<user>"
| table identity, first, last, email, bunit, category, priority, managedBy
```

```spl
| makeresults
| eval src="<src>"
| lookup asset_lookup_by_str asset as src OUTPUT nt_host, owner, bunit, category, priority
| table src, nt_host, owner, bunit, category, priority
```

- Developer or data-science workstation, CI runner, or a server? A framework on a production server or a non-technical user's laptop is the unusual case.

### Step 3: Review the framework process activity

The rule's second drilldown:

```spl
| tstats summariesonly=t allow_old_summaries=t count min(_time) as firstTime max(_time) as lastTime values(Processes.parent_process_name) as parent_process_name from datamodel=Endpoint.Processes where Processes.dest="<src>" (Processes.process_name IN (`hdsi_ai_agent_framework_execution_cli_names`) OR (Processes.process_name IN (`hdsi_ai_agent_framework_execution_launchers`) AND Processes.process IN (`hdsi_ai_agent_framework_execution_cmdline_patterns`))) by Processes.user Processes.dest Processes.process_name Processes.process
| rename Processes.* as *
| convert ctime(firstTime) ctime(lastTime)
| table firstTime, lastTime, user, dest, process_name, process, parent_process_name, count
| sort - count
```

What to look for:

- **Run versus setup.** `crewai run`, `langgraph dev`, `autogenstudio ui`, `python -m openhands...` or `docker run .../openhands` mean an agent ran. Scaffolding and housekeeping commands also match and score the same (see False Positives).
- **Where it runs.** A container (`docker run`) with the host's home directory or Docker socket mounted gives the agent wide access.
- **Who started it.** An interactive shell or IDE parent means a person; a scheduler or service parent means automation.

### Step 4: Check what the agent did

The rule's third drilldown lists children of framework CLIs:

```spl
| tstats summariesonly=t allow_old_summaries=t count values(Processes.process) as process from datamodel=Endpoint.Processes where Processes.dest="<src>" Processes.parent_process_name IN (`hdsi_ai_agent_framework_execution_cli_names`) by Processes.user Processes.parent_process_name Processes.process_name
| rename Processes.* as *
| sort - count
| head 100
```

- Python-hosted agents show `python` as the parent, which is too common to pivot on. For those, check `Endpoint - HDSI AI Agent Autonomous Action Detection - Rule` risk on the same host, which categorises agent-run commands (secret reads, persistence, system changes).
- Check network activity from the host to AI provider APIs in the same period (AI DNS and API detections).

### Step 5: Check for related detections

```spl
| from datamodel:"Risk.All_Risk"
| search (risk_object="<user>" OR risk_object="<src>") source="*HDSI*"
| stats sum(risk_score) as total_risk dc(source) as detections values(source) as sources by risk_object, risk_object_type
| sort - total_risk
```

- 40 user points is two thirds of the medium threshold of `Threat - HDSI RBA AI User Risk Threshold Exceeded - Rule` (60, at least two distinct HDSI AI detections). One more AI detection on the same user the same day raises the notable.
- This rule counts as `local_tooling` in `Threat - HDSI RBA AI Multi-Vector Risk - Rule`, and as execution-phase risk in `Threat - HDSI RBA AI Privilege Escalation Correlation - Rule`.

### Step 6: Determine sanctioned status

```spl
| inputlookup ai_sanctioned_entities
| where enabled=1 AND (lower(entity)=lower("<user>") OR lower(entity)=lower("<src>") OR match(allow_key, "^\*\|"))
| table entity_type, entity, provider, scope, expires, owner, reason, allow_key
```

- The provider in allow-list keys is the framework name in lower case (`crewai`, `langgraph`, `openhands`...).

### Step 7: Make a determination

- **True Positive:** an unsanctioned framework ran on a host or by a user where agents are not approved, or it ran with access to sensitive data or credentials.
- **Benign True Positive:** an approved developer team, a sanctioned pilot or a CI pipeline building an agent project.
- **False Positive:** a command that only installs, scaffolds, builds or inspects a framework without running an agent, or a path that merely contains a framework name.

---

## True Positive Indicators

- The framework ran on a server, a shared host or a non-developer's machine.
- Long-running agent servers (`langgraph dev`, OpenHands, AutoGen Studio) exposed on the host, or containers with broad mounts.
- `Endpoint - HDSI AI Agent Autonomous Action Detection - Rule` reports credential access, persistence or system changes on the same host.
- The user is not part of an approved AI or engineering programme.
- AI API traffic from the same host to providers that are not sanctioned.

---

## False Positive Scenarios

Evidence from the 2026-10-09 validation on 4 production ES tenants (package README and validation notes):

| Scenario | Likelihood | Mitigation |
|---|---|---|
| Developer or data scientist evaluating a framework | High where frameworks are adopted | Allow-list the user, host or `bunit` group with an expiry |
| CI runner building or testing an agent project | Medium | `..._filter` (`NOT Processes.dest IN ("ci-runner-*")`) or an allow-list entry for the host |
| Scaffolding, build and inspection commands not excluded: `crewai install`, `uvx crewai create`, `python -c "import crewai; ..."`, `docker build -t crewai-app .`, `docker compose logs/pull/ps <framework>` | Medium | They score like a run (user 40, system 30). Drop them in `..._customizations`, e.g. `search NOT process="*docker compose*"` |
| Project path or temp folder that contains a framework name | Low | Patterns are framework-specific on purpose. In live data `*gpte*`, `*dify*` and `*n8n*` hit temp-folder names and Windows Update arguments, and an unrelated `Interpreter.exe` exists; do not widen to bare words |
| Long-running agent server restarted several times | Low | One event per user and host per day (24 h suppression) |

## Response Actions

### If confirmed True Positive

1. **Contain:** stop the framework process or container; block the host's access to unsanctioned AI APIs if data exposure is likely.
2. **Notify:** the user's manager and the AI governance or platform team.
3. **Investigate:** review what the agent ran (Step 4, and Agent Autonomous Action risk), which API keys it used (`.env`, environment variables) and which data it could reach.
4. **Remediate:** rotate API keys and credentials available to the agent; remove the framework or move it to an approved, sandboxed environment; document the approved path for agent experiments.
5. **Document:** record findings in the case.

### If Benign True Positive

1. Add the user, host or group to `ai_sanctioned_entities` with an `expires` date and the justification in `reason`.
2. Exclude CI runners in `..._filter`.
3. Close the related aggregator notable (if any) as benign.

## Tuning Guidance

### Reducing false positives

- Prefer `ai_sanctioned_entities` entries (`user|provider`, `host|*`, `group|provider`) over editing the scope macros.
- Use `hdsi_ai_agent_framework_execution_filter` for inline `tstats` exclusions (`NOT Processes.user IN ("svc_ci*")`).
- Use `hdsi_ai_agent_framework_execution_customizations` for post-aggregation exclusions (`search NOT provider="LangGraph"`).
- Use `hdsi_ai_agent_framework_execution_risk_score` (last pipe) to set a numeric `risk_score` (`min(100, ...)`); it overrides both static scores for that row.

### Adjusting thresholds

There is no count threshold. Before enabling, list existing framework users and hosts over 7 days and load the sanctioned ones into the allow-list:

```spl
| tstats summariesonly=t allow_old_summaries=t count min(_time) as firstTime max(_time) as lastTime from datamodel=Endpoint.Processes where (Processes.process_name IN (`hdsi_ai_agent_framework_execution_cli_names`) OR (Processes.process_name IN (`hdsi_ai_agent_framework_execution_launchers`) AND Processes.process IN (`hdsi_ai_agent_framework_execution_cmdline_patterns`))) earliest=-7d by Processes.user Processes.dest Processes.process_name
| rename Processes.* as *
| convert ctime(firstTime) ctime(lastTime)
| sort - count
```

### Adding allowlist entries

`ai_sanctioned_entities.csv` in `hdsi_ai_rba_common` (lower-case keys `<entity>|<provider>`):

```
entity_type,entity,provider,scope,expires,owner,reason,enabled,allow_key
group,data science,CrewAI,group,<YYYY-MM-DD>,<your_name>,<justification>,1,data science|crewai
system,ml-build-02,*,global,<YYYY-MM-DD>,<your_name>,<justification>,1,ml-build-02|*
```

Validation summary (read-only, 2026-10-09, 4 production ES tenants): the rule and its 3 drilldowns parse on Tenants A to D, and 24 h and 7 d runs returned 0 rows everywhere with no FATAL/ERROR messages (command-line fill 93% to 100%). No real agent-framework activity existed on any tenant in 7 days, so true positives are proven by a synthetic `makeresults` test of the full pipeline on Tenant A: 14 command lines gave exactly the 7 expected detections (including `langgraph dev` as SYSTEM and `gpte` as a machine account, both system-only) and dropped the 7 expected non-detections (`pip install`, `uv pip install`, `docker pull`, a username path, `python -m pytest`, a project path containing `langchain`, an unknown host). Expected volume today: 0 a day on all four tenants; where frameworks are adopted, at most one event per user and host per day.
