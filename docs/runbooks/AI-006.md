# AI-006 - HDSI AI API Access From Non-Dev Endpoint

> **Detection ID:** AI-006
> **Package:** `hdsi_ai_api_access_from_non_dev_endpoint` (v1.1.0, `deployment_type: global`, requires `hdsi_ai_rba_common`)
> **Search name:** `Network - HDSI AI API Access From Non-Dev Endpoint - Rule`
> **Status:** Active. Risk-only (`action.notable = 0`, `action.risk = 1`); the HDSI RBA AI aggregators decide when accumulated risk becomes a notable.
> **Risk Objects / Score:** `src` (system) and `user` (only when exactly one firewall or proxy user was seen for the host). Dynamic `risk_score = min(50, round(base x severity_weight x risk_multiplier))`, base 20 (5 when every firewall session was blocked). Typical values 6 to 24. Literal fallback 24 / 24.
> **MITRE ATT&CK:** T1588.007 (Obtain Capabilities: Artificial Intelligence), T1102 (Web Service), T1567 (Exfiltration Over Web Service)
> **Data Model:** `Network_Resolution` OR `Network_Traffic` (NGFW App-ID) OR `Web` (any one is enough)
> **Schedule:** `45 1 * * *` (daily at 01:45)
> **Lookback Window:** `-1d@d` to `@d` (the previous calendar day)
> **Suppression:** 20 h (`72000s`) on `src,user`; one row per host, so in effect one risk event per host per day
> **Kill Chain Phase:** `execution` (`ai_kill_chain_phase`)
> **Last Updated:** 2026-10-09

---

## Overview

This detection finds hosts that call **AI provider APIs**, such as `api.openai.com`, `api.anthropic.com`, AWS Bedrock, GCP Vertex AI, Azure OpenAI, DeepSeek, Deepgram or OpenRouter, even though nothing else suggests a developer works on them. A developer laptop or build server calling an LLM API is normal. A kiosk, line-of-business workstation, office PC or production server doing the same is usually one of these:

- a script or agent using a personal API key;
- a browser extension or desktop tool that calls the API directly;
- a third-party product that sends business data to an AI vendor.

Each of these moves data outside the sanctioned AI channels. LLM-enabled malware uses the same APIs.

"Developer" is decided by what the host does in the same day. A host that reaches package registries (npm, PyPI, Maven and others), container registries, VS Code or JetBrains update services, or the GitHub Copilot and Cursor APIs is a developer endpoint and is not reported. A host that also used the same provider's consumer chat app that day (for example `claude.ai` and `api.anthropic.com`) is not reported for that provider either, because the desktop and web apps call the API hostname themselves.

The rule writes one risk event per host per day. It never writes a risk event on an `unknown` or empty object.

## Detection Logic

### Plain English

1. **Collect one day of evidence** with three chained `tstats prestats=t append=t` calls in the main pipeline (no `append` subsearches, so no 60 s subsearch truncation):
   - `Network_Resolution`: `DNS.query` by `DNS.src`. Names are matched with and without the trailing root dot that some resolvers log.
   - `Web`: `Web.url_domain` **or** `Web.site` by `Web.src`, `Web.user`. `fillnull_value="unknown"` keeps rows where `site` is empty, and `ai_domain = lower(coalesce(url_domain, site))`.
   - `Network_Traffic`: firewall App-ID (`All_Traffic.app`, for example `anthropic-api-base`, `openai-api`) by `src`, `user`, `action`.
   Each branch is pre-filtered to three hostname lists: AI API endpoints, consumer AI app front-ends and developer-tooling names.
2. **Developer fingerprint:** any developer-tooling hostname or App-ID (`github-base`, `gitlab-base`, `visual-studio*`, `docker*`, ...) on the host that day sets `dev_tooling=1`. The host is not reported.
3. **Provider resolution:** App-IDs are mapped by `..._app_id_map`; everything then goes through `ai_domains_filter`. Only `usage_type="api"` rows remain.
4. **Consumer-app check:** if the host also reached that provider's own chat app (`claude.ai`, `chatgpt.com`, `gemini.google.com`, App-ID `claude-base`, `openai-chatgpt`, ...), the API row for that provider is dropped.
5. **Exclusions:** `..._excluded_providers` (GitHub Copilot, Cursor, Suno), `..._sanctioned_endpoints`, resolver and developer asset categories, `..._dev_sources`, and approvals in `ai_sanctioned_entities` via `ai_unsanctioned_filter(user,src,provider)`.
6. **Asset gate:** the host must be in the ES asset inventory (`asset_lookup_by_str`, by `ip`) or carry a user (`..._require_known_asset = 1`).
7. **Aggregate per `src`.** `user` is set only when exactly one user was seen. More than `..._max_users_per_src` (3) users means shared egress (NAT, VDI, terminal server), and the row is dropped.
8. **Score:** base 20 (5 when every firewall session was blocked) x `severity_weight` (1.2 for the main LLM and cloud AI APIs, 1.0 for speech and aggregator APIs, 0.8 for Azure AI Services) x `risk_multiplier` (identity `bunit` sensitivity, 1.0 without a user), capped at 50.

### Key Fields

| Field | Description | Example Value |
|---|---|---|
| `src` | Host that called the API (system risk object) | `10.20.30.40` |
| `user` | Single firewall or proxy user for the host, otherwise empty | `jdoe@example.com` |
| `user_display` | User, "N users: ...", or "no user attribution" | `no user attribution` |
| `provider_list` / `providers` | AI providers whose API was reached | `Anthropic, AWS Bedrock` |
| `endpoint_sample` | Up to 5 API endpoints | `api.anthropic.com, bedrock-runtime.us-east-1.amazonaws.com` |
| `evidence_type` | Which data paths saw it | `DNS + Web proxy` |
| `src_asset` / `src_category` | ES asset name and de-duplicated category, or `no asset category` / `not in asset inventory` | `kiosk\|workstation` |
| `event_count` | DNS queries, proxy requests or firewall sessions in the day | `412` |
| `allowed` | 0 when every firewall session was blocked | `1` |
| `base_score`, `severity_weight`, `risk_multiplier`, `risk_score` | Scoring inputs and result | `20, 1.2, 1.0, 24` |

### Thresholds

| Parameter | Default Value | Macro | Notes |

## Triage Steps

> **Estimated triage time:** 10-15 minutes. There is no notable for this rule. You reach it from an HDSI RBA AI aggregator notable or from a risk event on the host or user. Set the time picker to the day the risk event covers (the rule reads the previous calendar day).

### Step 1: Validate the risk event

```spl
| from datamodel:"Risk.All_Risk"
| search source="Network - HDSI AI API Access From Non-Dev Endpoint - Rule" risk_object="$src$"
| table _time, risk_object, risk_object_type, risk_score, risk_message
| sort - _time
```

- The risk message names the providers, the evidence type (DNS, Web proxy, firewall App-ID), the asset category and the user.
- A score of 5 or 6 means every firewall session was blocked: an attempt, not a confirmed data flow.

### Step 2: Identify the host and its owner

```spl
| inputlookup asset_lookup_by_str where ip="$src$"
| table asset, ip, dns, nt_host, owner, bunit, category, priority
```

- Is this a kiosk, shared workstation, line-of-business PC or a production server?
- If it is actually a developer or build machine, the fix is the asset category (see Tuning Guidance), not a ticket.

If the risk event names a user:

```spl
| inputlookup identity_lookup_expanded where identity="$user$"
| table identity, first, last, email, managedBy, bunit, category, priority
```

### Step 3: Review the evidence for the day

DNS (the most portable path; no user):

```spl
| tstats summariesonly=t allow_old_summaries=t count min(_time) as firstTime max(_time) as lastTime
    from datamodel=Network_Resolution
    where DNS.src="$src$" (`hdsi_ai_api_access_from_non_dev_endpoint_api_endpoints(DNS.query)` OR `hdsi_ai_api_access_from_non_dev_endpoint_app_endpoints(DNS.query)` OR `hdsi_ai_api_access_from_non_dev_endpoint_dev_endpoints(DNS.query)`)
    by DNS.src DNS.query
| rename DNS.* as *
| convert ctime(firstTime) ctime(lastTime)
| sort - count
```

Firewall App-ID (user, action and bytes):

```spl
| tstats summariesonly=t allow_old_summaries=t count sum(All_Traffic.bytes_out) as bytes_out values(All_Traffic.dest) as dest min(_time) as firstTime max(_time) as lastTime
    from datamodel=Network_Traffic
    where All_Traffic.src="$src$" (`hdsi_ai_api_access_from_non_dev_endpoint_app_ids` OR `hdsi_ai_api_access_from_non_dev_endpoint_dev_app_ids`)
    by All_Traffic.src All_Traffic.user All_Traffic.app All_Traffic.action
| rename All_Traffic.* as *
| eval mb_out=round(bytes_out/1024/1024,2), dest=mvindex(dest,0,4)
| convert ctime(firstTime) ctime(lastTime)
| table firstTime, lastTime, src, user, app, action, count, mb_out, dest
| sort - count
```

Proxy (handles proxies that fill `url_domain`, `site`, or only one of them):

```spl
| tstats summariesonly=t allow_old_summaries=t fillnull_value="unknown" count sum(Web.bytes_out) as bytes_out values(Web.http_user_agent) as http_user_agent min(_time) as firstTime max(_time) as lastTime
    from datamodel=Web
    where Web.src="$src$" (Web.url_domain=* OR Web.site=*)
    by Web.user Web.src Web.url_domain Web.site
| rename Web.* as *
| eval url_domain=coalesce(nullif(url_domain,"unknown"),nullif(site,"unknown")), mb_out=round(bytes_out/1024/1024,2)
| convert ctime(firstTime) ctime(lastTime)
| table firstTime, lastTime, user, src, url_domain, count, mb_out, http_user_agent
| sort - count
```

- Look at the API hostnames and the steadiness of the traffic. Round-the-clock calls from a server point to an integration. Short bursts during working hours from a workstation point to a person or a desktop tool.
- `http_user_agent` values such as `python-requests`, `node-fetch`, `curl` or an SDK name confirm programmatic use. A vendor product name points to embedded AI in third-party software.
- Upload volume (`mb_out`) shows how much data left the host.

### Step 4: Rule out a developer host the rule missed

Run the DNS query from Step 3 over the last 7 days. If developer-tooling names (`registry.npmjs.org`, `pypi.org`, `update.code.visualstudio.com`, ...) appear on other days, this is a developer host that did not pull a package on the reported day. Label it in the asset inventory or add it to `..._dev_sources`.

### Step 5: Check for related AI risk on the same objects

```spl
| from datamodel:"Risk.All_Risk"
| search risk_object IN ("$src$","$user$") source="*HDSI AI*"
| stats sum(risk_score) as total_risk dc(source) as detections values(source) as rules count as events by risk_object, risk_object_type
| sort - total_risk
```

- This rule belongs to the `shadow_usage` vector of `Threat - HDSI RBA AI Multi-Vector Risk - Rule`.
- The user aggregators raise a medium notable at 60 points from at least two detections and a high notable at 90 points in 24 hours.
- Upload, DLP or key-exposure detections on the same object make the API use much more serious.

### Step 6: Determine sanctioned status

```spl
| inputlookup ai_sanctioned_entities
| where tonumber(enabled)=1 AND (lower(entity)=lower("$src$") OR lower(entity)=lower("$user$") OR entity="*")
| table entity_type, entity, provider, scope, expires, owner, reason, allow_key
```

- Approval keys are `<src>|<provider>`, `<user>|<provider>`, `<bunit>|<provider>` or `*|<provider>`, all lowercase. The provider string is the one in the risk message, for example `gcp vertex ai`.
- An expired row (`expires` in the past) no longer applies.

### Step 7: Make a determination

- **True Positive:** an unapproved script, tool or person sends data to an AI API from a non-developer host.
- **Benign True Positive:** an approved integration or a known vendor product (for example speech-to-text on kiosks). Approve it so it stops scoring.
- **False Positive:** a developer host that is not labelled, a DNS server reported as the client, or a roaming address shared by several laptops. Fix the classification.

---

## True Positive Indicators

- The host is a non-technical workstation (finance, HR, front office) with no developer tooling on any day.
- `http_user_agent` is a scripting library or SDK, and the user is not in an approved AI programme.
- The provider is not one the organisation licenses, for example a personal OpenAI or DeepSeek key, OpenRouter, or a model aggregator.
- Upload volume to the API host is large or rising.
- The same user or host also has upload, DLP, key-exposure or after-hours AI risk.

## False Positive Scenarios

Evidence is from read-only live tests on 4 production ES tenants (Tenant A-D) on 2026-10-09.

| Scenario | Likelihood | Mitigation |
|---|---|---|
| Embedded vendor AI on shared kiosks and line-of-business PCs. On Tenant A, 17 of 36 daily rows were `api.deepgram.com` (speech-to-text) from kiosks, almost certainly a third-party application | High (where such software exists) | After one governance review, approve it with `..._sanctioned_endpoints` (`"api.deepgram.com"`) or per host in `ai_sanctioned_entities` |
| Production servers calling cloud AI (Tenant A: 6 servers calling GCP Vertex AI all day, 2 also Azure AI Services) | Medium | Approve per host: `<server ip>\|gcp vertex ai`. If the organisation runs its own endpoint, add it to `..._sanctioned_endpoints` (for example `"contoso-*.openai.azure.com"`) |
| Developer host not labelled and without tooling that day | Medium | Fix the asset category (matched by `..._dev_categories`) or add the range to `..._dev_sources` |
| Roaming DNS security client reporting a home-network `192.168.x.x` or IPv6 address (Tenant B: 3 of 5 daily rows) that several laptops share | Medium on roaming-DNS tenants | Set `..._unreliable_src`, for example `cidrmatch("192.168.0.0/16",src) OR match(src,":")` |
| DNS server or forwarder recorded as the client (Tenant A: domain controllers were 18 of 45 API sources before exclusions) | Low after shipping defaults | Label resolvers in the asset inventory (`..._resolver_categories`) or exclude their IPs in `..._filter` |

## Response Actions

### If confirmed True Positive

1. **Contain:** block the API hostname for the host or its network segment at the proxy or firewall, or stop the script or service on the host.
2. **Notify:** inform the host owner's manager and the data governance or AI governance team.
3. **Investigate:** find the process that makes the calls (EDR network connections on the host), how the API key was obtained (personal account or corporate), and what data was sent. Check for the same key or tool on other hosts.
4. **Remediate:** revoke the API key with the provider, remove the tool, and route the business need to a sanctioned AI service.
5. **Document:** record the findings in the case management system.

### If Benign True Positive

1. Approve the integration: add a row to `ai_sanctioned_entities` (common package) with an `allow_key` such as `<src>|<provider lowercase>` and an expiry date, or add the endpoint to `hdsi_ai_api_access_from_non_dev_endpoint_sanctioned_endpoints` if it is approved for everyone.
2. Record the business justification in the `reason` field.
3. If an aggregator notable was raised, close it as Benign True Positive and reference the approval.

## Tuning Guidance

### Reducing false positives

- Keep the asset inventory accurate. Developer, build and resolver categories drive two exclusions.
- Approve known integrations once, per host or per endpoint, instead of raising thresholds.
- On roaming-DNS tenants, set `..._unreliable_src`.
- Large tenants: the full-day run took about 230 s on the largest validation tenant. Leave the 01:45 schedule outside the busiest scheduler window.

### Adjusting thresholds

Derive `..._max_users_per_src` from full days of firewall User-ID (repeat with `Web.user`/`Web.src` for proxies). Set it just below the first source count that belongs to known shared infrastructure:

```spl
| tstats summariesonly=t allow_old_summaries=t dc(All_Traffic.user) as users from datamodel=Network_Traffic
    where `hdsi_ai_api_access_from_non_dev_endpoint_app_ids` All_Traffic.user=* NOT All_Traffic.user="unknown"
    by All_Traffic.src _time span=1d
| stats max(users) as max_users_per_day by All_Traffic.src
| stats count as srcs by max_users_per_day
| sort max_users_per_day
```

### Key tuning macros

| Macro | Ships as | Use |
|---|---|---|
| `hdsi_ai_api_access_from_non_dev_endpoint_filter` / `_web_filter` / `_app_filter` | `()` | Inline exclusions per branch (`DNS.*`, `Web.*`, `All_Traffic.*` names) |
| `..._sanctioned_endpoints` | `"__none__"` | Endpoints approved for everyone, wildcards allowed |
| `..._excluded_providers` | `"GitHub Copilot","Cursor","Suno"` | Providers never reported |
| `..._dev_categories` / `..._resolver_categories` | regexes | Asset categories treated as developer or DNS server |
| `..._dev_sources` / `..._unreliable_src` | `false()` | Eval expressions for unlabelled developer networks or roaming addresses |
| `..._customizations` / `..._risk_score` | `search *` | Post-aggregation hook; last-pipe score override (keep `risk_score` at or below 100) |

### Adding allowlist entries

To approve one host for one provider (columns of `ai_sanctioned_entities`):
```
entity_type,entity,provider,scope,expires,owner,reason,enabled,allow_key
system,<src>,GCP Vertex AI,provider,<YYYY-MM-DD>,<your_name>,<justification>,1,<src>|gcp vertex ai
```
