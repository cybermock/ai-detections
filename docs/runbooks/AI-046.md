# AI-046 - MCP Server Execution

> **Detection ID:** AI-046 (package `hdsi_ai_mcp_server_execution`, `detection_id=hdsi_ai_mcp_server_execution`)
> **Search name:** `Endpoint - HDSI AI MCP Server Execution - Rule`
> **Status:** Active, version 1.1.0, `deployment_type: global`, ships with `enable_alerting: false`
> **Output:** Risk only (`action.notable = 0`). Notables come from the HDSI RBA AI aggregators.
> **Risk Score:** computed `risk_score = min(60, base_score x risk_multiplier)`, applied to both `user` and `src` (static `_risk` fallback: user 30, system 20). `base_score` is 40, 30 or 15 (see Thresholds)
> **MITRE ATT&CK:** T1059 - Command and Scripting Interpreter (Execution); T1588.007 - Obtain Capabilities: Artificial Intelligence (Resource Development)
> **Data Model:** `Endpoint.Processes` (accelerated, with full command lines)
> **Schedule:** `4-59/15 * * * *` (every 15 minutes)
> **Lookback Window:** `-20m@m` to `-5m@m`
> **Suppression:** `user,src` for 86400s (one risk event per user and host per day)
> **Kill Chain Phase:** `execution`
> **Last Updated:** 2026-10-09

---

## Overview

This detection finds Model Context Protocol (MCP) servers running on endpoints. An MCP server is the bridge that lets an AI assistant or agent (Claude Desktop, Claude Code, Cursor, VS Code Copilot agent mode, Codex and similar) read files, query databases, drive a browser, or call source-control and SaaS APIs on the user's behalf. An unsanctioned MCP server is a shadow-AI finding. It is also a data-access path that bypasses normal application controls: whatever the user can reach, the agent can reach.

The typical actor is a developer or power user wiring an AI client to local resources. Less often it is an attacker who uses an agent framework with MCP tools to automate collection. The rule writes risk on the `user` and on the `src` host. It never creates a notable on its own. A day's risk can raise a notable through the HDSI RBA AI aggregators (see Related Detections).

## Detection Logic

### Plain English

1. **Prefilter.** `tstats` over `Endpoint.Processes` for rows where `process_name` or `process` contains `mcp` or `modelcontextprotocol`, grouped by user, host, process name and full command line. The tenant exclusion macro `hdsi_ai_mcp_server_execution_filter` sits inline in this `where` clause.
2. **Drop non-execution.** Package management (`npm install`, `pip install`, `uv add`, `docker pull` and similar) is dropped: installing an MCP package is not running it. IDE-extension auto-registration (`<client> mcp config|install ... --source=<extension>`, for example GitLens) is dropped too.
3. **Classify (`mcp_role`).** A row is kept only if one of these roles matches:
   - `mcp_server_binary`: the process itself is an MCP server (`*mcp-server*`, `*-mcp.exe`, `fastmcp`, ...).
   - `mcp_config_command`: an AI client changes its MCP configuration (`claude mcp add`, `docker mcp catalog`, ...). Scores 15.
   - `extension_mcp_server`: an AI client's MCP server started by an IDE extension (`gk mcp --source=gitlens`). Scores 15.
   - `ai_client_mcp_command`: an AI client run as an MCP server or gateway (`claude mcp serve`, `codex mcp-server`, `docker mcp gateway run`).
   - `mcp_package` / `launcher_mcp_argument`: a package runner or interpreter (node, npx, uvx, python, docker, ... from `hdsi_ai_mcp_server_execution_launcher_regex`) with an MCP package, image or script in the package position, such as `npx -y @playwright/mcp@latest`, `uvx mcp-server-git`, `python -m mcp_server_sqlite` or `docker run -i --rm mcp/fetch`. Shells, browsers, IDEs, `git` and installers are never read for arguments.
4. **Name and type.** `mcp_server` is taken from the binary, package, image or `<client> mcp`. `mcp_type` is one of filesystem, database, source_control, saas, browser, infrastructure, gateway, web_retrieval, memory, ai_client or unclassified. `data_access=1` for user-run servers of the first seven types.
5. **Redact credentials.** Up to five command lines (500 characters each) go into `mcp_commands` with bearer tokens, `*_API_KEY=` values, `--token` values, URL passwords and well-known key formats replaced by `<redacted>`.
6. **Clean the risk objects.** `user` is nulled for `unknown`, `SYSTEM`, `root`, `NT AUTHORITY\*` and machine accounts (`*$`), which gives system-only risk. Rows without a usable host are dropped.
7. **Aggregate** to one row per `user` + `src`.
8. **Allowlist.** Look up the user's `bunit` in `identity_lookup_expanded`, then `ai_unsanctioned_filter(user,src,provider)` with `provider="MCP Server"`.
9. **Score.** `ai_risk_multiplier` (bunit sensitivity x 1.25 for privileged identities, capped at 2.0), then `risk_score = min(60, round(base_score x risk_multiplier))`.
10. `hdsi_ai_mcp_server_execution_customizations`, then `hdsi_ai_mcp_server_execution_risk_score` as the last pipe.

### Thresholds

| Parameter | Default | Where | Notes |
|---|---|---|---|
| Base score, user-run data-access server | 40 | SPL (`evt_base`) | filesystem, database, source_control, saas, browser, infrastructure, gateway |
| Base score, other user-run server | 30 | SPL | web_retrieval, memory, unclassified |
| Base score, IDE-extension server or configuration command | 15 | SPL | |

## Triage Steps

> **Estimated triage time:** 10-20 minutes. Replace `$user$` and `$src$` with the values from the risk event. For a `DOMAIN\user` value, replace the backslash with `*` inside quoted search terms. Set the time picker to cover the risk event (24 hours to 7 days).

### Step 1: Validate the risk event

```spl
| from datamodel:"Risk.All_Risk"
| search source="Endpoint - HDSI AI MCP Server Execution - Rule" (risk_object="$user$" OR risk_object="$src$")
| table _time, risk_object, risk_object_type, risk_score, risk_message, mcp_activity, mcp_servers, mcp_types, mcp_roles, parent_display
| sort - _time
```

- Is the user a real person, or is the event system-only (machine account or unknown user)?
- Is `mcp_activity` "MCP server execution" (a running server, scored 30 to 60) or one of the 15-point forms (extension-started server, configuration command)?
- Is this the first day, or does the host show up every day (an established workflow)?

### Step 2: Identify the user and the host

```spl
| inputlookup identity_lookup_expanded
| search identity="$user$"
| table identity, first, last, email, managedBy, category, priority, bunit
```

```spl
| inputlookup asset_lookup_by_str
| search nt_host="$src$" OR dns="$src$" OR ip="$src$"
| table ip, dns, nt_host, owner, bunit, category, priority
```

- ES identities have no `department` field. `bunit` drives both group allowlisting and the risk multiplier.
- If the identity does not resolve as logged, search the bare name (without `DOMAIN\` or `@domain`).
- Is the host a developer workstation, a build or CI server, or a production server? An MCP server on a production server is more serious than one on a developer laptop.

### Step 3: Review the MCP process activity on the host

This is the rule's own "View MCP-related process activity" drilldown:

```spl
| tstats summariesonly=t allow_old_summaries=t count min(_time) as firstTime max(_time) as lastTime values(Processes.parent_process_name) as parent_process_name from datamodel=Endpoint.Processes where Processes.dest="$src$" (Processes.process_name="*mcp*" OR Processes.process="*mcp*" OR Processes.process="*modelcontextprotocol*") by Processes.user Processes.dest Processes.process_name Processes.process
| rename Processes.* as *
| convert ctime(firstTime) ctime(lastTime)
| table firstTime, lastTime, user, dest, process_name, process, parent_process_name, count
| sort - count
```

- Read the full command lines. Which server package, image or binary ran? Which arguments did it get (paths, connection strings, repository names, URLs)?
- `parent_process_name` names the AI client (Claude, Cursor, Code, codex, node). It was filled for 13-86% of events across the validation tenants, so a missing parent is normal.
- The raw command line is not redacted here. Treat any token it shows as exposed.

### Step 4: Review what the MCP server did

The rule's "View processes spawned by MCP servers" drilldown shows the children of the server process:

```spl
| tstats summariesonly=t allow_old_summaries=t count min(_time) as firstTime max(_time) as lastTime from datamodel=Endpoint.Processes where Processes.dest="$src$" (Processes.parent_process_name="*mcp*" OR Processes.parent_process="*mcp*" OR Processes.parent_process="*modelcontextprotocol*") by Processes.user Processes.parent_process_name Processes.process_name Processes.process
| rename Processes.* as *
| convert ctime(firstTime) ctime(lastTime)
| table firstTime, lastTime, user, parent_process_name, process_name, process, count
| sort - count
| head 200
```

- Shells, `git`, `curl`, database clients, `kubectl`, cloud CLIs or archive tools started by the server show what the agent actually did with its tool access.
- For a filesystem server, the arguments name the directories it was allowed to read. Check whether they hold sensitive data (home directory, source trees, finance or HR shares).

### Step 5: Check related AI risk for the user and the host

```spl
| from datamodel:"Risk.All_Risk"
| search (risk_object="$user$" OR risk_object="$src$") source="* - HDSI AI * - Rule"
| stats sum(risk_score) as total_risk dc(source) as detections values(source) as sources values(ai_kill_chain_phase) as phases by risk_object, risk_object_type
| sort - total_risk
```

```spl
`notable`
| search search_name="Threat - HDSI RBA AI *" ("$user$" OR "$src$")
| table _time, search_name, rule_title, urgency, status_label, owner
```

- MCP execution often fires alongside `Endpoint - HDSI AI Agent Framework Execution - Rule` and `Endpoint - HDSI AI Agent Autonomous Action Detection - Rule` for the same developer.
- This rule's events have `ai_kill_chain_phase=execution`, so they count as the AI half of `Threat - HDSI RBA AI Privilege Escalation Correlation - Rule` when the same account had a privilege change earlier in the window.
- The user threshold aggregators raise a medium notable at 60 points from at least 2 detections and a high notable at 90 (shared `ai_detection_config` rows `medium_risk_threshold` and `high_risk_threshold`).

### Step 6: Determine sanctioned status

```spl
| inputlookup ai_sanctioned_entities
| where enabled=1 AND in(lower(provider),"mcp server","*")
| table entity_type, entity, provider, scope, expires, owner, reason, allow_key
```

- Is the user, host or `bunit` approved for MCP use? Is the approval expired?
- Is MCP approved for the whole organisation (`*|mcp server`)? Then the rule should already be silent.

### Step 7: Make a determination

- **True Positive:** an unapproved MCP server with data access (filesystem, database, source control, SaaS, infrastructure) on a host or account that should not run one, or one whose arguments point at sensitive data or production systems.
- **Benign True Positive:** an approved developer workflow (Claude Desktop, Cursor or VS Code agent mode with MCP servers), or a vendor tool that ships an MCP server binary. Allowlist it with an expiry.
- **False Positive:** the classification picked up a non-MCP process (an `mcp`-named host, folder or image argument). Report the command line so the pattern can be fixed. Exclude the host with the filter macro meanwhile.

---

## True Positive Indicators

- The server type is filesystem, database, source_control, saas, infrastructure or gateway (`data_access=1`, base 40), and its arguments point at sensitive paths, production connection strings or corporate repositories.
- The host is a server, a jump host or a production system rather than a developer workstation.
- The command line carries credentials (redacted in `mcp_commands`, visible in the drilldown): personal access tokens, database passwords or cloud keys passed to the server.
- `mcp-remote` or `mcp-proxy` connects the client to an external, unknown MCP endpoint.
- Child processes of the server include shells, archive tools, `curl` or cloud CLIs running against data the user does not normally touch.
- The same user also has upload or exfiltration risk (`Network - HDSI AI High Volume Upload To AI Service - Rule`, personal-email correlation) on the same day.

---

## False Positive Scenarios

| Scenario | Likelihood | Mitigation |
|---|---|---|
| Approved developer workstations using Claude Desktop, Cursor, VS Code agent mode or Claude Code with MCP servers | High in developer-heavy estates | `ai_sanctioned_entities` rows for the user, host or `bunit` with provider `MCP Server` and an expiry |
| GitLens-style IDE extension starting its MCP server for the agent (15 points, once a day per workstation) | Medium | `search mcp_activity!="MCP server started by an IDE extension"` in `hdsi_ai_mcp_server_execution_customizations` if sanctioned |
| Configuration-only commands (`claude mcp add`, 15 points) | Low | `search is_exec=1` in the customizations macro |
| Vendor tooling that ships an MCP server binary (for example SQL tooling). Seen once on Tenant C: one development host, 414 launches in 7 days, system-only, database, score 40 | Low | Allowlist the host (`<host>\|mcp server`) or exclude the binary with the filter macro |
| A runner argument that is an `mcp`-named host or image-like value (for example `docker run --add-host mcp-x:...`) | Low (not seen on any tenant) | `NOT Processes.dest IN (...)` or `NOT Processes.process="*...*"` in `hdsi_ai_mcp_server_execution_filter` |

Bare `mcp` substrings are not matched. In one day of production data, about 9,000 `*mcp*` command lines across 4 tenants (names in file paths, vendor data files, host and service names, Windows Update correlation vectors, base64 tokens, an agent feature flag) were all correctly dropped.

## Response Actions

### If confirmed True Positive

1. **Contain:** stop the MCP server process and remove it from the client configuration (`claude_desktop_config.json`, `.cursor/mcp.json`, `.vscode/mcp.json`, `~/.claude.json` or the Docker MCP catalog). On a server or a host showing malicious child processes, isolate the endpoint through EDR.
2. **Notify:** the user's manager and the AI governance or data owner for the systems the server could reach.
3. **Investigate:** list what the server could reach (paths, databases, repositories, SaaS tenants) and what its child processes did (Step 4). Check upload and exfiltration risk for the same user. For `mcp-remote` or `mcp-proxy`, identify the remote endpoint in proxy or firewall logs.
4. **Remediate:** rotate every credential that appeared in the command line or the server configuration (personal access tokens, database passwords, API keys). Restrict MCP use to approved servers, and publish an approved MCP server list.
5. **Document:** record the server, its scope, the credentials rotated and the decision in the case.

### If Benign True Positive

1. Add an `ai_sanctioned_entities` row with provider `MCP Server`, a scope and an expiry (see Tuning Guidance).
2. Record the business justification in `reason`.
3. Close the related aggregator notable (if any) as benign.

## Tuning Guidance

### Reducing false positives

| Macro | Ships as | Use |
|---|---|---|
| `hdsi_ai_mcp_server_execution_filter` | `()` | Inline tstats exclusions, e.g. `NOT Processes.dest IN ("ci-runner-*")` |
| `hdsi_ai_mcp_server_execution_launcher_regex` | node/npx/npm/pnpm/yarn/bun/deno/tsx/uv/uvx/pipx/python/docker/podman | Runners whose package-position arguments count. Never add a shell |
| `hdsi_ai_mcp_server_execution_customizations` | `search *` | Post-aggregation, e.g. `search NOT mcp_servers="*approved-internal-mcp*"`, `search is_exec=1`, or drop extension-started servers |
| `hdsi_ai_mcp_server_execution_risk_score` | `search *` | Last pipe. Override or re-cap `risk_score` |

If a secret in an unusual position (a bare positional argument) can still reach `mcp_commands`, add `fields - mcp_commands` to the customizations macro and rely on `mcp_servers`.

### Adjusting thresholds

There is no count threshold. Before enabling, copy the rule's SPL into a search, run it over the last 7 days and append:

```spl
| stats count dc(src) as hosts dc(user) as users by mcp_activity, mcp_types, risk_score
```

Use the result to decide whether the 15-point rows are wanted and which developer users, hosts or groups to approve.

### Adding allowlist entries

The provider string is `MCP Server`. Keys are lowercase:

```
entity_type,entity,provider,scope,expires,owner,reason,enabled,allow_key
user,jdoe@example.com,MCP Server,provider,2027-03-31,security,approved_mcp_developer,1,jdoe@example.com|mcp server
system,dev-ws-0142,MCP Server,provider,2027-03-31,security,approved_mcp_host,1,dev-ws-0142|mcp server
group,engineering,MCP Server,group,2027-03-31,security,engineering_mcp_pilot,1,engineering|mcp server
group,*,MCP Server,global,2099-12-31,security,mcp_approved_org_wide,1,*|mcp server
```

- A host key is the only per-object key that covers system-only rows (machine accounts, unknown users).
- A `bunit` group key works only when the user resolves in `identity_lookup_expanded`.
- `*|mcp server` silences the rule for the whole organisation.

## Validation (2026-10-09)

Read-only live tests on 4 production ES tenants. The rule and its 3 drilldowns parse on all four.

| Tenant | Endpoint data | Rows 4h / 24h / 7d | Notes |
|---|---|---|---|
| A | About 6.5M process events an hour, full command lines | 0 / 0 / 0 | Only MCP-related activity was GitLens auto-registration (dropped). About 68k other prefilter events (mostly `cmd.exe`) were all classified as not MCP |
| B | Server-only endpoint data, machine accounts | 0 / 0 / 0 | No prefilter events |
| C | About 6.2M an hour | 0 / 1 / 1 | One MCP server binary for SQL tooling on a development host: system-only, database, score 40 |
| D | About 8k an hour | 0 / 0 / 0 | Only Windows Update correlation vectors matched the prefilter (dropped) |

A 68-command-line synthetic control gave the expected 29 kept and 39 dropped rows on every tenant. Expected volume: about 1 risk event a day on Tenant C, 0 elsewhere. Developer-heavy estates should expect about one event per active MCP-using workstation per day.
